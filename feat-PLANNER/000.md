## 第一段 · 目标与验收

### 一、目标状态的形式化

**输入**：用户在系统 `plan` 入口提出一段规划请求。
**输出**：一份 `P`。`P` 是 Markdown 文档。体例是 Knuth 伪代码 ＋ ASD-STE100 无样板变种中文。详细程度是保姆级。
**过程**：若干跑者接力。每个跑者是一段逻辑任期。跑者在同一物理 session 内轮换。
**终止**：最后一任交付 `P`。交付后本次规划结束。不进入实施。

跑者拿到的东西只有三样：

```text
U            本 work 内全部用户输入原文（runtime 拥有，模型不碰）
LWR_prev     上一任期的记录，剥掉 Opening（runtime 拥有，模型不碰）
P            伪文件 Markdown（模型唯一可写的 durable 产物）
```

模型能写的只有 `P`。`U` 与 `LWR_prev` 由 runtime 生成。

### 二、事实

### 三、根因

1. SWELoop 的阶段门是生产者自评。它可以被游戏，也可以死锁。
2. 底稿的收尾是生产者自决。它没有结构性检查。
3. 质量不能由生产者声明。质量由**必须使用凭据的下一个跑者**在行动中暴露。

所以本设计把阶段结束门改成交接。它不改成阻塞。

### 四、决策与取舍

| 决策 | 决定 | 门型 |
|---|---|---|
| 阶段结束门 | 改成交接，不改成阻塞 | 单向门 |
| 接力是否换上下文 | 换逻辑任期，同一物理 session | 单向门 |
| Plan 是否依赖 Road | 不依赖。Plan 自带极简轮换 | 单向门 |
| `P` 是否注入消息 | 不注入。只经 `js-plan` 读 | 双向门 |
| `P` 的读写面 | 走 JS 编程面，复用 `edit` / `rewrite` | 单向门 |
| 交付门 | `P` 写成功即可。取消读回校验 | 双向门 |
| 末任终态 | 另立 `PlanDelivered`。不背 Manager 的证书词汇 | 单向门 |
| 首任能否直接交付 | 不能。每条链至少一次交接 | 单向门 |
| 交付后能否再问 | 不能 | 单向门 |
| Manager 轮换是否现在重写 | 不重写。Plan 的极简形状留作参照 | 双向门 |

一条已知代价：取消读回后，系统无法证明「落盘字节 ＝ 预期字节」。崩溃发生在「写成功、终态未提交」窗口时，恢复只能凭写入时的摘要，不能复核内容。这条代价记在案，不假装它和读回等价。

### 五、验收

1. 每条链至少一次交接。没有后继的那一任才可 `deliver`。
2. 每一任只拿 `[U, LWR_prev, P]`。`U` 与 `LWR_prev` 由 runtime 生成，模型不碰。
3. 模型唯一可写的 durable 产物是 `P`。`P` 从第一任起就成形，逐段长成。
4. 交付门是事实门：`P` 落盘成功。不读回。
5. 崩溃后按 durable 事实重绑「当前任期 ＋ 阶段 ＋ `P`」。不靠内存。
6. 非 Plan 路径行为不变。
7. 三条宿主能力先验证：
   1. `transform` 能按任期隔离消息。
   2. `js-plan` 能把 `read` / `edit` / `rewrite` 绑到单一路径。
   3. `materialize` 的 `range` 语义正好等于一个任期。
   任一条不成立，先补对应 owner。不得绕过。

## 第二段 · 路径与理由

### 一、理解

未知量是一个机制。这个机制要做到：在同一物理 session 里换跑者，只交三样东西，模型只写 `P`。

### 二、探索

探索过五个候选。逐个列出未选的理由。

| 候选 | 未选的理由 |
|---|---|
| 复用 Road 作容器 | Road 可能消失。Plan 不该依赖它 |
| 复用 Manager 的证书、评估、快照 | 已裁为形式主义。快照更穿透每条事件与每次重放 |
| `P` 注入消息 | 会造出「消息里一份、文件里一份」两份真相 |
| 把 `P` 的读写做成普通工具 | 等于重造 `edit`。Markdown 补丁是刚需 |
| 自评门（`confidence` 与 `detail_clarity` 双满分） | 可游戏，且可死锁 |

另有一项分析结论：Manager 的轮换骨架是对的，载荷重。骨架七条可以复用：

1. durable 事件 fold，重放幂等。
2. 一个容器同时至多一个活跃任期。
3. 退休 → 开下一任。
4. stale 请求身份（`RetiredProviderRunIds` 与 `ProjectionCut`）。
5. 退休前的 blocker。
6. 固定 DevOps 绑定。
7. `IterationOrdinal` 由 durable openings 派生，不是执行游标。

载荷里另有五处现在就不优雅：

| 问题 | 位置 |
|---|---|
| `isForeignDevOps` 定义两遍 | `Fold.fs:526` 与 `Fold.fs:829` |
| `Decision` 层重复校验 `Fold` 已校验的规则 | `Decision.assess/retire/confirmRetirement` 对 `Internal.assess/requireRetirementTarget/requireBlockTarget` |
| `BoundDevOps` 有派生默认值，再被特判 | `Fold.fs:521`、`527`、`830` |
| `AuthorityRevisions` 与 `AuthorityMessageIds` 是两条必须下标对齐的平行表 | `Fold.fs:26-28` |
| `RoadView` 有 18 个字段，多数是 `option` | `Fold.fs:39-68` |

### 三、选定路径

1. 新增 `Role.Plan`。工具集是 `js-plan`（编程面）加 `ask`、`resume`、`handoff`、`deliver`（编排面）。
2. Plan 自带极简轮换：5 条事实、3 个阶段、约 250 行 fold。
3. `transform` 新增通用 disposition：轮换后按 baton 隔离。Plan 先用。Manager 以后可用。
4. 交接是一次前缀重锚。
5. 交付是 `PlanDelivered` 加唯一成功终态。

Plan 的极简轮换与 Manager 的对照：

| 项 | Manager | Plan |
|---|---|---|
| 事实 | 9 条 | 5 条 |
| 阶段 | 4 个 | 3 个 |
| view 字段 | 18 个 | 5 个 |
| fold 行数 | 约 890 | 约 250 |

### 四、检验与反思

1. **最容易漏的一条**：交接收缩消息集，撞上前缀稳定。交接必须是一次前缀重锚，开新 epoch。
2. **取消读回的代价**：无法证明「落盘字节 ＝ 预期字节」。恢复只能凭摘要。
3. **`U` 的因果边界**：一次 `deliver` 之后的用户输入，属于新的显式请求，不属于本 work。
4. **`js-plan` 的形态**：它是 JS 编程面。作用域只有 `P` 一个路径。它没有任何仓库能力。
5. **隔离 disposition 要写成通用的**：不写成 Plan 专用。否则 Manager 以后要用，还得再改一次 transform。
6. **硬编码清单要手工加名**：`StaticTools.fs` 的清单与 `InvestigationEstimateContract.classifyTool` 都禁止前缀匹配。

## 第三段 · 可照做的流程

### 数据

**事实（5 条）**

```text
PlanWorkOpened(workId, root)
PlanDevOpsBound(workId, devopsId, target)
PlanIncumbencyOpened(workId, incumbencyId, stage)
PlanIncumbencyRetired(incumbencyId, outcome)          # outcome ＝ Continue 或 Delivered
PlanDelivered(incumbencyId, workId, digest, path)
```

**状态（每个 work 一份）**

```text
Active            : { Id; Stage; Phase } option
Retired           : incumbencyId list
LatestRetirement  : (incumbencyId, outcome) option
BoundDevOps       : (devopsId, target) option
Delivered         : receipt option
```

**阶段**

```text
Phase  ＝ WorkOwned | EndingDeclared(intent) | CleanupBlocked
intent ＝ Handoff | Deliver
```

**路径**

```text
root ＝ <git-common-dir>/wanxiangshu
path ＝ root/plan/<canonical-work-key>/plan.md
```

### Algorithm A（身份与资源装配）

输入：仓库与现有角色目录。输出：`plan` 可被唯一托管，工具面与资源齐备。

```
A1. [登记角色.] 在 `Foundation/Roles.fs` 的 `Role` 增加 `Plan`。
    在 `roleLabel` 增加 `| Role.Plan -> "plan"`。
    在 `tryParseRole` 增加 `| "plan" -> Some Role.Plan`。
    把 `Role.Plan` 加入 `Roles.all`。
A2. [登记托管配置.] 在 ManagedAgent 目录增加 `plan` 条目。
    只写本插件拥有的字段：`mode`、`permission`、`hidden`、`prompt`、`temperature`。
    不写 `model`。
A3. [登记权限.] 在 `OfficeCapability` 增加 Plan 的权限。
    允许：`js-plan`、`ask`、`resume`、`handoff`、`deliver`。
    禁止：`read`、`glob`、`grep`、`edit`、`write`、`run`、`fork`、`fission`。
A4. [登记工具.] 在 `ToolRegistry` 注册五个工具。
    `js-plan` 走 JS 编程面。其余四个走编排面 ToolSpec。
    在 `StaticTools.fs` 的清单与 `InvestigationEstimateContract.classifyTool` 显式加名。
A5. [写资源.] 新建双语资源。成对提供，缺一侧即失败。
    `resources/provider/role/plan/{en.md,zh-CN.md}`
    `resources/provider/planning/s1/{en.md,zh-CN.md}`
    `resources/provider/planning/s2/{en.md,zh-CN.md}`
    `resources/provider/planning/s3/{en.md,zh-CN.md}`
    `resources/provider/tool/js-plan/{en.md,zh-CN.md}`
    `resources/provider/tool/ask/{en.md,zh-CN.md}`
    `resources/provider/tool/resume/{en.md,zh-CN.md}`
    `resources/provider/tool/handoff/{en.md,zh-CN.md}`
    `resources/provider/tool/deliver/{en.md,zh-CN.md}`
A6. [写阶段方法.] 三份 planning 资源分别写 S1、S2、S3 的方法与该段的内容体例。
    S1 段：目标形式化、事实、根因、取舍、验收。
    S2 段：理解、探索、路径、检验与反思。
    S3 段：Knuth 伪代码。
A7. [装配系统提示.] 在 `experimental.chat.system.transform` 按当前任期的 `stage` 装配对应方法。
    只按字节识别自己的段落。不翻译，不发明散文。
A8. [终止.] 算法终止。
```

### Algorithm B（轮换事实与 fold）

输入：Plan 的持久事件。输出：Plan 轮换投影。

```
B1. [定义事实.] 定义五条事件。见「数据」节。
B2. [定义状态.] 每个 work 一份。见「数据」节。
B3. [定义阶段.] 见「数据」节。
B4. [定义 fold.] 对每条事件执行 B5。
B5. [应用一条事件.]
    B5.1. [查重.] 若同一身份的事件已应用，且载荷相同，则忽略。转 B6。
    B5.2. [拒冲突.] 若同一身份的事件已应用，且载荷不同，则拒绝。转 B6。
    B5.3. [应用.] 按事件种类改状态。
B6. [断言.] 同一 work 至多一个 `Active`。
    `Retired` 只增不减。`Delivered` 至多一次。旧任期不得复活。
B7. [终止.] 算法终止。
```

### Algorithm C（任期隔离）

输入：一次 provider 请求的消息集。输出：本任期可见的消息集。

```
C1. [认身份.] 读本次 session 的 managed agent 角色。
    若 ≠ `plan`，则返回原消息集。
C2. [定任期.] 从 Plan 轮换投影读当前 `incumbencyId` 与 `stage`。
    若无活跃任期，则返回原消息集。
C3. [取 U.] 取本 work 因果范围内的全部真实 user 消息。
    保持原文、原顺序。不改写、不压缩、不重编码。
C4. [取 LWR_prev.] 若本任期不是首任，则取上一任期的记录。
    用 `materialize(range ＝ 上一任期, includeOpening ＝ false)` 渲染。
    若本任期是首任，则本项为空。
C5. [组装.] 消息集 ← U ＋ 记录消息（LWR_prev）＋ 本任期开始后的 assistant 与 tool 消息。
C6. [剥前任.] 前任任期的 assistant 与 tool 消息全部剥掉。
C7. [不注入 P.] `P` 不进消息集。模型经 `js-plan.read` 取。
C8. [重锚前缀.] 若本次是任期第一条请求，则记一次前缀重锚，开新 epoch。
    断言：本任期第一次 provider wire 是本 epoch 的起点。
C9. [终止.] 返回组装后的消息集。算法终止。
```

### Algorithm D（动作门）

输入：一次 Plan 工具调用。输出：许可或拒绝。

```
D1. [认身份.] 核对调用者 ＝ Plan，且 session 有活跃任期。否则转 D7。
D2. [查终态.] 若本 work 已有 `Delivered`，则只允许 `js-plan.read`。其余转 D7。
D3. [查在途.] 若有未结算的 `ask`、`resume` 或导出操作，
    则只允许结算该操作。新的外部效果动作转 D7。
D4. [判阶段动作.]
    若 `stage ＝ S1`，则只允许 `handoff`。`deliver` 转 D7。
    若 `stage ＝ S2`，则 `handoff` 与 `deliver` 都允许。
    若 `stage ＝ S3`，则只允许 `deliver`。`handoff` 转 D7。
D5. [判交付.] 对 `deliver`：核对无未结算外部操作，且输入版本未落后。否则转 D7。
D6. [许可.] 返回许可。
D7. [拒绝.] 返回 typed 错误。不留副作用。
D8. [终止.] 算法终止。
```

### Algorithm E（handoff）

输入：`handoff` 调用。输出：本任期退休，下一任期开启。

```
E1. [过门.] 执行算法 D。不许可则返回错误。
E2. [查 blocker.] 读本任期递归 live 资源：
    child、后台作业、PTY 与进程、活跃工具、副作用租约。
    有 blocker 则记 `CleanupBlocked`，返回 blocker 摘要。
E3. [定意图.] `intent ← Handoff`。
E4. [提交退休.] 一次事务写两条事件。
    `PlanIncumbencyRetired(incumbencyId, Continue)`
    生成下一任 `incumbencyId`。`stage ← 下一段`。
    `PlanIncumbencyOpened(workId, nextIncumbencyId, nextStage)`
E5. [断言.] `Retired` 加一。`Active` 换新。旧任期不得复活。
E6. [终止.] 返回下一任期的开始。算法终止。
```

### Algorithm F（deliver）

输入：`deliver` 调用。输出：唯一成功终态。

```
F1. [过门.] 执行算法 D。
F2. [查 blocker.] 同 E2。
F3. [取 P.] 从 `path` 读 `P` 当前字节。若为空，则返回错误。
F4. [算收据.] `digest ← sha256(字节)`。`length ← 字节数`。
F5. [提交终态.] 一次事务写两条事件。
    `PlanIncumbencyRetired(incumbencyId, Delivered)`
    `PlanDelivered(incumbencyId, workId, digest, path)`
F6. [断言.] `Delivered` 至多一次。这是唯一成功线性化点。
F7. [呈现.] 系统展示 `P` 的路径。不再调模型。不启动实施。
F8. [终止.] 算法终止。
```

### Algorithm G（ask）

输入：`ask` 调用。输出：用户原文回答。

```
G1. [过门.] 执行算法 D。
G2. [受理.] 追加待回答事实。关联调用身份。
G3. [显示.] 幂等显示问题与「等待回答」。
    不保持无限占用的 provider 请求。
G4. [停驻.] 停驻本次模型运行。不轮询、不催问、不消耗恢复预算。
G5. [等回答.] 循环，直到收到合法用户输入，或取消。
G6. [接受原文.] 用户原文 durable accepted，关联到该待回答调用。
    依据调用与物理消息的因果身份。不依据文本内容。
G7. [回送.] 只选一个路径：工具结果，或合法 continuation。二者互斥。
G8. [终止.] 返回用户原文。算法终止。
```

### Algorithm H（resume）

输入：`resume` 调用。输出：DevOps 本次 invocation 的完成记录。

```
H1. [过门.] 执行算法 D。
H2. [解析绑定.] 读本 work 的固定 DevOps 绑定。
    无绑定则 single-flight 创建。目标由运行时解析。
    模型不传 id、role、model。
H3. [投递.] 经 PromptDispatcher 投递调查目标。
H4. [等完成.] 等本次 invocation 的正式完成事实。
H5. [收敛.] 确认答复已被权威记录接受，且本次执行已收敛。
H6. [返回.] 把完整答复交给 Planner。不做模型二次摘要。
H7. [终止.] 算法终止。
```

### Algorithm I（`P` 的路径与读写）

输入：`workId` 与 `P` 的操作。输出：受限读写。

```
I1. [推导 key.] `canonical-work-key ← 安全编码(workId 的完整身份元组)`。
    模型不传路径。
I2. [推导路径.] `root ← <git-common-dir>/wanxiangshu`。
    `path ← root/plan/<canonical-work-key>/plan.md`。
I3. [拒逃逸.] 拒绝路径穿越、符号链接逃逸、不安全 id、根目录漂移。
I4. [读.] `js-plan.read()` 返回 `P` 全文。
    分页时显式返回是否还有内容与下一页游标。
I5. [编辑.] `js-plan.edit(patches)` 与 `js-plan.rewrite(content)` 只作用于 `path`。
    复用既有 `edit` 与 `rewrite` 原语。
I6. [写盘.] 每次写原子发布。
    创建排他临时文件。写完 flush。原子替换。不读回。
I7. [断言.] 模型唯一可写的 durable 产物是 `P`。它没有任何仓库能力。
I8. [终止.] 算法终止。
```

### Algorithm J（恢复）

输入：durable 事实与物理证据。输出：重绑后的运行位置。

```
J1. [读事实.] 读 Plan 轮换投影。定位 `workId`。
J2. [定位置.] `incumbencyId ← Active`。`stage ← Active.Stage`。
J3. [取 P.] 从 `path` 读 `P`。
J4. [判终态.] 若有 `Delivered`，则幂等呈现产物。不再调模型。
J5. [判在途.] 处理未结算的 ask、resume、导出。
J6. [断言.] 不按文本猜阶段。不凭同名 session 认 DevOps。
    事实不足则失败关闭，保留证据。
J7. [终止.] 算法终止。
```

### Algorithm K（施工顺序）

输入：A 到 J 的算法。输出：一次提交的闭环。

```
K1. [先证三条宿主能力.] 执行第一段第五条。
    不成立则先补对应 owner。
K2. [身份与资源.] 执行算法 A。
K3. [轮换 fold.] 执行算法 B。先写红测试，再写实现。
K4. [隔离.] 执行算法 C。先写红测试，再写实现。
K5. [工具与门.] 执行算法 D、G、H、I。
K6. [交付.] 执行算法 E、F。
K7. [恢复.] 执行算法 J。
K8. [门与回归.] 跑 language-parity-gate、provider-leak-gate、js-surface-gate、architecture。
    跑非 Plan 路径回归。
K9. [终止.] 算法终止。
```

### Algorithm L（验收）

输入：实现与测试。输出：证据。

```
L1. [纯规则.] 测 stage 到动作的许可。
    测首任不得 `deliver`。测交付后禁问。
    测 `P` 路径推导拒绝穿越与逃逸。
L2. [契约.] 测 `handoff` → `Continue` 加新任期加 stage 前进。
    测 `deliver` → `PlanDelivered` 加唯一终态。
    测同一事件重放幂等。测异载荷拒绝。
L3. [隔离.] 测交接后消息集 ＝ `U` 加 `LWR_prev`。
    测前任 assistant 与 tool 不在。测前缀重锚确实发生。测 `P` 不在消息里。
L4. [真宿主.] 测连续三任同一物理 session。
    测 `js-plan` 读写可用。测 `deliver` 后无新模型调用、无新调查。
L5. [记录.] 记命令、通过数、失败数、跳过数。
    未跑过的写「未验证」。不把「预计红」或「预计绿」写成证据。
L6. [终止.] 算法终止。
```

## 附录

### A. 术语

| 词 | 含义 |
|---|---|
| 跑者 | 一段逻辑任期。同一物理 session 内轮换。 |
| 接力门 | 阶段结束时的交接。它不是阻塞门。 |
| 交付门 | 唯一的硬门。`P` 落盘成功。 |
| `P` | 伪文件 Markdown。逐段长成，最终即交付物。 |
| `U` | 本 work 内全部用户输入原文。 |
| `LWR_prev` | 上一任期的记录，无 Opening。 |
| baton | 注入下一任的三样东西：`U`、`LWR_prev`、`P`。 |
| blocker | 递归 live 资源。它阻止交接与交付。 |

### B. 工具面

| 工具 | 形态 | 作用 | 门 |
|---|---|---|---|
| `js-plan` | JS 编程面 | 读、编辑、重写 `P` | 作用域只有 `P` 一个文件。无仓库能力。 |
| `ask` | 编排面 | 问用户一个问题 | 一次一个未决问题 |
| `resume` | 编排面 | 找本次固定 DevOps | 目标由运行时解析 |
| `handoff` | 编排面 | 出关：交棒给下一任 | 首任只能用它 |
| `deliver` | 编排面 | 交付：`P` 即最终稿 | 末段只能用它 |

### C. 三条链的形态

```text
S1 只能 handoff。        # 首任不得直接交付
S2 可以 handoff 或 deliver。
S3 只能 deliver。        # 末段无后继
```

最短链 2 任（S1 → S2）。最长链 3 任（S1 → S2 → S3）。

### D. 不在本次范围

1. 不把 `P` 交给 Manager。
2. 不启动实施。
3. 不重写 Manager 的轮换。只把它列为后续参照。
4. 不改仓库现有的 `js-*` 工具命名。
5. 不恢复 QA、SKILL、Teacher 一类旧机制。
6. 不新建知识存储。`P` 是唯一正式交付文件。
