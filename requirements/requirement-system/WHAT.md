# requirement-system — WHAT

## [001] 唯一语义所有权

任何一个产品规范命题在任意时刻恰归一个包所有，严禁无所有者，也严禁多所有者。

## [002] 包身份独立于物理布局

所有包的物理目录布局、文件名组织与元数据表现格式由本包定义。

## [003] 全部包同时为真

每个包的规范正文描述该能力当前的、可观察的合同，接受用户目标与反例的修订，不自动取得公理地位。包之间的依赖关系表示语义递进，不表示执行优先级或规范覆盖；被依赖的包不获得对下游包命题的裁决权威，反之亦然。实现性约束须说明其直接目的，不得因写入规范而免于随用户目标一并修订。

## [004] 测试属于条款

任何一个测试恰好属于某个条款。如果服务于多个包或条款，以主服务对象为准。

## [005] 所有语义均属于某个包

任何正式语义行为都必须归属于某个包的规范正文，其他文件不得定义正式的语义行为。规范文件由 [007] 指定。合同以当前实现为据，不宣称由包内容对系统做无遗漏复现。

## [006] 包的完整性

所有合法包必须完整包含 `WHY.md`、[007] 指定的规范文件与 `tests/` 目录。缺少当前规范文件时必须报告失败，不以旧导航页替代。

## [007] 每包只有一份规范正文

`verification-system` 的规范正文是 `AXIOMS.md`：AXIOM 写关切与理由，LEMMA 写前提、推理和适用条件，SPEC 写可验收的条款及证明范围。其他尚未迁移的包仍使用 `WHAT.md`。包目录下只有指定文件可以定义正式条款，`WHY.md` 仅解释设计理由与动机。

旧链接可以保留导航页，但不能保留另一份条款正文或在新文件缺失时回退。迁移规范文件时须同步规范发现、完整性、唯一归属和引用检查；格式转换不改变包所有权，也不表示旧运行设施已经迁移。

## [008] 条款 ID

正式命题 ID 只能在包的指定规范文件标题中定义；`AXIOMS.md` 的编号条款放在 SPEC 部分。其余文档只能引用，格式形如 `requirement-system-008`。
测试标题中的 `WHAT[pkg-NNN]` 是稳定的条款索引，不表示必须读取同名文件；本次格式迁移保留既有编号与测试锚点。
命题废止后其编号永久空缺，不得复用。

## [010] 不保存历史

当前规范不得提到已废止的历史行为，哪怕是负面陈述也是不必要的。

## [011] 提案

未来材料与延期提案归存于 `proposals/` 目录并由用户全权管理。除非用户明确要求阅读/操作，否则直接忽略。

## [015] 直接闭环

对于规范的局部修复、代码简单重构、测试补充或文档排版，允许在单次提交内原子化对齐规范、代码与证明，但严禁借机弱化用户体验或殃及其他正式条款。

## [017] 包结构测试

必须维护可执行的测试，对 `requirements/` 全树进行机械化扫描验证。如果某条款已删除，对应的测试需要提示用户进行相应处理。

## [018] 规范和测试的印证

测试标题中的 `WHAT[pkg-NNN]` 锚点用于定位所验证的条款，是导航而非构建资格；跨包真实场景可同时覆盖多条承诺，只需标明一个主要归属并在必要处引用其余条款。同一命题的测试是否拆分为多个文件，由测试的独立使用方式决定。
覆盖缺口由 `requirements/GAP.md` 如实记录。完成条件是受托目标已实现且剩余结果真实，不要求压降 GAP 数量后再宣告完成。
