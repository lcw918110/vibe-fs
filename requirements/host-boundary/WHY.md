# host-boundary — WHY

## 存在理由

Host 提供物理运行能力，业务系统决定这些观察意味着什么。流式碎片、传输重试和界面变化容易重排或随版本改变；把它们当成业务完成，会让偶然时序变成产品承诺。粗粒度唤醒配合完整快照，把观察与解释分开。

身份也要对得上。一次会话可能包含多次物理执行，只有会话 ID 分不清某条消息是否开始、失败或结算。精确配对、唯一定位和明确的未知状态，避免旧信号终结新工作。

## 边界的取舍

公开 Hook/SDK 让集成不依赖 Host 私有实现；契约测试说明预期，真实 Host canary 看环境是否兑现。两者缺一时，模拟测试跑绿不足以支撑业务承诺。

动态 JavaScript 值需要在入口验证实际类型，Fable 类型标注不能代替运行时检查。类型化失败把参数拒绝、物理故障和致命错误分开，使普通拒绝不会杀死进程，也使致命退出不会先于已持有资源的结算。

合同、消息解码、信号订阅与物理运行时关注不同知识。窄合同和单向依赖能避免读取一个消息就连带获得整个 Host 的工厂和进程能力。可选诊断只帮助解释观察，不能反过来改变准入、恢复或结算。

## 生命周期与结果可信度

加载插件与激活业务分开，能防止注册 Hook 时提前恢复、发起请求或写入业务事实。订阅与工作区定位有明确的所有者，资源释放才能有可检验的终点。

工具结果在交给 Host 前完成确定性限界，保留有用的尾部并说明截断，避免传输层再随机丢弃内容。真实子进程退出才算最外层的物理效果；日志写着失败、收到 HTTP 响应或界面显示结束，都不能替代它。

给 provider 的提示不等于执行授权。提示字段可以被错误填写，真正的能力门禁仍看身份与当前事实；提示的暂时清理若改写原调用，就会让历史与实际执行脱节。恢复必须保留同一份参数及其顺序，异常路径也不能失去这条联系。
