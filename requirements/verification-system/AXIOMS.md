# 测试与验证规则

本文是 `verification-system` 的唯一规则正文，约束本仓测试的编写、运行、优化和报告。使用时先读本文，再读被测模块的现行合同；本文不替业务模块定义行为，也不替库侧规则规定工具链。

`WHAT[verification-system-NNN]` 定位到同编号 SPEC；[WHAT.md](WHAT.md) 仅作导航。规范检查器按[规范文件约定](../requirement-system/WHAT.md)读取本文，缺失时报错，不回退。规则变更、实现变更和验证通过分别记录。

AXIOM 写关切与理由，LEMMA 写推理与适用条件，SPEC 写验收与证明。宿主、工具和协议的具体选择在相应 SPEC 中明示，不把现有实现当作公理。证明入口不等于通过记录；结果与范围见[测试说明](tests/README.md#条款与证据)和所链接的实验记录，未证明部分标为 `[TODO]`。

## AXIOM

1. [使用者] **承诺真实成立。** 测试应能发现被测行为违反合同。
   - 理由：测试通过只有在能够暴露目标错误时才有价值。
2. [使用者、开发者] **结论可复核。** 输入、执行范围、结果和未知部分应可区分。
   - 理由：漏执行、隐藏失败或混用版本会误导后续决定。
3. [开发者] **同等验证的成本越低越好。** 成本包括整次等待、计算和维护。
   - 理由：重复准备和无效等待不增加保护；削减覆盖也不是同等验证。
4. [使用者、开发者] **资源有明确归属。** 测试的影响限于约定的验证范围。
   - 理由：遗留资源会拖慢后续工作，误清共享资源会破坏仍在履行的承诺。

## LEMMA

### L1 — 按承诺选择最小充分边界

- 前提：AXIOM 1、3。
- 推理：不同承诺需要不同观察。选择足以暴露目标违约的最小边界，可以减少准备成本而保留证据效力。
- 适用条件：按合同和实际副作用选择；物理行为须有物理证据。只有共享生命周期本身属于承诺时，才要求连续的真实场景。

### L2 — 判定依据独立且能够失败

- 前提：AXIOM 1、2。
- 推理：判定依据若复刻实现的错误，测试会一起算错。反例若只触发缺依赖等无关异常，也不能证明检查有效。
- 适用条件：断言对照合同；静态门禁用合规输入与受控违约验证。断言充分性和判定依据的独立性仍需审阅。

### L3 — 结束等待与结束工作分别处理

- 前提：AXIOM 1、3、4。
- 推理：等待返回不代表任务或竞争分支已结束。清理须按所有权释放失效资源，不破坏合同要求继续运行的工作及其保护。
- 适用条件：资源所属作用域决定释放或移交责任。撤销活跃登记前须确认任务结束或移交；验收证据按 [021] 保存。

### L4 — 因果和时钟各自提供证据

- 前提：AXIOM 1、3、4。
- 推理：固定 sleep 不能证明目标状态已到达；事件、握手和屏障能提供因果证据。虚拟时钟可重放逻辑顺序，不能证明物理资源释放。
- 适用条件：逻辑时序用虚拟时间，真实计时器、事件循环和进程回收用物理观察。等待设明确结束条件，诊断采集有界。合同允许参数化预算时可用较小测试值；针对固定期限的回归保留该期限，不改动待验边界来掩盖失败。

### L5 — 比较收益先保证比较对象一致

- 前提：AXIOM 2、3。
- 推理：环境缺失、崩溃和陈旧缓存都可能让测试更快，却减少实际验证。数量相同也可能运行了不同用例。
- 适用条件：对照时核对输入、环境和用例身份，声明被比较的改动。准备复用按其失效条件校验相关版本、输入及产物；共享状态与资源的范围、所有权须明确。

### L6 — 报告完整范围与完整成本

- 前提：AXIOM 2、3。
- 推理：测试正文完成后，结果流和进程可能仍未结束。局部耗时、CPU 用时或 worker 时间总和不能代表用户的整次等待。
- 适用条件：验证范围由改动影响和委托目标决定。整套提速任务或整套收益声明须有同范围完整对照；重复次数由波动与结论所需证据决定。失败基线不代表全绿流水线的性能。

### L7 — 门禁服务于可说明的违规

- 前提：AXIOM 1、2、3。
- 推理：路径不存在而空跑，或拒绝合法的替代实现，都会误导结论。门禁须区分目标违约、合法实现和检查失败。
- 适用条件：只声称检查器实际能识别的范围；不以形式扫描代替行为证明或人工审阅。

## SPEC

### [001] 按承诺与副作用选择检查

前提：LEMMA L1。

按承诺选择检查：纯计算直接检查，逻辑时序使用虚拟时间，真实环境行为使用真实组合。互不依赖的场景可在隔离环境中分别验证；必要的物理边界不得用替身代替。

- 证明方法：结合具体用例审阅合同与验证边界；层级标签或措辞扫描不能证明边界充分。可识别的具体违规仍可设门禁，按 [004] 验证。

### [002] Long Stroke 的生命周期范围

前提：LEMMA L1、L4。适用：承诺依赖同一物理生命周期的宿主验收。

Long Stroke 从单一入口启动，在同一物理环境的单次生命周期内完成。相互独立的端到端场景可在隔离环境中并行。

- 证明入口：[002](tests/002.test.mjs)、[014](tests/014.test.mjs) 验证注册、编译和发布控制。真实场景的执行须另有记录。

### [003] 检查选择而非固定阶梯

前提：LEMMA L1、L6。

按 [001] 选择必要检查并说明选择依据，不要求 Pure → Temporal → Adapter → Long Stroke 逐级通过，也不为层级选择另设用户确认。局部验证如实报告范围；未运行（not-run）、失败（failed）和通过分别记录。

- 证明入口：[017](tests/017.test.mjs) 验证聚焦选择与发布入口的区别；[021](tests/021.test.mjs) 验证结果分类。具体选择是否充分仍需审阅。

### [004] verifier 必须可红

前提：LEMMA L2、L7。

测试必须能因目标要求被违反而失败。每个静态门禁用同一检查实现验证合规输入和受控违约：前者通过，后者因目标违规以非零退出码失败。与目标要求无关的缺依赖、加载失败或异常不算有效反例；不得为通过而削弱断言。

- 证明入口：[004](tests/004.test.mjs)，覆盖已列门禁的受控正反例。

### [005] 检查异常必须失败

前提：LEMMA L2、L6、L7。

门禁、运行器及验证基础设施遇到数据损坏、协议失配、不可解析的边界状态或未知异常时，停止受影响的验证，按 [008] 回收本次拥有的资源，并以非零退出码报告失败。清理失败也须报告，不吞没原始错误，不报告通过。

就绪超时或就绪前退出不得计为通过。

- 证明入口：[005](tests/005.test.mjs)，覆盖受控故障和失败传播。

### [006] 因果推进

前提：LEMMA L3、L4。

挂死监测贯穿验证过程，以距最近一次因果进展的静默时长判断；首次进展前从监测开始计时，不仅凭总运行时长判定。续期须有受监测目标实际推进的证据，无关活动或重复观察不得续期。

达到静默限值时，先报告目标、当前等待和最近进展，再按 [008] 收尾并以非零退出码结束。缺失信息说明原因；诊断采集有界，监测不得拖延正常结束。

- 证明入口：[006](tests/006.test.mjs)、[覆盖明细](tests/README.md#006-的测试用例与证明范围)。[TODO] 全程接线和业务进展分类仍有未闭合边界。

### [007] Temporal

前提：LEMMA L1、L4。

Temporal 层使用虚拟时钟、可注入时间端口和显式因果轨迹（trace）；时间推进离散且可枚举。逻辑时序证明不得依赖真实 sleep、物理时钟或偶然调度。真实超时和物理资源另按 [001] 验证。

- 证明入口：[007](tests/007.test.mjs)，覆盖虚拟推进、取消和轨迹重放。

### [008] 断言与资源释放

前提：LEMMA L2、L3。

断言覆盖目标合同要求的结果、顺序及副作用；合同规定精确结构或序列化文本时，完整比较。

测试与夹具按各自作用域释放所拥有的资源，或明确移交继续运行的工作。正常结束、启动失败、异常、取消、超时、挂起与恢复等适用路径均须履行该义务；清理失败如实报告，旧回调不得干扰恢复后的调用。`finally`、`use` 等是实现手段，不限定内部写法。

资源回归验证本作用域结束后的真实释放；涉及仍需运行的工作时，同时验证其合同保护。`Promise.race` 不自动取消另一方；强制退出或仅禁止资源保活不能代替释放。不要求其他测试或整个宿主的资源归零。

- 证明：原优化分支的[定时器回归与实验记录](https://github.com/dyx13/vibe-fs/blob/4a29ac65e22b17b234b6c5816fb1380d53f90016/evidence/test-optimization-20261027/README.md)覆盖调用结束及挂起恢复路径；该实现未随本次规则变基移植。[TODO] 当前上游的相应资源路径须另行验证；任意测试的断言充分性仍需审阅。

### [009] 静态门禁命中真实路径

前提：LEMMA L5、L7。

静态门禁的路径、匹配规则和入口须对应实际检查范围。必需目标缺失或被错误的匹配规则漏掉时报错，不得把漏扫写成通过；合同允许为空的检查集合按该合同处理。

- 证明入口：[009](tests/009.test.mjs)，覆盖目标路径及发现、执行计划；计划可达不等于用例已执行。

### [010] 验收判据不可放宽

前提：LEMMA L2、L5、L6。

未经正式规范修订，不得放宽现行正式合同已确定的验收判据、缩小该合同要求的验收范围，或将按该判据应阻塞验收的问题降为不影响通过。

在不改变合同义务的前提下补充或重构测试，或按 [003] 进行局部验证，不因此要求修订规范。删除冗余或失效断言须保留现行合同的有效保护。发布验收不得选择性采用重跑结果掩盖未解决的失败或不确定性。

等覆盖对照须保持需求场景、有效断言、属性样本、seed 和失败缩减能力一致。重构或新增回归单列，说明原义务如何继续受保护。减少覆盖、增加跳过或压低原有预算，不得计作等覆盖提速。

- 证明入口：[010](tests/010.test.mjs) 覆盖预算与不重试调度；原优化分支的对照见[实验记录](https://github.com/dyx13/vibe-fs/blob/4a29ac65e22b17b234b6c5816fb1380d53f90016/evidence/test-optimization-20261027/README.md)。其他改动须分别核对覆盖与失败。

### [011] 覆盖率门禁分母完整

前提：LEMMA L5、L7。

覆盖率分母必须涵盖全部项目生产模块，并与生产模块清单及当前编译产物核对一致；编译器运行库、外部依赖、测试和工具脚本不计入。未被测试加载的生产模块必须以 0% 覆盖率计入，严禁为填充分母而全量预加载模块，或擅自排除生产模块。

- 证明入口：[011](tests/011.test.mjs)，覆盖生产分母、未载入模块和损坏、陈旧报告的拒绝。

### [012] 禁止机械行数检查

前提：LEMMA L7。项目选择：不设文件行数政策。

门禁只针对明确的语义违规、架构越界或规范不变量破坏。不得按文件行数设置硬门禁或警告，也不为证明政策存在而增设机械扫描。

- 证明入口：[012](tests/012.test.mjs)，以受控正反例验证已知静态模式，允许普通行数测量。

### [014] Long Stroke

前提：LEMMA L1、L4。项目约定：本条约束本仓 OpenCode 连续场景，不要求所有测试经过该场景；宿主迁移须另行核对接线与业务义务。

Long Stroke 必须在同一 OpenCode 进程的单次生命周期内，验证以下真实行为：

1. 嵌套 Replica 物理启动且不阻塞属主；
2. 伴生会话的前缀律、批次合并、会话删除捕获与结算；
3. 直接 HumanRoot Manager 循环的多轮迭代、权威消息继承与状态收敛；
4. 运行态 Join 屏障、无变更冷检索（Cold Fetch）与真实 Host 插件观测点。

- 证明入口：[014](tests/014.test.mjs)；静态检查或跳过真实场景均不能证明本条通过。

### [015] 日志观察器因果消费与完整性

前提：LEMMA L2、L4、L6。协议范围：使用本仓 Journal Observer 取证的验证设施。

日志观察器（Journal Observer）只能将完整、合法的 `Fact` 记录识别为事实，不得根据正文关键字猜测。多字节 UTF-8 与未闭合行必须等待完整行结束符到达后，才能消费并提交位点。

非法 JSON、`event_id` 冲突、文件身份替换或已消费前缀截断必须报错。多写入者交错时仍须按日志顺序完整消费，位点单调前进，订阅通知与消费一致；关闭后停止监听与派发。日志的原子追加由 durable-events 的存储契约保证。

- 证明入口：[015](tests/015.test.mjs)。覆盖消费完整性、损坏拒绝和关闭；不替写入方证明原子追加。

### [016] 验证输入版本与结果适用性

前提：LEMMA L5。

工作树验证在运行前记录输入摘要，阶段间重新采集并比较。发现变化时报告失败，不继续把后续阶段算作同一版本的验证；既有结果只适用于其实际输入。边界采样不能证明阶段内或采样前从未发生变化。

稳定发布使用显式准备、与并行编辑隔离的源码产物完成构建和验证。归档须保留路径逃逸与所有权校验；是否完整归档由交付需要决定，不作为每次检查的前提。

耗时对照记录前后代码版本，固定被比较改动之外的运行时、工具能力、依赖、测试输入、并发、预算、层级和缓存条件，保留产物新鲜度检查。核对发现、启动、完成及 skip/TODO、失败的用例身份；文件数或通过数相同不足以证明范围一致。非预期的环境变化、崩溃或漏执行的轮次保留并调查，不用于等覆盖提速结论；声明目标改动也不能免除 [010] 的等覆盖要求。

- 证明入口：[016](tests/016.test.mjs) 覆盖输入集合与步骤边界；[TODO] 完整输入隔离、阶段内改后恢复和实际验证入口的结论绑定仍待证明，见[覆盖明细](tests/README.md#条款与证据)。

### [017] 日常与发布验证

前提：LEMMA L1、L6。项目约定：本仓宿主验证入口。

日常全量入口依次执行格式、静态检查、构建、unit 与 integration；发布入口另加 Long Stroke 与打包证明。按 [001] 可选择受影响 requirement 的聚焦套件，不必每次全量运行。完整发布结论仍须有全部适用阶段的证据。

- 证明入口：[017](tests/017.test.mjs)。覆盖阶段顺序、聚焦选择和失败停止；调度测试通过不等于真实发布通过。

### [018] FCS 扫描禁令

前提：LEMMA L7。项目选择：不以编译器扫描作为额外取证设施。

全仓禁止自建 FCS（`FSharp.Compiler.Service`）扫描，禁止为扫描取证额外启动或插桩编译器；正常构建使用 FCS 不受此禁令约束。

实际构建的常驻适配器可在 `scripts/compiler/Checker.fs` 与 `scripts/compiler/toolchain.mjs` 使用编译器 API；这些文件同样不得增加扫描取证入口。

- 证明入口：[018](tests/018.test.mjs)，以受控正反例验证已知扫描模式，允许普通构建。

### [019] 测试行为与准备成本

前提：LEMMA L1、L2、L5。

优先断言可观察行为。源码扫描用于明确的静态约束，不用词形猜测业务行为，也不把合同未限定的内部写法作为验收条件。

可复用昂贵的不可变准备，按其失效条件校验相关版本、输入及产物，并保留验证边界。无关用例不得相互污染可变状态、权限或可写目录；合同要求共享状态或资源的场景，由场景夹具明确管理所有权与收尾，场景之间不泄漏状态或资源。

收益计入准备、失效、清理和维护成本。共享夹具或缓存的新增复杂度须由当前验证需要或实测收益支持，不以“通用”为引入或禁止它的理由。

- 证明方法：按具体测试审阅验证边界、状态与资源归属，性能收益由 [016]、[021] 的对照确认。源码形式检查不能代替这些判断；针对具体违规的检查仍按 [004]、[009] 验证。

### [020] 属性测试

前提：LEMMA L2、L5。

输入生成器只构造合法、边界或明确非法的输入，不计算预期结果；不得重建被测状态机作为 oracle（预期结果的判定依据）。

无限或组合爆炸的输入域固定 seed、限定 run budget，失败时输出可重放的 shrink path；有限小域优先穷举。随机样本不代表穷尽证明，oracle 独立性须能说明。

### [021] 验证范围与结论

前提：LEMMA L5、L6。

报告原定范围、实际完成范围及未完成原因，区分被测对象违约与验证未取得有效结论。未执行、无有效结论和范围外事项不计通过；局部通过不表述为整体验收通过。

耗时从入口启动计至结果排空和资源回收完成，包含该入口的准备；unit 与完整流水线分别报告。测试正文时间、CPU 用时或 worker 时间总和不能代替整套实际耗时；墙钟长而 CPU 用时少只能作为调查线索，不能据此判定泄漏。逐轮记录改动、覆盖、耗时、失败、波动及排除原因，说明保留或放弃策略的依据；未解释的可靠性变化单列。

运行器的协议约定：嵌套监督将子进程 stdout/stderr 解码为 UTF-8 诊断文本后转发，不得继承外层协议流或向其中写入原始二进制块。node:test worker 的 stdout 专用于原生结果协议，子进程诊断转发到 stderr；普通独立命令保留两条流的区分。解码保留跨块的合法字符，非法 UTF-8 可用替换字符，不宣称保留了原始二进制。诊断中的协议头诱饵不产生结论；权威结果只来自独立 IPC 及完整收尾证据。

- 证明入口：[021](tests/021.test.mjs) 覆盖结果分类、排空与嵌套输出协议；原优化分支的耗时与排除轮次见[实验记录](https://github.com/dyx13/vibe-fs/blob/4a29ac65e22b17b234b6c5816fb1380d53f90016/evidence/test-optimization-20261027/README.md)。[TODO] 全仓报告链的范围传播仍需核查，见[缺口记录](../GAP.md)。单次实验的提速比例不作为其他任务的目标或承诺。
