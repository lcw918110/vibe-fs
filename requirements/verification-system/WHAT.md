# verification-system — WHAT

## [001] 按承诺与副作用选择检查

检查层级由被验承诺与真实副作用决定，而非一条所有命题都必须逐级通过的固定阶梯：纯计算直接检查；需要时间确定性的部分使用虚拟时间；承诺真实环境行为的用真实组合检验。需要真实环境而场景互不依赖的承诺，可在独立环境中分别进行，不必共用单一环境。

## [002] Long Stroke 的生命周期范围

Long Stroke 用于确实依赖同一共享生命周期的承诺，保持单一入口并在同一物理环境的单次生命周期内完成；相互独立的端到端场景不受此限，可在独立环境中并行进行。

## [003] 检查选择而非固定阶梯

语义命题按承诺与实际副作用选择必要检查，不要求 Pure → Temporal → Adapter → Long Stroke 逐级通过，也不以“不适用须用户确认”作为通用门。局部范围内单独运行并如实报告其范围；not-run 与 failed 必须始终区分，失败不得改成通过。

## [004] verifier 必须可红

所有测试必须能因所验证的要求被违反而失败。每个静态门禁必须有回归测试，以受控反例输入证明其能准确识别违约，并以非零退出码报告失败。严禁为使测试通过而削弱断言。

## [005] 中止

所有门禁、运行器与基础设施遇到数据损坏、协议失配、不可解析的边界状态或未知异常时，必须安全失败，并以非零退出码向上层报告；严禁吞没异常或报告通过。

就绪超时或就绪前退出不得计为验证通过。

## [006] 因果推进

验证执行必须全程按距最近一次因果进展的静默时长判断挂死，首次进展前从监测开始计时；严禁仅以总运行时长判断。因果进展必须有受监测目标实际推进的证据，无关活动及同一进展的重复观察不得续期。

达到静默限值时，必须先输出因果诊断，再以非零退出码安全结束验证。诊断须说明受监测目标、当前等待及最近进展；无法取得的信息须标明缺失及原因，诊断采集不得无限阻塞退出。监测不得拖延验证正常结束。

## [007] Temporal

Temporal 层测试必须基于虚拟时钟、可注入的时间端口与显式因果 trace，所有时间推进必须离散且可确切枚举。语义与逻辑证明严禁依赖真实 sleep 或物理时钟、调度的偶然性。

## [008] 断言有效性

测试必须完整断言所验证命题要求的结果及副作用，不得以弱于要求的检查替代。规范规定精确结构或序列化文本时，必须完整比较。

## [009] 静态门禁命中真实路径

静态门禁的扫描路径、目录匹配规则及检查入口必须对应真实存在的检查对象，严禁因目标不存在而空跑通过。

## [010] 验收判据不可放宽

未经正式规范修订，执行者不得放宽已冻结的验收判据、缩小验收范围，或将阻塞项降为不影响通过。删除冗余或失效断言不得削弱现行要求的有效保护。发布验收不得通过选择性采用重跑结果掩盖尚未解决的失败或不确定性。

## [011] 覆盖率门禁分母完整

覆盖率分母必须涵盖全部项目生产模块，并与生产模块清单及当前编译产物核对一致；编译器运行库、外部依赖、测试和工具脚本不计入。未被测试加载的生产模块必须以 0% 覆盖率计入，严禁为填充分母而全量预加载模块，或擅自排除生产模块。

## [012] 禁止机械行数检查

门禁只针对明确的语义违规、架构越界或规范不变量破坏。严禁基于文件行数设置硬门禁或警告，严禁仅为证明政策存在而设立机械扫描门禁。

## [014] Long Stroke

Long Stroke 必须在同一 OpenCode 进程的单次生命周期内，验证以下真实行为：

1. 嵌套 Replica 物理启动且不阻塞属主；
2. 伴生会话的前缀律、批次合并、会话删除捕获与结算；
3. 直接 HumanRoot Manager 循环的多轮迭代、权威消息继承与状态收敛；
4. 运行态 Join 屏障、无变更冷检索（Cold Fetch）与真实 Host 插件观测点。

## [015] 日志观察器因果消费与完整性

日志观察器（Journal Observer）只能将完整、合法的 `Fact` 记录识别为事实，不得根据正文关键字猜测。多字节 UTF-8 与未闭合行必须等待完整行结束符到达后，才能消费并提交位点。

非法 JSON、`event_id` 冲突、文件身份替换或已消费前缀截断必须报错。多写入者交错时仍须按日志顺序完整消费，位点单调前进，订阅通知与消费一致；关闭后停止监听与派发。日志的原子追加由 durable-events 的存储契约保证。

## [016] 验证输入版本与结果适用性

日常验证在当前工作树运行并记录其观察到的输入版本（运行前采集的输入摘要），阶段间重新采集输入并与起始摘要比较。输入中途变化时，后续阶段不再适用并以失败报告，已得结果只对变化前的输入版本成立；运行前是否发生变化无从观察，不得宣称“全程未变”。

稳定发布验证使用系统显式准备的源码产物完成构建与验证，与并行编辑隔离，其结论不受原工作树继续编辑影响。归档材料的路径逃逸与所有权校验始终保留；是否启用完整归档由具体交付需要决定，不是每次检查的前置条件。

## [017] 日常与发布验证

日常验证执行格式、静态检查、构建、unit 与 integration；发布验证另加 Long Stroke 与打包证明。全量流水线是发布便利入口，不是唯一可接受的完成路径：可按受影响 requirement 运行聚焦套件并如实报告实际范围。not-run 与 failed 必须始终区分，任何失败都不得改成通过。

## [018] FCS 扫描禁令

全仓禁止自建 FCS（`FSharp.Compiler.Service`）扫描，禁止为扫描取证额外启动或插桩编译器。
实际构建的常驻适配器可在 `scripts/compiler/Checker.fs` 与 `toolchain.mjs` 使用编译器 API；这些文件同样不得增加扫描取证入口。

## [019] 测试行为

尽量不使用扫描源码的测试，测试应该测试行为而非实现。

## [020] 属性测试

输入生成器只能构造合法输入、边界输入或明确非法的输入，不得计算预期结果；严禁在测试中重建状态机作为平行 oracle（预期结果的判定依据）。

无限或组合爆炸的输入域必须固定 seed、限定 run budget，并在失败时输出可重放的 shrink path；有限小域优先穷举。无法说明 oracle 独立性的随机测试不得宣称提供完整证明。

## [021] 验证范围与结论

验证报告必须说明原定范围、实际完成范围及未完成原因，并区分被验对象违反要求与验证过程未取得有效结论。未执行、未取得有效结论及范围外事项不得计为通过；局部通过不得表述为整体验收通过。

嵌套监督时，子进程 stdout/stderr 按 UTF-8 诊断文本经父进程转发，不能借继承的文件描述符或原始二进制块写入外层测试协议流。嵌入 node:test worker 时，其 stdout 专用于原生结果协议，子进程的诊断转发到 stderr；普通独立命令仍保留 stdout/stderr 的区分。文本解码必须保留跨块的合法多字节字符；非法 UTF-8 可显示替换字符，不宣称诊断文本是原始二进制存档。输出中即使出现类似协议头的字节，也不得被解释为测试结论；权威结果仍只来自独立 IPC 通道及其完整收尾证据。
