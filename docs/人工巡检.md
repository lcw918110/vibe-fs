# 人工巡检方法

巡检回答一个唯一的核心问题：**用户打开软件，提出需求，系统是否能按预期帮用户把事情做完、做成，且不留隐患。**

巡检不是数测试用例，不是核对函数签名，更不是看 AI 验收报告是否全绿。它关注的是在真实宿主与真实工作场景中，软件的实际行为是否符合预期。

## 一、核心原则：总流程为纲

一切巡检围绕总流程展开：
**用户需求 → 合理交互 → 查清事实 → 稳妥修改 → 真实完成。**

| 巡检维度 | 关注重点 | 不接受的替代品 |
|---|---|---|
| 用户意图 | 机制是否真正解决了用户痛点？用户能否直接理解并掌控当前状态？ | “历史代码就是这么写的”、“规范条目规定如此” |
| 行为与边界 | 职责划分是否干净？谁负责做决断，谁负责执行？是否把脏逻辑渗入了核？ | 函数名对上了、测试 mock 全绿、注释里写了声明 |
| 真实体验 | 真实模型在真实宿主（OpenCode 等）中能否可靠做成？遇到异常能否干净降级或由人接管？ | AI 打印了“全部完成”、跑了虚假测试、仅有日志无实际产出 |

## 二、巡检步骤

1. **先看意图与价值**
   抛开历史包袱与临时实现，直接看这个功能在总流程中到底扮演什么角色。如果删掉这个机制用户感知不到任何损失，或者它只是为了“证明自己正确”而堆砌的检查员，那它就是债务，应当标记清理。

2. **追查真实路径**
   从真实的输入入口（例如宿主信号、用户消息、工具调用）一路向下追踪：
   - 是否存在中间绕道、空实现、假拦截？
   - 报错与失败时，错误信息是否对人诚实晓畅？
   - 状态是否真落盘？故障重启后是否能按真实因果恢复？

3. **现场场景实操**
   - 走一条最直接的正向路径（Happy Path），看能否顺利做成。
   - 走一条常见的失败路径（如超时、网络断开、非法输入），看系统是体面停下并交待清楚，还是陷入死循环或假装成功。
   - 检查是否有资源泄漏（僵尸进程、未关句柄、孤儿文件）。

## 三、三层分工对照

巡检时核对职责是否符合三层分工契约：
- **万象理（核）**：是否保持 Smalltalk / Actor 式的自治与中立？绝不出现具体宿主（OpenCode / omp / Cline）的专有名词与特异行为。
- **万象通（适配）**：所有针对宿主怪癖的翻译、参数转换、hook 抹平是否收拢在此处？
- **本仓（产品面）**：提示词与工具资源是否在为总流程服务？是否已去除证明崇拜与假进度表？

发现与目标不符之处，明确标出“程序待改”或“架构待移”，不把现状当成真理，也不拿口号掩盖缺口。
