# 人工巡检方法

巡检只回答一个问题：**用户打开软件，提出需求，系统能不能按预期把事情做完、做成，且不留隐患。**

它不数测试用例，不对函数签名，也不看谁打印了「全部完成」。它看真实宿主、真实模型、真实工作里的行为。

## 一、总流程为纲

一切围绕这条线：**用户需求 → 合理交互 → 查清事实 → 稳妥修改 → 真实完成。**

| 看什么 | 关注点 | 不算数 |
|---|---|---|
| 用户意图 | 机制真解决了用户的难处吗？用户能否看懂当前状态并掌控它？ | 「历史代码就是这么写的」「规范条目如此」 |
| 行为与边界 | 职责是否干净？谁决断、谁执行？脏逻辑有没有渗进核？ | 函数名对上了、mock 全绿、注释里写了声明 |
| 真实体验 | 真实模型在真实宿主（OpenCode 等）里能否可靠做成？出岔子能否干净降级或由人接手？ | AI 自报完成、虚假测试、只有日志没有产出 |

## 二、巡检步骤

1. **先看意图**。抛开历史包袱，看这个功能在总流程里演什么角色。删掉它用户感知不到损失，或者它只是为「证明自己正确」堆的检查员，那就是债务，记下待清。
2. **追真实路径**。从真实入口（宿主信号、用户消息、工具调用）往下追：
   - 有没有中间绕道、空实现、假拦截？
   - 出错时的话是否对人诚实、说得清？
   - 状态真落盘了吗？故障重启后能否按真实因果恢复？
3. **现场走一遍**。
   - 走最直接的正向路径，看能不能顺利做成。
   - 走常见的失败路径（超时、断网、非法输入），看是体面停下并交待清楚，还是死循环、假装成功。
   - 查资源泄漏：僵尸进程、未关句柄、孤儿文件。

## 三、三层分工对照

巡检时问两句：这段东西离开具体宿主还有没有意义？它该由谁拥有？

- **万象理（核）**：状态有主人的中立能力在这里自治，不认识具体宿主（OpenCode / omp / Cline）的类型、生命周期词、工具名、环境变量语义。
- **万象通（适配）**：宿主专有的东西收在这里——消息长相、hook 次序、工具参数与错误文案、配置与环境、wire 解码。
- **本仓（产品面）**：提示词、工具资源与顶层组装。它可以直接消费万象理的公开入口，不必先经万象通。

「离开宿主也有意义」不等于「必须进核」：本仓可以直接用，也可以只留薄薄一层组装。反过来，凡是只对某个宿主才成立的东西，别塞进核。依赖只朝下：本仓 → 万象通 → 万象理，本仓 → 万象理。发现反向认识，标「程序待改」，不当场重排。

对不上目标的地方，标「程序待改」或「架构待移」。不把现状当真理，也不拿口号盖住缺口。发现的东西写一句人话，不进证明栏，不数违例。
