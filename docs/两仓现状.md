# 两仓实际现状与资产盘点（纠偏令闸门 A 清单）

> 本文件为纠偏令闸门 A 阶段对宿主仓 `wanxiangshu` 与中立核 `wanxiangli` 的只读摸底人话清单。
> 依据两仓代码与文件系统实际现状整理，区分静态检索事实与已证实运行行为，不将未逐一核实的模块一概判定为健康或待删，不修改业务源码。

---

## 一、两仓实际状态归属（State Ownership）

### 现状事实
1. **宿主仓（wanxiangshu）仍在承载庞大的历史状态模型与流程实体**
   - `src/Wanxiangshu/` 下现有 1,600 余个 F# 源码与工程配置文件，由 `src/Wanxiangshu/compile-order.txt` 进行全量线性编排。
   - 会话生命周期、任务规划、持久化流水（如 `Persistence/Journal/`、`Mission/Lifecycle/DurableWorkHost.fs` 等）在宿主仓内依然拥有独立且完整的数据结构与实体实现。
2. **核侧（wanxiangli）已备齐独立子模块与契约导出，但尚未达成全量 clean-break 切换**
   - `wanxiangli/package.json` 对外导出了 40 余个独立的 Smalltalk / A-B-C 模块（如 `./work`、`./eventstore`、`./durable-work`、`./session` 等），自带基于 Node.js 官方测试套件的独立校验。
   - 宿主仓目前仅在 `src/Wanxiangshu/Omp/Adapter.fs` 等少数点位通过 Fable 宏（`[<Import("...", "wanxiangli/...")>]`）引用了部分包（如 `pair-hint`、`scope-progress`、`projection`）。
   - **判定**：两仓当前处于“新核已备、旧核未退”的双轨状态。宿主仓尚未达成收敛为 empty 的目标，领域状态所有权尚未完成向万象理的实质交割。

---

## 二、宿主适配层与三层结构落点（Host Adapters）

### 现状事实
1. **万象通（wanxiangtong）已确立文档落点**
   - 目录与规范说明文件 `wanxiangtong/README.md` 已由并行工作建立，明确了万象通作为主工作树外层子目录、承担宿主“翻译税”与脏活隔离层的定位。
2. **具体宿主适配逻辑当前仍主要嵌在宿主仓内部**
   - **OpenCode 适配**：插件入口为 `package.json` 的 `main`（指向 `./dist/OpenCode/Plugin/Plugin.js`），源码实现在 `src/Wanxiangshu/OpenCode/Plugin/Plugin.fs` 与 `PluginHooks.fs`，直接处理 OpenCode 的消息结构、工具调用与 hook 回调。
   - **omp (oh-my-pi) 适配**：实现在 `src/Wanxiangshu/Omp/Adapter.fs`，负责映射 omp 扩展协议。
   - **核侧涉宿主模块**：`wanxiangli/src/host-omp/` 目录下保留有明确的 `AGENTS.md` 规范文件，并在头部明确标为“程序待改：宿主（omp / OpenCode / Cline）的专有适配与翻译税应位于外部适配目录万象通（wanxiangtong），不应常驻中立核内，待后续迁移至万象通”。核侧调查亦指出该模块涉及 omp 的特定工程适配；它绝非无意义的空目录残余，但从职责分工上看属于应当迁出核侧、归入万象通的宿主翻译层。
   - **判定**：虽然万象通的架构落点与定位已在文档中明确，但实际的宿主翻译代码尚未从宿主仓 `src/Wanxiangshu/` 剥离迁移到 `wanxiangtong/` 下。

## 三、运行路径与持久化落地（Operational Paths）

### 现状事实
1. **构建与运行入口**
   - 顶层构建入口为 `package.json` 中的 `"build": "node scripts/build.mjs"`。
   - `scripts/build.mjs` 串联子模块 `wanxiangli` 构建与宿主仓 Fable 编译（输出至 `dist/`）。
2. **数据路径契约**
   - 抽查的主要持久化模块与路径契约（如 `src/Wanxiangshu/Persistence/Journal/RuntimePath.fs` 等）均显式指定工作区下的 `.Herdchestra/` 作为持久化状态目录，主工作树与 linked worktree 共享该约定，且未发现使用已退役的 `.git/wanxiang*`。
   - **注意**：上述结论来自主要契约与关键点位抽查，未做 1,600+ 源码文件的全量运行时遍历，不排除深层或历史分支仍有未被触发的硬编码隐蔽路径。

## 四、历史证明装置、门禁脚本与观测逻辑辨析

### 现状事实
1. **形式化证明装置与旧规范负担**
   - `requirements/` 目录下存留 52 个子包及 `GAP.md`，包含大量旧规范文本、oracle 验收栏与检查员逻辑。
   - `scripts/checks/` 下留存 20 余个静态审查与基线校验脚本（如 `fatal-inventory-gate.mjs` 等），依赖基线 JSON 对全仓代码实施硬性比对，属于典型的“维持正确性”自嗨门禁。
2. **严谨区分“证明税”与“真实因果/物理运行观测”**
   - 静态全局检索中存在数百处包含 `witness` 或 `proof` 命名的符号与文本。
   - **必须区分对待**：不能因名称包含 witness 就一概认定为应开除的“证明税”。例如核侧 `wanxiangli/src/run-witness/ProviderRunWitness.fs` 实际承载的是针对 provider run 物理调用的执行模型路由与不可变观测记录，属于真实物理事件的捕获与因果记录；而旧 requirements 中的 AI 自动验收证明栏、基线棘轮警察才是需要坚决清除的证明税。

## 六、已知未确定事项与闸门限制

1. **未逐一核实的模块不可断言全量健康或一律待删**：
   万象理导出的 40 多个包及宿主仓 1,600+ 文件体量巨大，本次盘点仅从架构拓扑、顶层依赖及主要契约层面开展抽样与宏观梳理。各模块在具体业务浪花下的成色、冗余度与可用性，需在后续各环节逐一核实，不可凭目录或文件存在冒进下结论。
2. **闸门 A~D 的严格限制**：
   当前处于闸门阶段（盘点、纠偏、调结构、清理/重组支撑程序）。在负责人明确确认过闸门之前，**严禁开新的功能迁移刀，严禁使用自动化脚本批量迁移代码**。当前工作重心应集中于结构诚实化（如万象通职责界定）与支撑体系瘦身。
