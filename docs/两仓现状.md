## 二、程序状态 owner 现在在哪

### 2.1 核侧已有真实能力，宿主也确实在消费

- 静态事实：宿主 F# 源码里有 49 种不同的 `wanxiangli/<入口>` 模块被 Fable `[<Import>]` 引用，覆盖 `runtime`、`fission-group`、`dispatch`、`chat-execution`、`authority`、`projection`、`handle-lifecycle`、`program`、`identity`、`casebook`、`capability`、`delegate-batch` 等。按入口名去重后统计 import 出现次数只能说明「宿主代码提到这些入口多少次」，不能说明这些入口在运行时真正持有多少状态。
- 要判断某个入口是不是真实 owner，得看它的状态是否存在、跨回合是否留存、重启后能否恢复；这些需要按调用点逐个读，或者跑真实会话，本轮没做。所以这里只记「宿主引用了核的 49 个入口」，不推断迁移进度，也不推断双写风险。

### 2.2 宿主仍持有的状态

- `Persistence/`（35 个文件）与 `Mission/Lifecycle/DurableWorkHost.fs` 仍是宿主持有的会话、任务与流水实现；事件账本落在 `.Herdchestra/wanxiangshu/events/`（NDJSON），`advisor-process.sqlite` 等 SQLite 由宿主直接持有。
- `Composition/`（31 个文件）拥有跨库编排：`Durable/` 的 Journal 适配、`Turn/` 的普通回合工作流与调度、`Plugin/`、`Omp/` 的组装入口。
- `Execution/`（144 个文件）是最大的领域块：会话、委派（fork / resume / join）、Fission、路由、等待。部分规则已上核（`fission-group`、`handle-lifecycle`、`routing`），会话与结算的权威仍在宿主。
- `Interaction/Authority/`、`Interaction/Admission/` 仍持有交互权威与准入事实的宿主侧 fold。
- 路径契约：状态根是主工作树的 `.Herdchestra/`（`OpenCode/Host/PathsPort.fs`、`Persistence/Journal/RuntimePath.fs`），检索未发现读取 `.git/wanxiang*` 旧路径。
- **判断**：以上是「宿主源码里有这些领域与持久化实现」的静态事实。哪一份是当前唯一权威、是否与核里的同名能力双写，要按状态读取路径核实，本轮未核实。闸门内不动业务，登记为过闸后逐个核实的迁移面。

### 2.3 核侧的例外与宿主词汇

- `wanxiangli/src/run-witness/`、`authority/` 的 `ClosureWitness`、`capacity/` 快照核对、`program/Catalog.fs` 的 `todowrite-for-<role>` 工具名、`routing/RoutingProtocol.fs` 与 `resources/Language.fs` 的 `wanxiangshu.mjs` / `WANXIANGSHU_*` 已在核的《例外清单》登记，使用方与解除条件写清。核侧不再重复。
- **更正上一版**：`wanxiangli/src/host-omp/` **不存在**。核子模块 `359a1ec`（2026-10-28，「Fix package manifest and remove stale host documentation」）已删除 `src/host-omp/AGENTS.md` 并从 `package.json` 摘掉该入口；核内仅剩两处文档行文提到「旧草稿称物理时钟 / 执行在 host-omp，已撤回」（`src/runtime/process/AGENTS.md`、`src/runtime/time/AGENTS.md`）和 `wanxiangli/AGENTS.md` 的「旧文称 GAP / host-omp 的宿主适配，目标归万象通」。核里已无该目录、无该导出。

### 4.2 witness / proof 词汇在程序里

- 宿主源码里 `witness` 散落在数十个 `.fs`，例如 `OpenCode/Host/DeliveryWitnessWriter.fs`、`Composition/Durable/Projection.fs`、`Execution/Session/ChatExecution/*`、`Interaction/Authority/Facts.fs`。数量不是判断依据，不在这里维护。
- 按万象理第 7 条：**按使用方判断，不按名字处决**。闸门内不批量改名、不批量删；过闸后沿调用点逐处判断：删了它，操作员会在总流程上立刻做错事吗？不会就删或迁出核。
- 核《例外清单》登记的两处不算已判定的证明税：`run-witness` 的 `ClosureWitness` 编解码仍被宿主的执行路由与 `Run.fs` 真实消费，`capacity` 快照核对仍在外层对不上时收手。它们的解除条件写在核里——沿调用点判断哪些记录是真实运行所需，剩下迁出核或删掉，不凭名字删。

### 4.3 测试装置

- 统一入口 `requirements/verification-system/tests/run.mjs`（staleness gate + `node:test` 监督 + 计数），`verify.mjs` 的 `unit` 步调它；`integration/run.mjs` 先跑 `scripts/warmup-opencode.mjs` 再跑集成。
- `verify.mjs` 文件头已改写成 phases 叙述（format → static checks → build → unit → integration，release 再加 Long Stroke 与真实 npm 包），不再有 proofs / oracle 字样；`AXIOMS.md` 也是说明书口径（「不设证明栏、验收栏、witness 表」）。
- `scripts/coverage.mjs`（c8）挂在 `npm run coverage`，不在 `verify` 链上；测试覆盖不是胜利指标。
