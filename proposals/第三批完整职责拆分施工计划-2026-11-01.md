## 第一项：附着会话的建立、复用、替换和退场

### 用途、现状和归属

同一工作再次委派给同一种角色时，复用属于它的子会话；原关联消失时按原协议替换，工作结束时释放自己的关联。真实生产链是 `PluginSessionWiring` 创建 `AttachedSessionRuntime`，再由 `SyncDelegate/Workflow` 的 `GetOrCreate` 消费，当前 Engineer/DevOps 路径在用。

先读 [AttachmentLeaseCore.fs](../src/Wanxiangshu/Execution/Session/Attachment/AttachmentLeaseCore.fs)、[AttachedRuntime.fs](../src/Wanxiangshu/Execution/Session/Attachment/AttachedRuntime.fs)、[CompanionLeaseRuntime.fs](../src/Wanxiangshu/Execution/Session/Attachment/CompanionLeaseRuntime.fs)。库已有 `AttachmentLease` 规则与 `AttachmentLeaseRegistry`，本项补齐它们外侧的建立/复用/清理过程，不重复抽注册表。CompanionLeaseRuntime 当前只确认 SatelliteSurface/AttachmentSurface 构造；保持这些消费者，不宣称插件已用，也不新增产品入口。

建议从现有 `attachment-lease` 导出 `AttachmentSessions(registry)`，拥有调用中的协作，所有 bindings/flights 仍归传入的唯一 registry。公开消息草图：

```text
getOrCreate(spec, { isUsable, observe, create, link })
ensureAssociated(spec, { list, create, abort, link, close })
retireAssociated(owner, kind, { abort, close })
```

`spec` 使用 owner、kind、agent、title、directory、restoreHint 等中立值；结果保留 Created/Reused/Replacement 和原失败通道。两个建立入口对应现存两种寿命，不能强行合成同一套 finally。外层负责 role→kind、ReuseScope、宿主子列表、root/owner children 合并、精确标题和 SDK 调用；`registerParent/bindChild/onReady` 保留原顺序，通过 link 适配执行。库接收操作及观测结果，不接收整个宿主 runtime。

### 必须保持的行为

- 已有可用绑定直接复用，返回创建时的 agent；后一次请求不能改写。不同 owner/kind 分别持有，删除子会话时仍能反查其 owner。
- 没有 restoreHint 就创建，不因同名兄弟存在而收养。有 hint 时，唯一 id 还要 agent/title 精确一致；歧义与冲突保持原错误。
- 替换时先创建，再关闭消失的旧关联，最后 Link 新子。Close/Link 返回普通 Error 时，仅 fresh 子会话需要 Abort；Abort 返回 Error 被忽略，原错误保留，Abort Promise 拒绝仍向外传播。
- Reused 失败不 Abort。同步委派的发布钩子仍是原来的 unit 回调；不新增补偿或持久关联。
- Attached 的观测 Error/拒绝发生在现有 FinishEnsure finally 之外，可能保留 flight；Companion 的 finally 范围不同。迁移原样保留，不顺手改成自动重试或全部清理。
- Companion 退场按 Abort → Close → Remove → Finish；普通 Error 继续收尾且 Abort 错误优先，Promise 拒绝会中断。Clear 只删除该适配拥有的 kind，不清共享 registry 的其他租约。

## 第二项：一次命名程序的文件效果和终局结算

### 用途、现状和归属

一次命名程序可以读写文件、暂停、恢复，最后报告实际落地的效果。即使程序或结算失败，已发生的文件变化仍须如实返回；暂停不能把本次已积累的效果和待结算记录丢掉。

真实链为 [OpenCode/ToolHost.fs](../src/Wanxiangshu/Repository/Programming/Js/OpenCode/ToolHost.fs) → [ToolWorkflow.executeValidated](../src/Wanxiangshu/Repository/Programming/Js/ToolWorkflow.fs) → [JsPrograms.forSession](../src/Wanxiangshu/Repository/Programming/Js/Programs.fs) → 库 ProgramSession.execute。[ToolsBindings.fs](../src/Wanxiangshu/Repository/Programming/Js/ToolsBindings.fs) 创建 FileSession，ToolWorkflow 的闭包仍持有 staging、reads、settlementFailure。

扩 `program` 为完整 `ProgramInvocation`，拥有本次文件效果集合、显式读记录、终局结算及原失败对象的携带。ProgramSession/Run 继续持有命名运行、重放和 park/unpark/close；runtime.FileSession 继续实际操作文件；[JsAsIsLedger](../src/Wanxiangshu/Repository/Programming/Js/TransactionStore.fs) 继续按现行规则记录审计。不得新增第二份 ProgramSession、run registry 或审计账本。

公开面草图：

```text
ProgramInvocation({ root, ledger, observe, checkReturn })
  .execute(session, optionsWithoutApiAndSettle, buildApi)
  -> Promise<{ receipt, settlementFailure? }>
```

对象自行创建真实 FileSession，用 before/after/read 观察维护集合；`buildApi(files)` 只添加现有能力投影、RuntimeTools 和动态宿主成员。ledger 仅暴露 prepared/committed/settle，保留原 token/失败对象；observe 接 reads/effectPaths；checkReturn 使用现有返回值规则，返回 code/reason 及不透明原失败。主程序仍用 JsToolsData 给 Bookkeeper 等入口解析，不复制一套 validator 进库。

宿主活动租约、权限/评审、委托/Ask、产品回执和 TOML 留适配。BookkeeperTool 的 CasebookEdit 是另一种调用级事务，继续走原路径，不为了统一把它塞进本对象。

### 必须保持的行为

- 显式读按 Path 去重并保留首条；效果四类保留发生顺序，effectPaths 不另加去重。只有实际 after 才记录落地效果，before 仍建立原审计准备项。
- 先 observe；它原本吞掉的异常继续吞掉。再等待 ledger.Settle 等完全部记录、按发起顺序选首失败，最后检查返回值。失败仍带已落地 effects，不回滚，不改审计写入/等待/失败策略。
- JSON.stringify 的抛错继续交原 Run settle 异常路径。即时调用的 Failed 在相同 code 时保留原 F# JsFailure 引用；不能为跨 unpark 找回失败而增建全局错误表。
- parked 目标保存原 API、ledger 和集合闭包；执行 unpark 的控制程序不冒领目标的 effects。动态 host/ask 每次成员调用重新 resolve，不能在创建 invocation 时冻结旧租约。
- noteCaller 仍在 outputRoot 取得后执行，clearCaller 仍在原 finally。PluginSessionScope 仍先 closeSession，再按返回的 pendingNames 写 Reaped；不要提前释放 parked 程序的文件能力。
- lifecycle 持久写入仍由原 Run 顺序等待，lifecycleError 原样返回。executeValidated 当前未使用的 `settlement`、`deadlineEpochMs` 不借迁移恢复成旧交付机制。

## 第三项：一次提示派发的发送、确认和迟到回执

### 用途、现状和归属

提示已经认领并记入日志后，真正发送到宿主；回执可能先到、物理消息可能晚到，Detached 发送还可能在调用返回后才失败。本项收齐这一次发送的整个寿命，让“已发起”“有回执”“物理接受”“结果未知”保持原来的区别。

先读 [Send.fs](../src/Wanxiangshu/Interaction/Dispatch/Send.fs)、[Dispatcher.fs](../src/Wanxiangshu/Interaction/Dispatch/Dispatcher.fs) 和 [PhysicalAcceptance.fs](../src/Wanxiangshu/Interaction/Dispatch/PhysicalAcceptance.fs)。现有 root 与 continuation 的实际方法、Manager idle dispatch 都消费这些过程。起点是本次 PromptClaimed 成功落盘；授权根创建、选择 continuation 和 ManagedChat 接纳仍是各自领域工作，不把整个 Dispatcher 当成同一个模块搬入。

扩 `dispatch` 为 `DispatchAttempt(promptPhysicalAcceptance)`，提供 `sendInitial(spec,effects)` 与 `sendContinuation(spec,effects)`。它拥有一次发送的 terminal subscription、acceptance registration、confirmation lease、pending send 及迟到回执协作。PendingClaims 仍归 Journal projection，物理等待者归已有全局 PromptPhysicalAcceptance；不再建 pending/settled 字典。gateNudgeFlights 仍按 Runtime 实例持有。

`spec` 携带 key、await/detached、observer 的 notify/own/budget、原发送观测和失败通知。effects 提供 subscribe、send、submitted、acceptPhysical、abandon 和 diagnostic；send 返回原有五类 NativeSendOutcome，SDK 对象不进库。continuation 另外提供同步 `admit()`，承接原第二次 RequireActiveProfile 和 physicalAdmission。返回 Sent、NotSent、Failed、AdmissionRejected，保留原 reason 或不透明失败对象。

库安排发送、持久回执和清理；回调只做单个现有操作。主体负责 PromptRequest/metadata、文案和 Diagnostic/F# 形状。不得把全部“该怎么发送”再次委托给一个 hostWorkflow 回调。

### 必须保持的行为

- Claimed 持久失败时不订阅、不发送。真正发送前 observer 已取得本次注册，可立即 dispose；own/AttachDisposable 抛错只释放本次新 lease，再按原方式传播。
- continuation 最后一次 admit 必须同步，成功后立即调用真实 SendPrompt，中间不能 await。校验的时点不能前移到 claim 之前。
- Await 收到 receipt-only 先记 Submitted；只有存在 observer 才等物理确认，没有 observer 可返回 key。physical-id 路径仍按 Submitted → AcceptPhysical。
- Detached 先真实调用 SendPrompt，再记 `accepted-detached-${key}` 的本地 Submitted；成功即可返回，SDK Promise 永不完成也不能阻塞这次返回。即使 SDK 返回 physical-id，也不据此写 PhysicalAccepted。
- Unknown 不追加、不 abandon、不重发。Refused 走既有 Abandon，取消该 key 等待；OwnedSettled 不写额外事实。SDK Promise 与 late listener 两路保留，不能加 settled 锁吞掉 Unknown 后的 Refused。
- 普通 Result Error 与 Promise 拒绝的结算不同：发送失败中的 Abandon Error 按旧分支忽略；admit 拒绝后 Abandon Error 可覆盖原失败；Detached 拒绝的 Abandon Error 只诊断。settle 异常仍返回 Failed 且 notSent=false。
- initial 的 Detached 持久失败当前没有统一释放 acceptance registration，continuation 则会释放；保持两条现行路径，不加万能 finally。Dispose 自身异常也不统一改写成另一类发送失败。

## 第四项：模型执行准入、容量借用和精确释放

### 用途、现状和归属

用户或代理发起一次模型执行，系统为这一次物理输入保留容量；等待、续接、工具结束和旧回执到达时，都不能误删另一执行的资源。这项迁完整的准入和资源协调，约涉及 ModelRoutingRuntime 的一千多行及 ModelCapacity 的协作，不再切出几个 map/helper。

先读 [ModelRouting.fs](../src/Wanxiangshu/Execution/Routing/ModelRouting.fs) 与 [ModelCapacity](../src/Wanxiangshu/Execution/Routing/ModelCapacity/)。真实链包括 [ChatAdmissionTransaction](../src/Wanxiangshu/Interaction/Admission/ChatAdmissionTransaction.fs) 的 acquire/commit、SessionExecutionBinding 的 enterStep、HostSignalBootstrap/ExecuteGate 的 endStep，以及 SessionRecoveryHost、PluginSessionScope、SyncDelegate.Runtime 的 exact release/continue。

**当前生产事实：** `ensureShared()` 直接构造 `ModelRoutingRuntime(null)`，模型来自宿主选择。测试可注入 scheduler，但主流程没有加载旧 MJS 配置入口。本项不恢复该入口，也不改变谁选择模型。

扩现有 `routing`，增加 `ExecutionRouting` 组合对象。它持有 activeBySession、activeProviderStepTasks、continuationInputs、heldPhysicalReleases、固定 target 缓存、superseded/stopped physical 集合和 fatalError。已有 `permit`、`admission-queue`、`borrowing`、`run-witness` 各自继续持有 token、队列或观察；通过公开入口调用，不能重新复制状态或跨工程编译实现。

公开面围绕现有使用过程收敛：

```text
ExecutionRouting({ scheduler: null | policy, readBoundTarget? })
  acquire({ session, physical, role, participant, purpose, lender?, hostTarget? })
  commit(lease, exactIdentity)
  releaseBeforeProvider(lease, exactIdentity)
  tryRead(session, physical)
  releasePhysical(session, physical) -> Released(outcome) | HeldForInput
  retainInput / tryInput / cancelInput / cancelSessionInputs / continue
  enterStep / endStep / suppressStep
```

acquire 保留 Admitted、Queued、QueueFull、Cancelled、Superseded；Queued 返回原 completion Promise 的节点，不压扁为“等完才返回”。lease/node 作为不透明对象传递，不从字段重造。其余 reserve、绑定与 provider-run 查询只按现存消费者保留。

SDK model 形状、角色到字符串的转换、宿主事件含义、durable resolver 安装和共享实例装配留适配。进程共享实例只能有一个；两个插件不能各 new 一个资源 owner。固定目标由已有读取能力提供，不能让库导入 DevOps 宿主模块或全局配置。

### 必须保持的行为

- 同一 physical 重试保留 target，并核对 role/participant；reservation adoption 不重复占 token。TryRead 只读已 commit 的执行，不暗自升级 reservation。
- 新请求因满队列尚未获准时不能先抹旧 active；队列上限仍为 32，跳过暂不 eligible 的队首，释放后按现行次序重扫。
- 续接先 retain 旧 permit，旧 physical release 返回 HeldForInput；continue 到新 physical 时重定向所有 retained 引用。最后取消才 exact release，不按 session 清掉新 pending。
- 迟到 release 不影响新的 physical。provider step 的 requestKey 缓存只在非空时生效；结束/抑制只清原 exact 前缀。
- scheduler 错误保留原异常并使当前、等待和后续请求进入既有 poison 状态；不吞错改用默认模型。测试 scheduler 保持三个参数和同步结果限制。
- 固定 target 的冷读取、冲突、缓存及 DropSession 行为不变；没有固定记录的普通请求仍走宿主选择。未知、观察到结束、物理释放不能互相代替。

## 第六项：本机多 writer 事件存储

### 用途、现状和归属

多个进程向同一工作区保存事实，后续读取应看到实际提交的状态；发生部分写入、同步或释放失败时，必须知道结果尚未确认。这项承接当前 NDJSON 后端，既不改成 SQLite，也不再抽一次已经进库的 segments reader/writer。

真实构造入口是 [WorkspaceEventStore.fs](../src/Wanxiangshu/OpenCode/Host/WorkspaceEventStore.fs)、Omp.Adapter 和 Sphinx 的 Composition/Bind。它们组织各领域 IntegrationRule，调用 CanonicalIntegrator.createWithRules 与 EventStore.createLocal。源码主干为 [Store.fs](../src/Wanxiangshu/Persistence/EventStore/Store.fs)、[IntegratorEngine.fs](../src/Wanxiangshu/Persistence/EventStore/IntegratorEngine.fs)、[IntegrationKernel.fs](../src/Wanxiangshu/Persistence/EventStore/IntegrationKernel.fs) 和 [ProcessEventLog.fs](../src/Wanxiangshu/Persistence/EventStore/ProcessEventLog.fs)。Sphinx 的既有构造入口也要适配，但不扩大主程序启用范围。

拟增完整入口 `wanxiangli/local-eventstore`。LocalEventStore 持有 staged payload、freshness 和追加过程；内部 Integrator 持有唯一的 Current、event/payload index、规则槽与候选。通过 `events/segments/convergence/quarantine/file-lock` 等现有公开入口合作；规则选择和领域解释留各自 owner。现有 `wanxiangli/eventstore` 继续是 SqliteJournal，不偷换其名称或协议。

公开构造输入：directory、lockTarget、writerId、segmentCap、isKnownEventType，以及一组 `{name, initial, accepts, faultScope, integrate, planCut, applyCut}` 规则。event 使用现有 events 的原生 EventInput/EventOutput；rule 每次只接自己的 opaque current 和一个 event，不能拿其他槽、整个 store、宿主 Context 或历史读取器。库保存并提交 rule 返回的对象，不序列化/深拷贝它，也不解释 ProjectionSet。

公开操作为 `append(events)`、`writePayload(bytes)`、`readPayload(ref)`、`current(slot)`、`event(id)`、`heads/head/allHeads` 与 `reload()`。这是现行 IEventStore 的完整使用面，不先发布只转发旧 Store 的空入口。构造仍在实际创建 store 时同步加载，失败保持原构造错误路径；Workspace 外层的懒构造时点不能丢。

AppendOutcome 保留成功 receipt，以及 StorageInvalid、AppendFailed、AppendNotAttempted、CommitUnknown、NoNewWriteReleaseFailed 和原 semantic-cut 信息。requested/prepared/cuts、phase、原 cause 引用与 cleanup failures 都带回，不压成一个 message。cut 在 receipt、拒绝或未知中的原位置不变，主程序转回既有 DU 时不重建原异常。

主体保留 EventEnvelope/Map/DU 的形状转换、Fact/Journal codec、各领域规则和词汇表。`.Herdchestra/wanxiangshu/events` 等产品路径、state-root 选择、workspace pool、hostProgram 注册仍由外层传入。`ProjectionCutTail`、`integrator/cut-tail/<rule>` 及其字段继续按原字节读写。

### 必须保持的行为

- PrepareLive 只准备候选；物理 append/fsync 完成后才 Commit。Commit 保留 expectedState 引用，reload/另一次提交改变引用后再 Commit 会失败；若已有字节落地，仍是 CommitUnknown，不回退成未写入后重试。
- 外部 writer 改变 inventory 后，在同一跨进程锁内刷新。freshness pending 跨懒 RuntimeStarted 与第一条业务追加保留，不能丢掉第二次重判。
- 同 ID 同规范字节幂等，不同字节冲突；父依赖、批内环、payload closure 与 retained-window replay 的区别不变。
- staged payload 优先，引用仍按原摘要选择；每一行嵌入它引用的 payload，使之自包含。不新增磁盘格式、旁路数据文件或审计策略。ReadPayload 的已有 staged/committed 顺序保持。
- 成功返回包含锁 release 完成。release 失败按此前是否新写入分别给未知或 NoNewWriteReleaseFailed；primary cause 不被清理错误覆盖，cleanup 顺序不变。
- full-replay fallback 仍是全进程一次额度，不能变成每 store 一次或无限自动恢复。retention、旧式/新式共存、64 MiB 默认分段上限和显式测试 cap 都保持。
- Journal、Casebook、Sphinx、JS 等 rule 的 accept/integrate/cut 行为原样参与，不把这些领域逻辑移进通用存储，也不删除现有审计事件。

## 第七项：Journal 的寿命、修订通知和关闭排空

### 用途、现状和归属

多个调用共享一个 Journal，只有已提交的业务事实能推进本地修订并唤醒等待者。退出时先停止接收，再等已接受的追加结束；恢复动作共享同一轮执行。这些状态应由完整 Journal 会话承担，不能只迁一个 waiter 数组。

先读 [EventStoreJournalWriter.fs](../src/Wanxiangshu/Persistence/Journal/EventStoreJournalWriter.fs)、[AgentJournal.fs](../src/Wanxiangshu/Persistence/Journal/AgentJournal.fs) 和 [SharedAgentJournal.fs](../src/Wanxiangshu/Persistence/Journal/SharedAgentJournal.fs)。真实消费者有 WorkspaceSharedJournal、PluginHost、Omp、AgentJournalPortAdapter；PluginRecoveryWiring 登记恢复，HostSignalBootstrap/Fork.RunLifecycle 等待恢复。这里的恢复回调是现有运行路径，与前面未接入的子工作跨进程恢复不是同一入口。

拟增 `wanxiangli/journal-session`，包含 JournalSession 的 writer 状态和通知/恢复状态，两部分内部各守自己的字段。迁走懒初始化、currentSeq、firstFailure、serial、closeTask/closed，以及 revision、lastChange、waiters、recovery generation。共享实例/refcount 继续使用已有 `wanxiangli/work` 的 sharedAsyncJournalPool，不抽第二个池。领域 Current 仍唯一归存储 Integrator。

公开面草图：

```text
JournalSession({ initialization, newEventId, now,
                 makeEnvelope, commitEnvelope,
                 readCurrent, refreshCurrent, onSettlement })
  append(request) -> Promise<JournalOutcome>
  snapshot / snapshotWithRevision / revision
  awaitChange(fromRevision, cancellation)
  enqueueRecovery / runOrAwaitRecovery
  release / releaseAsync / isPoisoned
```

request 是原 stream/providerRun/fact 的不透明对象；makeEnvelope 只按库分配的 ID、sequence、时间构造旧 Envelope。commitEnvelope 执行一次现有 store append，父引用/payload closure 在真正轮到该追加时计算，不能在 API 被调用时提前计算。readCurrent 只返回 Journal 槽位的原对象，库不 fold ProjectionSet。

提交结果至少区分 accepted、durable semantic rejection、known pre-write refusal、not-attempted physical failure、unknown、no-new-write release failure，附原 failure。序号、poison、revision 的决定在库内，不用 shouldPoison/shouldWake 回调把整个流程再交给主体。onSettlement 仅承接现行 FatalProcess 等产品处置及错误文案，不允许它改队列和修订。

主体保留 FactCodec、EventStoreJournalCodec、JournalPayloadClosure、父依赖规则、`blobs/<sha256>`/UTF-8 适配、Ablation 策略与领域 fold。取消令牌只适配已有 cancellation，取消某个 waiter 不创建第二个取消 owner。

### 必须保持的行为

- 创建 Journal 不触发 store；RuntimeStarted 在第一条业务事实之前懒写，初始化序号 1，业务从 2 开始。不要把构造新类变成启动时读写磁盘。
- event ID 在 append 调用时就分配，即使 closing/closed/poisoned；observedAt 和业务 envelope 在轮到执行且初始化成功之后才构造。
- 业务 accepted 或成功 receipt 中的 durable cut 都消耗序号；只有 accepted 才发布修订和唤醒。revision 继续取已提交 envelope 的 LocalSeq，不改成另一个独立递增计数。
- 初始化 unknown 与本次业务未尝试分别返回。初始化成功 receipt 内自身带 cut 的分支先走原 FatalProcess，不能合并成“任何初始化非成功都 poison”；按现行分支映射，不修复策略。
- 普通业务 AppendFailed 是已知未写入拒绝，writer 不 poison；其余物理 failure 记住第一次原失败，后续拒绝引用它。不新加 append 去重。
- RefreshCurrent 不推进本地 revision、不唤醒 waiter；已有更晚 change 的检查、注册和取消顺序不变，取消不消费下一次提交。
- release 立即关准入，但排空已接受前缀；重复 releaseAsync 返回同一个 close task。意外 Promise 拒绝保持 serial 链拒绝，后续已接受操作不执行；close 的 finally 仍置 closed，close task 仍拒绝，不能吞错续跑。
- recovery 首调用启动并共享；新一代登记等待前代 settled。前代 rejected 时按现状传播，不变成自动重新恢复。序号/revision 保留 bigint 及现行 int64 语义。

## 有条件储备：子工作的恢复、完成保存和唤醒

**暂缓施工。** 下述算法与夹具存在，但 `restoreLinkedChildren` 在当前源码中没有调用者；`resolveAndCommit` 仅由 Restart 内部消费。[Fork Runtime](../src/Wanxiangshu/Execution/Delegation/Fork/Host/Runtime.fs) 明确普通生命周期不接跨进程恢复。需先确认真实的显式 resume 入口或由用户另行决定是否启用；本计划不做该产品决定。完整细纲保留，避免以后重新从零调查，不能计作已可接回的第八项。

### 用途、现状和归属

插件重新加载后，父工作需要知道已有子工作还在运行、已经可取回、尚不能判断，还是恢复被阻塞。恢复过程中保存完成记录，成功后只发唤醒；Join 继续从 Journal 读取事实，不能把进程内通知当成结果本身。

先读 [ChildRecoveryWorkflow.fs](../src/Wanxiangshu/Execution/Delegation/ChildRecoveryWorkflow.fs)、[Fork/Host/Restart.fs](../src/Wanxiangshu/Execution/Delegation/Fork/Host/Restart.fs) 和 [Fork/ChildRecovery.fs](../src/Wanxiangshu/Execution/Delegation/Fork/ChildRecovery.fs)。保留算法的内部链为 `HostForkRestart.restoreLinkedChildren → restore/recoverChild → resolveAndCommit`。完成记录和恢复判定已经有 `CompletionRecord`、`HandleLifecycleLaw`；若以后明确启用，迁它们外侧的整个恢复过程，不重新抽 decode 或 resolve 小函数。

建议扩 `handle-lifecycle`，增加 `ChildRecovery`：`recover(input, effects)` 恢复一个子工作；`restore(record, effects)` 处理已有完成记录的路径；`restoreFamily(records, effects)` 顺序遍历并归并结果。它只持有本次调用的在途结果和汇总，Journal 仍持有领域事实，ForkRuntime 仍持有物理 children。

`input` 是 handle、child、agent 等身份及中立观察。effects 按现有操作给出 `currentHandle/readBlob/readSnapshot/acceptedFor/findWork/deliveryFor/saveCompletion/saveAbandon/rejectLegacy/bind/pulse/interrupt` 等窄能力；不传整个 Host Context 或 Journal。`findWork` 返回既有 canonical admission 的不透明引用，保存能力只执行现有写入，不把恢复判定留在回调里。只给各路径实际需要的能力，不要求所有调用构造一套无用空方法。

宿主适配把 SDK 消息解释为 missing/unreadable/active/terminal，其中 terminal 携带原文、精确 physicalParentId 与 providerRun。末条 assistant、后续 user、`finish=stop`、text parts 拼接和 SDK 错误解释仍归适配；库负责精确 Accepted/root/admitted Work/delivery 关联，以及保存和唤醒的先后。

### 必须保持的行为

- 先读 durable，再读 snapshot；即使 durable 已有终态，也不悄悄跳过现行 snapshot 调用。没有可读结果时保持原有 Unknown/Incomplete/Blocked 区别。
- 精确 Accepted 的 physical message 才能确定 Authority Root。重试的新 physical id 不能当 root；缺少 Accepted、admission 或交付关联时不猜、不重发。
- active 恢复路径要求 record.Work 存在且完成记录 belongsToWork；Restart 的已有完成分支使用 `Option.forall`，无 Work 的历史记录仍可通过。不能为了统一接口把两条既有兼容规则收紧成一种。
- `commitJoinable` 目前只接受 CompletedV2；已非 Active、非 legacy 的同一 scoped work 可幂等返回。迁移不扩成接受 failed/aborted 记录，也不生成新的完成格式。
- 完成保存成功才 pulse。保存 Error/拒绝均不 pulse；保存后 pulse 抛错，不再次保存。只有 abandon 路径在原时点取 Clock 写入，且不 pulse。
- 无正文的 completion 回到 recover；ref/digest 不全阻塞。legacyFalseAbort 写拒绝事实后保持 waiting 并 interrupt；invalid body 只 waiting。Retired/Abandoned 不重建 child。
- 家族恢复先收 pending 的 joinable/abandoned，再收 linked 并去重，过滤 HostOwnedHidden，保持绑定、目录、Restore 的时点。汇总优先级仍为 blocked → waiting → recovered → none。保留顺序执行，不改为并发 Promise.all。
