# 主程序剩余职责与最终骨架预估

2026-11-01。源码基线：主体 `a6154341144909d191b4c8f546c925362a0293ca`，万象理 `2dd1ff8c5dd7efa8948b7fb5c31c99fd057cdfed` / 0.84.0。本文保留当时只读盘点的总体预测，不是逐项施工计划，也不是迁移闸门通过或程序改动的授权。后续施工按另行授权推进，实际结果见详细施工记录，不把原规模当作当前剩余量。

## 总体判断

主程序还没有接近只剩骨架。前面的拆分已经迁出不少基础对象，但大量完整运行流程仍在主体：参与者已有各自的库，安排它们合作、持有在途状态、处理结束和恢复的组合者还没有迁完。后续重心应从小型边缘计算转向这些完整能力，不能再按文件名切一批 helper。

按调查基线的调用关系，下表可分成 **22–29 个完整职责迁移单元，粗估二十多项**。这包含当时已经选好的 CompletionRecord、CasebookEdit、CasebookState 三项，不另加一次。一个单元可能需要若干小步实现，不等于一个 PR，更不等于一个新公开模块；边界继续核实后，宜按约 20–30 项理解这个原始量级。

[前三项](下一批完整职责拆分计划-2026-11-01.md)与[后三项](后续完整职责拆分施工计划-2026-11-01.md)已经接回主体，结果及未通过项见施工记录。之后沿主体 `9225b440a`、库 `920d276` / 0.90.0 写成[第三批七项详细计划与一项条件储备](第三批完整职责拆分施工计划-2026-11-01.md)，仍计在上述粗估内。PTY 开启/交互和子工作跨进程恢复均未确认生产入口，不为实现粗估数量而启用。下文规模数字仍是原调查基线，不是此刻重新统计后的剩余量。

预计其中真正需要新增公开模块/入口的约 **5–9 个**，其余主要补齐已有 runtime、casebook、trace、handle-lifecycle、dispatch、routing 等边界。调查基线是一个 npm 包、57 个公开子路径；新入口以库 manifest 为准。不能把下一步解释为再造二十多个 npm 包，也不把最终入口数设成目标。后续若合并旧入口，净增数还会下降。

最终纯产品组装骨架可暂按 **3,000–6,000 行实现源码**规划；万象通暂不拆仓，所以包含宿主适配的主仓运行源码仍可能约 **3–5 万行**。这是职责归位后的量级预测，不是逐行裁剪承诺，更不是下一批三项做完后的大小。

## 宿主适配另走一条线

万象通按 **OpenCode、omp 两套宿主适配**组织；各自内部按会话、消息/请求投影、工具、启动/关闭等职责分文件即可，不因此再创造十几个 npm 模块。具体宿主下的内容仍要逐项判断：

- 宿主消息字段、SDK/HTTP 结果、config hook、工具 schema、provider 请求写回、订阅和物理会话操作，归万象通。
- 调度哪个工作、何时宣告业务完成、持久发送协议、运行租约和工作归属，随上表领域对象进入万象理。
- 宿主协议的在途状态可以由适配器持有；它不是再复制一份 Work/Case/委派账本。

第四批已把请求投影、请求延迟看护与 Trace 宿主捕获适配放入 `wanxiangtong/`，外层源码发现、构建输入跟踪、产物清理和打包已接入现有构建。其余适配仍需沿真实调用归位；这项支撑能力直接复用，不再为下一批重建框架。具体候选见[第五批详细计划](第五批完整职责与宿主适配计划-2026-11-02.md)。

## 推进顺序与每段的目标

1. **已接回的六项转入施工记录。** 完成记录、案例编辑/集合、命令运行、Bookkeeper 事务及保存取用维护的实现和接线见前两篇；已知未通过项如实保留，不重新列为待拆模块。
2. **先执行已有真实入口的完整过程。** [第三批计划](第三批完整职责拆分施工计划-2026-11-01.md)的附着会话、命名程序结算和单次派发已接回，接着处理执行容量与 Trace。PTY 和子工作恢复暂缓；具体步骤不再在本文复制维护。
3. **处理共享的持久边界。** 本机 NDJSON 存储与 Journal 的详细步骤已写入第三批，可通过现有适配分别施工；涉及未知结果、外部效果、序号与关闭时保持现行协议。失败策略和完整会话恢复仍待后续细化，不借存储迁移顺带改变。
4. **最后收跨领域流程和宿主接线。** 将 Fission、Work/Change、回合续接中的中立协作收好；具体宿主解释进万象通。每个领域收拢时就退出自己的类型桥、codec/事实转换或转发残留，不等最后再做全仓机械清理。

先后由实际依赖决定，不以表格顺序强制串行。后段单项可能涉及几千行与多个协作者；不再用先前百行边缘模块的速度估计剩余工期。当前能给职责数量和规模范围，还不足以给可信的总工时。

## 最后留下什么，预计多大

下面都是未来规划区间，沿用实现源码物理行的大致口径；不计签名、测试、构建脚本、提示词、静态资源或生成产物。

| 所说的“骨架” | 预计量级 | 应留下什么 |
| --- | ---: | --- |
| **纯产品启动和组装** | **3,000–6,000 行** | 选择宿主、加载产品配置/资源、创建对象、连接能力、注册入口、安排启动与关闭；不拥有领域状态或继续/完成等业务规则 |
| **万象通运行实现** | **约 25,000–40,000 行** | OpenCode/omp 真实的消息、会话、工具与生命周期翻译；包括从其它目录归来的适配，不只是现有 OpenCode 文件 |
| **主仓运行源码合计，不含 Sphinx** | **约 30,000–50,000 行** | 上述两层与暂缓能力等残留；区间相关，不能将每行上下界当作独立预算相加 |
| **Sphinx 若仍留在本仓** | **另约 9,000 行现有规模** | 独立服务/Inquiry 子系统，不把它当成几百行接线，也不未经决定删除 |

万象通暂不拆仓，因此“根部只剩几千行”和“主仓仍有数万行”可以同时成立。多数代码只是转移职责归属，并不会凭拆库消失；净减少主要来自退出重复状态、重复类型转换和多余转发，不能预先靠删除现有功能凑体积。

这些区间依赖三个条件：领域组合真正迁走；宿主和核共享清楚的公开数据边界，旧 F# 桥接不会无限保留；产品描述与适配实现归位。若仅搬算法、主体继续持有所有协调状态，最终仍会残留数万行“胶水”，达不到上述骨架目标。

## 单列的工作，不拿来凑模块或瘦身

- **审计保持现状。** 现有事件写入、等待、失败和历史读取保持；将来迁 JS 调用组合时按现有行为搬，不把退出审计算收益。
- **WarmStart/Semble、问卷、日志整理继续暂缓。** 既不启用也不删除；它们未决时不能宣称所有旧 owner 已退出。最终清空主体前仍须有各自明确去向。
- **Sphinx 先单列。** 有独立服务入口和事件注册，但本轮未确认主程序实际启用链。若以后纳入，可再按 1–2 个完整能力规划，不拆 Graph/Budget 小包；不计入上述主线 22–29 项。
- **支撑面不等于骨架。** 当前 scripts 有 87 个文件、约 2.2 万文本行；resources 有 537 个文件、约 1.5 万文本行；requirements 还含大量测试与文档。这些须随实际依赖清理或归位，不能因为业务进库就整删，也不应作为新的业务模块。
- **交付仍是一件完整的事。** 每项都需接回主程序并退出旧实现，测试与主体加载同一候选。并列目录消费与版本取得方案另作支撑事项；不顺手改成浮动邻仓依赖。
