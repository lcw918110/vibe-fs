## 第四项：一次命令执行的完整协调

### 用途、边界与公开面

准备和发布工作树时，主程序需要运行 Git，取得完整输出，并按原有预算处理等待和取消。实际链为 [Change Host](../src/Wanxiangshu/Change/Host/Host.fs) → [GitAdapter](../src/Wanxiangshu/Change/Host/GitAdapter.fs) 的 `OrchestratorGit.run` → `ProcessRunner.run`。模型程序的命令执行已经走 `Runtime.startCommand`，本项不把两种不同寿命的入口强行合并。

来源是 [ProcessRunner.fs](../src/Wanxiangshu/Process/ProcessRunner.fs)、[NodeProcessHost.fs](../src/Wanxiangshu/Process/NodeProcessHost.fs)、[NodeProcessWait.fs](../src/Wanxiangshu/Process/NodeProcessWait.fs)、[ProcessOutput.fs](../src/Wanxiangshu/Process/ProcessOutput.fs)。四文件约 943 行，包含注释和 launcher 测试接缝；这只是调查尺度，不是迁移行数目标。

在现有 `runtime/process/` 内增加一次运行的完整协调实现，例如 `ProcessRun.fs`，由已有 runtime 工程编译并从 `wanxiangli/runtime` 导出 `runProcess`。不新增 process-wait、command-env、output-collector 入口。

| 谁负责 | 状态和行为 |
| --- | --- |
| 已有 ProcessSession | 原生进程、stdin、stdout/stderr 排空、真实 exit/close |
| 已有 OutputSpool | 输出内存、转文件、文件失败及删除 |
| 已有全局 LargeGate、Time | Large 排队许可；截止计算和物理定时 |
| 新运行协调者 | 本次门票是否已取得、输入处理、首个管道失败、等待阶段、输出结果移交；每次调用独立 |
| GitAdapter | Git 命令、原 30 秒估计与 65536 字节输出阈值、错误呈现、读取并删除成功 spool |

建议公开调用为 `runProcess(request, signal?) -> Promise<ProcessRunResult>`。request 分三组：command 的 fileName/args/cwd/env/stdin；estimate 的 runtimeSeconds/outputBytes/memory；context 的 hardLimitMs、默认工作目录、baseDirectory、环境快照和 spoolDirectory。都是明确的进程输入，不是主体 Context。主体把 F# CancellationToken 转成取消信号，并在调用结束后释放自己注册的回调。

结果保持 Completed、Spooled 和 TimeoutExceeded、SpawnFailed、ProcessCancelled、ExecutionFailed 的既有含义；库用原生 JS 带标签结果，主体只转 F# 形状。取消前段现有的 Promise 拒绝继续保留，不能因为新签名便把所有拒绝包装成 Result。共享 Command 上的 PtyOptions 不进入本接口，因为这条路径不消费它。

### 必须保持的行为

1. 期限实际为 `min(estimate, hardLimit)`，默认 hardLimit 一小时。旧注释的 ×3 不成立；只修说明。期限从 spawn 成功、进入等待阶段开始，排队和 spawn 不计入。
2. runtime 估计必须有限且大于零，output 估计不得为负；不顺便收紧 hardLimit、相对 PATH 等其它输入。cwd 优先级、环境覆盖和 PATH 查找沿原 NodeProcessHost 逻辑，OS 准备放在 runtime 内。
3. outputBytes 在这里是转文件阈值，内存上限为 `min(请求值, 204800)`，不是截断或杀进程预算。内存结果分 stdout/stderr；文件按收到的字节顺序合并，GitAdapter 仍将其全文当 stdout、stderr 置空。
4. stdin 按 UTF-8 编码，分 16 MiB 块顺序写；只有 Written 后才继续，未知消费不重发，最后结束输入。输入/管道/输出回调失败保留首个错误并请求 SIGKILL；close 后仍等输入处理，零退出码不能覆盖该错误。
5. ProcessSession.wait 到期本身不杀进程。协调层到期发 SIGKILL，再最多等 1000ms close；未确认时仍报超时。正常非零退出是结果数据，signal exit 仍映射 -1。
6. 等待中取消发 kill 后返回 ProcessCancelled，不承诺已经 close。直接子进程已 exit、后代仍持管道时，ProcessSession 为 Draining，不再向旧 PGID 发信号；不能宣称已经清完整个进程树。
7. 超时、取消、等待失败清理本次 spool；成功 spool 交消费者读后删除，迟到输出不改已结算结果。仅实际拿到 LargeGate 的调用负责释放，继续共用原全局 gate。
8. 保留各阶段取消差异：Large 在取得门票前/排队中可能直接拒绝；Medium 原生 host 在 spawn 前已取消返回 `Cancelled before spawn` 并映射 SpawnFailed；已启动等待中才映射 ProcessCancelled。受控 host 在取消时抛错的原映射也保留。
9. 原 runSpawned 在 wait 正常返回后还会 killQuietly，包含 TimedOut；不要把 wait 局部测试的“一次 kill”误写为整个流程的总次数承诺。超长 deadline 当前只算一次等待分片，本项不顺手改成新长时调度策略。

## 第五项：Bookkeeper 一次会话事务

### 用途、状态和接口

保存或维护案例时，系统用一次 Bookkeeper 会话改好一对 Q/A，再把结果交还。迁移的是完整的“建事务→创建会话→绑定与订阅→发送→等完成→取回→退场”，不是一个 Promise 等待器。

主要来源是 [BookkeeperRuntime.fs](../src/Wanxiangshu/Repository/Knowledge/Casebook/BookkeeperRuntime.fs) 的 Coordination。生产消费是 Lifecycle.spawnFinalize 和 Bookkeeper.applyRefresh；[PluginHostWiring](../src/Wanxiangshu/OpenCode/Plugin/PluginHostWiring.fs) 提供真实会话端口与终端通知。JsBookkeeperTool 使用同一个 ledger 找 txId，再通过同一个 staging 编辑；不能另起一套“库内专用”暂存实例。

在现有 casebook 内增加 `BookkeeperTransaction(staging, ledger)`。它只拥有本次调用的 child、等待、订阅与收尾进度；staging 继续独占 Q/A/touched，ledger 继续独占会话附着、一次提示授权与 pending completion。新组合者不复制会话字典。

建议公开消息：

```text
run({txId, ownerId, question, answer}, effects)
  -> Promise<Result<{question, answer}, string>>
```

effects 只含 `open()`、`subscribe(childId, complete)`、同步 `prepare(childId)`、`send(childId, agent, text)`、`abort(childId)`。subscribe 返回释放函数；prepare 返回原 agent/text 或原错误。它在原时点重查 active owner、核对先前签发的 seed 并构造 prompt。标题、角色名、PromptAuthority、SessionId、语言和提示词字节全部留外层，库不解释这些值。

首次 owner 查询、seed 签发及 txId 生成仍在主体的原位置；setPort/resetRuntime 和宿主能力选择仍为装配。公共 isAttached/tryTxId/tryConsumePromptAuthorization/completePhysical 仍连接同一个 ledger。第 2 项 CasebookEdit 是这项的实际前置；案例集合不是它的技术前置。

casebook 局部规则目前笼统写无 IO/不读存储/不写事件。施工时就近修为真实分工：基础状态对象不直接 IO；完整组合者经声明回调安排外部动作，具体宿主与持久协议留外层。同期去掉该受改章节的旧证明栏，不重写无关文档，不新增总册。这里只安排修改，当前规则和程序尚未因此改变。

### 必须保持的次序与后果

1. 首次 owner/seed 不合法，不 begin，也不创建会话。成功后顺序为 begin → open sibling → bind → registerCompletion → SubscribeTerminal → 再查 owner/seed → 构造 prompt → authorize → SendPrompt。
2. 创建返回 Error 时只 abort staging；二次身份校验或发送返回 Error 时，dispose/removeCompletion → abort staging → 等 AbortSession → unbind。终端 Error 也走现有失败收尾。
3. 终端 Ok 先检查 touched，再 take；未写时返回原错误 `bookkeeper program did not write the staged case`。第 2 项中零 setter 的成功程序仍会 touched，所以两种情况不能混淆。
4. AbortSession 返回 Error 或拒绝都被吞掉，之后仍 unbind；不能改成先解绑后 Abort。成功路径也等现有 retire 后才返回 Q/A。
5. 终端可能在 SendPrompt 返回前到达；发送随后返回 Error 时仍以发送失败分支收尾。同步订阅回调不能因重排注册顺序而丢失。
6. direct terminal subscription 和 completePhysical 共用原完成等待；重复通知不得触发重复 take/retire。reset、解绑和重绑的取消继续由原 ledger 处理。
7. **Result Error 与抛错/Promise 拒绝有区别。** CreateSiblingSession、SendPrompt 拒绝，以及 Subscribe/Dispose 同步异常，当前没有通用 finally 清理，可能留下暂存/附着。本项保留这种可观察差异，不顺手补清理；若要修复，另列明确差分。
8. 不新增超时、重试、互斥、事务代际或新的取消方式。不会把待完成的 Bookkeeper 因等待过久自动判失败。

### 施工步骤

1. 在现有 runTransaction 入口整理正常完成、创建/发送 Error、未写、重复终端和 Abort 拒绝用例。缺失的竞态用受控端口补上：订阅时同步完成、先完成后发送 Error、二次 owner 已变、发送直接拒绝；期望来自当前次序，不改成功定义。
2. 在 casebook 工程内实现完整事务组合并导出 `.d.ts`，直接组合原 staging 和 ledger。完成消息使用原生数据，F# 形状适配只在主体边缘。
3. 主体保留身份准备、prompt 构造和具体宿主端口，把 prepare 作为原时点执行的闭包；不能提前构造 prompt 或缓存二次身份结果。
4. 将 finalize 和 refresh 两处 runTransaction 接到同一个库实现，保持真实装配与测试装配使用同一组 staging/ledger。旧 setPort/resetRuntime 可只做装配，不另养事务状态。
5. 删除主体 Coordination 中 begin/bind/register、等待、touched/take、abort、dispose/unbind 的算法；原产品文案与宿主翻译保留，不能留下两个成功/失败收尾版本。
6. 在主体组合用例中让真实 JsBookkeeperTool/ProgramSession 修改 staging，再由新组合者取回。不能只让假端口直接返回一对改好的 Q/A。
7. 跑下面相关检查与共同交付步骤。到这里只完成会话事务，案例追加、索引和 fetch 还在下一项，不宣称整个 Casebook 已迁完。

## 第六项：案例保存、取用和维护

### 完整能力与前置

用户取用一个案例时，系统在相关文件变化后维护答案，再按现有方式交还；工作结束时，将最终 Q/A 与文件基线存为案例。本项把这两条完整流程收进现有 casebook，内部各自保持短流程，不制造 finalize-helper、freshness-helper 或 access-touch 模块。

来源为 [Lifecycle.fs](../src/Wanxiangshu/Repository/Knowledge/Casebook/Lifecycle.fs) 的草稿结算/归档、[Bookkeeper.fs](../src/Wanxiangshu/Repository/Knowledge/Casebook/Bookkeeper.fs) 的维护、[Workflow.fs](../src/Wanxiangshu/Repository/Knowledge/Casebook/Workflow.fs) 的追加前决定，以及 [FetchTool.fs](../src/Wanxiangshu/OpenCode/Tools/FetchTool.fs) 的取用决策。以第 2、3、5 项接回后的实际剩余代码为准，不按今天的文件行数定任务。

两条真实链必须都接回：

- PluginHostWiring → tryFinalizeDraft → Bookkeeper 事务 → freeze baseline → append Capture → 更新索引。
- FetchTool → shelfmark resolve → compare baseline → 按需 Bookkeeper/append Refresh → 重取答案 → append Access。

建议同工程增加 `CasebookService`，公开 `finalizeDraft(sessionId)`、`refresh(identity)`、`touch(identity)`、`fetch(shelfmark, notifyAppendFailure)`、`cleanup(sessionId)`。finalize 返回原结算分类；refresh/touch 返回原成功或失败；fetch 返回 unavailable、missing、fresh(answer)、refreshed(answer)、stale(answer)。工具层再按原语言渲染，不在核内生成工具 TOML。

### 谁拥有状态，外层还剩什么

| 状态/动作 | 本项安排 |
| --- | --- |
| Current 与案例变化 | 复用第 3 项 CasebookState；持久 Current 仍由原 Integrator 持有 |
| 草稿、观察、索引、Bookkeeper 事务 | 复用现有 SessionDraftStore、collector、casebookIndex 和第 5 项，不另建 Map |
| 服务在途状态 | 本次草稿快照、捕获目标基线和结果；不复制 conflicts、flight 或长期 Cases |
| 存储动作 | 窄回调取得 Current、追加 Capture/Refresh/Access；Store.fs 编解码、UUID/parents、payload refs、Append/cut 解释仍在原适配 |
| 基线动作 | 组合现有 file-baseline 的捕获/比较；目标与 diff 出自同一次捕获 |
| 宿主与产品面 | workspace marker、原启用时点、schema/工具名、SessionId、语言/呈现、宿主事件转草稿、原失败通知留外层 |

Service 接收这些实际协作者及窄动作，不传整个 IEventStore/Host/Authority。服务装配绑定 workspace 和存储动作；现有草稿、collector、索引等单例仍共用，不因创建 Service 而偷偷改成每实例一份。追加适配返回原成功或带原失败对象的结果；原 failure、EventId、Prepared、cause 等不得 JSON 克隆、重建异常或丢失对象身份。库透传既有追加后果，主体装回原 F# settlement；不能在这一刀重新设计持久错误体系。

Replay/needsRefresh 的暂缓状况不变。仅 Surface 消费的 finalizeEngineerCase/refreshWithDiff 可以复用迁出的同一归档/追加动作，但不新增生产用途。审计与全局恢复不进入本项。这里接走案例服务，不声称 Store codec、整个 Casebook 或宿主接线已清空。

### 保存流程必须保持什么

1. 原时点检查启用；禁用时清草稿、drain 观察、返回 NothingToFinalize，不启动 Bookkeeper。cleanup 本身从不发布案例。
2. tryTake 先消费草稿；无草稿或无最终 answer 时 drain 并结束。后续失败不自动放回草稿。
3. 有草稿时，先 drain，取 lastQuestion/transcript，再查是否已有案例；存在则 PhaseConflict，缺失才运行一次 Bookkeeper。不能改成先预检全部条件再消费草稿。
4. Bookkeeper 成功后才从 FileRead 观察取路径、distinct/sort、捕获完成基线；两种基线初值相同，sourceTrace/identity 仍是原 sessionId。
5. 追加前仍有第二次存在检查，不能因前面查过而删掉；也不能把它改成锁或跨进程 exactly-once 承诺。
6. Capture 成功后 invalidate，再 refresh 256。追加失败保留原 failure；追加成功但索引刷新失败仍 Unknown，不称为未提交。
7. dispatch 的原 catch 仍返回 Unknown 并再次 drain；不补写、不重试、不恢复草稿，也不据此回滚已发生的效果。

### 取用和维护必须保持什么

1. shelfmark 仍按当前 256 可见集合解析。unavailable、missing 和旧答案区分不变；容量裁剪不追加 eviction，也不修旧 TODO。
2. RelatedPaths 非空则原样使用；为空才从 FileRead 观察推出 sorted/distinct 路径。
3. 一次 compare 只捕获一次目标状态；targetState/diff 同时服务 Bookkeeper 和 Refresh，不能等 Bookkeeper 结束后重读文件换基线。
4. 无变化时不调用 Bookkeeper，只记 access；有变化时一次 Bookkeeper、一次 Refresh，再更新索引、重取答案、记 access。
5. 维护普通 Error 时，按原方式通知追加失败，再返回 cached answer 的 stale 结果。提交未知时即使 Current 可能已有变化，也不重读新版并报告成功。
6. 维护成功后重取缺失/错误仍返回 stale cached answer，不补建案例。Access 普通 Error 通知后仍返回既有 fresh/refreshed 答案。
7. 错误捕获位置不统一：touch 的 Promise 异常转 PreparationRejected；Refresh 的 Promise 异常当前直接拒绝。保留原通知异常的传播及原失败对象，不加总 catch。
8. fetch 起点和真正 touch 时各自的启用检查仍执行；不能起点缓存一次开关用到底。

**合并在途请求仍留一个 owner。** FetchFlightRegistry 已经在库里；它目前共享的是“已按首个调用者语言呈现的字符串 Promise”，而非可供每个调用者再次通知/呈现的领域结果。同 workspace+shelfmark 且同实际 store 引用共享首次调用的语言和失败通知 owner；不同 store 引用立即拒绝。

工具层保留以下小装配，传入真实 store 引用作为原身份 token，不能每次包一个新对象：

```text
registry.getOrCreate(root, shelfmark, actualStore,
  () => service.fetch(shelfmark, notifyFirstCallerAppendFailure)
               .then(renderUsingFirstCallerLanguage))
```

首个调用者的通知与呈现都在 factory 内；不建立第二个 flight，也不在共享 Promise 之外重做通知。notifyFirstCallerAppendFailure 只表达原通知能力，不再传整个调用 Context。

## 执行时怎样使用本计划

开工时先读取该项源文件和真实调用，确认自调查基线以来没有改变所列行为；只补实际变化，不重跑与它无关的历史套件。源码签名可随实现定稿，所有权、真实消费者、兼容行为与退出范围不可凭方便跳过。

每项的最小闭环仍是：库承担完整职责 → 主体真实调用 → 原状态和算法退出 → 差分检查通过。上面各节所列“新增测试”只为尚无覆盖的具体风险；若同一行为已有可复用用例，就迁用或改接它，不再复制一套。公开包消费者与分发检查按共同步骤执行，不拿另一个版本的结果代替当前主体。

如果实施时发现必须改变产品行为，先记录具体差异并移出这次迁移；能保持现状则照常继续。不得把这一条解释为整项停下来研究审计、扩权、重试或新的启用条件。
