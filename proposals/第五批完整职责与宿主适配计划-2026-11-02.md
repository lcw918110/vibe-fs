## 1. PrefixHistory：当前上下文世代、前一 Scope 归档和提问回执归一个 owner

### 为什么值得做，边界是什么

用户开启新 Scope 后，系统须知道当前世代、哪些重锚已处理、上一 Scope 的归档在哪里，以及同一提问是否已登记。现在 `wanxiangli/prefix` 的 `Prefix` 负责世代规则，却由主体 `ActivePrefixEpoch` 保存三份 Set、归档和提问 Map，再每次搬成 JS state 给库。这里不是新增一项小工具，而是让已有 prefix 从无状态规则补齐成完整状态 owner。

不把 `scopeQuestionReceipt` 单独切包；不迁 request renderer、宿主 snapshot 解码、Blob I/O，也不让 Prefix 认识 OMP、OpenCode、PairGuidance 或 Journal。

### 源与真实调用

主要源：`src/Wanxiangshu/Context/Prefix/Epoch.fs` / `.fsi`（约 230 行，含 `ActivePrefixEpoch`、`ArchivedScope`、所有推进/提问操作）。库现有：`src/prefix/Prefix.fs`、`index.d.ts`、`tests/`，公开入口继续 `wanxiangli/prefix`。

真实事实入口在 `Composition/Durable/DomainFamilyBridge.fs` 的 `ContextProjectionBridge.fold`：`ContextReanchored`、`TenureReanchored`、`ScopeReanchored`、`ScopeQuestionAsked`；`ProjectionUpdate.fs` 决定吸收重复还是报告失败，并在真正推进后退休辅助提示可见性。这些跨 owner 动作留组合层。

读者必须一起切换，不能只改 Epoch 后保留同名字段镜像：

- `OpenCode/Host/HostCompactionGate.fs`：读取当前世代、提出未处理 compaction 候选。
- `OpenCode/Tools/ScopeReset.fs`：计算下一 Scope 数、是否首次 Scope，记录归档重锚。
- `OpenCode/Tools/ToolRuntimeScope.fs`：读取上一归档，查询/登记 askPreviousScope 回执。
- `Omp/Adapter.fs`：相同 reset/归档/提问路径，不能只适配 OpenCode。
- `OpenCode/Plugin/PluginHooks.fs`、`OpenCode/Tools/ToolRegistry.fs`：读取 Scope 计数。
- `OpenCode/Plugin/PluginTransformComposition.fs`：读取 epoch，判断 tenure 是否已重锚。
- `Context/Prefix/Surface.fs`、`Context/Companion/FoldSurface.fs`：测试观察 DTO。既有测试有直接读 `proj.PrefixEpoch.EpochId/LastScopeArchive`，改成观察查询，不为测试保留可写字段。

### 库 API 草案与所有权

同入口增加 `PrefixHistory`；现有 `Prefix` 纯 API 保持，内部共享现行比较和拒绝规则，不复制一套近似规则。

```ts
new PrefixHistory()
history.epoch(): bigint
history.hasReanchored(evidence): boolean
history.reanchored(kind): readonly string[]
history.scopeCount(): number
history.lastScopeArchive(): Archive | null
history.scopeQuestion(callId): string | null
history.proposeCompaction(observedRuns): Candidate | null
history.advance(candidate): Result<PrefixHistory, PrefixRejection>
history.advanceScope(candidate, archiveRef: string | null, digest: string | null): Result<PrefixHistory, PrefixRejection>
history.recordScopeQuestion(targetEpoch, callId, questionsDigest): Result<PrefixHistory, string>
```

`Archive={sourceEpoch,targetEpoch,resetCallId,reference,digest}`；公开返回值是脱离内部状态的快照。Epoch 始终 bigint，无 Number 中转。库保存世代、已处理身份集合、最后归档和提问回执；主体 `ActivePrefixEpoch` 变 opaque native History，不再含 Set/Map。F# adapter 只负责 PrefixEpochId/BlobRef/结果枚举转换，方法名可调整而职责不变。

`advance` 的重复/旧世代仍返回当前已有的吸收性拒绝，不能改成 `Ok unchanged`，否则 `ContextProjectionBridge` 会再次清理辅助可见性。`advanceScope` 必须在一次成功推进中连同 archive 与清空 questions 一起提交；外侧不能先推进再单独清 Map。

### 不可顺带改变的行为

1. compaction/tenure 普通推进保留 `LastScopeArchive` 与 `ScopeQuestions`；只有 scope 归档推进清空提问回执。不得以“新世代”一概清空它们。
2. archiveRef 与 digest 同时存在才记归档；缺任一项时，**推进仍成功但 LastScopeArchive=None、questions 清空**。不擅自补严格拒绝。
3. `recordScopeQuestion` 先检查 target 等于当前 epoch，且最后归档 target 同样命中；不满足返回 `stale scope epoch or missing prior archive`。之后同 callId 同 digest 幂等，不同 digest 返回 `scope question receipt conflict`。
4. 同一 compaction/tenure/scope 身份跨后续世代仍算已处理；不要因当前 epoch 增加而忘记。
5. propose 只给候选，不改变 History；仍按 observedRuns 既有顺序选未处理项。拒绝次序和 `PrefixEpochProjection.describe` 的吸收范围保持。
6. PairGuidance/companion 退休是组合者的动作，不进 Prefix。没有新的实时不变量检查、没有新 archive reader。

## 2. ChildRunSet——一组本地子运行的登记、完成、取消和等待

### 要搬的实际责任

主体 `src/Wanxiangshu/Execution/Delegation/Fork/Runtime.fs` 的 `ForkRuntimeBackendState` 仍拥有 `agents`、`ptys`、共同锁和 mailbox 引用；每个 `ChildRun` 拥有 completion cell、取消状态、绑定的子会话和运行身份。这个 owner 真实生产在用：`Fork/Host/Runtime.fs:302` 调 `ForkRuntimeBackend.create`，由 `OpenCode/Tools/ToolRuntimeScope.fs` 和 `Change/Host/Host.fs` 创建的 `HostForkRuntime` 使用；Fork 命令、Host Join 和 `Execution/Session/HorizonRoster.fs` 都读它。

完整迁出范围：

- `Fork/Runtime.fs/.fsi` 中这个后端及其启动、完成、等待、列表、取消流程（现 `.fs` 约 377 行）。
- `Fork/ChildRun.fs/.fsi` 的运行状态、单赋值完成、取消语义与执行结算（约 202 行）。
- `Fork/Recovery.fs/.fsi` 的 restore/bind/interrupted（约 40 行）。
- `Fork/ChildRunProjection.fs/.fsi` 的状态快照（约 60 行）。

它不是“把整个 Fork 搬完”。`Fork/Host/Runtime.fs` 的 children、processOwnedAgents、processEstablishedAgents、dormantChildren、pendingRuns、promptAcceptanceScopes、joinInFlight、cancelTask/detachTask 及 PTY 物理租约仍有各自宿主生命周期，明确不搬；Host create/send/abort/事件订阅/恢复解释也不搬。现有 `PendingRunStore`、`JoinAttemptRegistry` 不重复抽取。

### 目标形状与状态归属

在现有 handle-lifecycle 项目增加 `ChildRunSet`。库内部可有私有 ChildRun 和 completion cell，但不为它们新增公共入口。组合当前已使用的 `wanxiangli/program` 的 `Wait.completionMailbox`，不能复制一套等待者队列。公开 API 草案：

```ts
new ChildRunSet({ mailbox, now, mintRunId, raceExit, runDefault?, onTerminal?, cleanup? })
set.fork({ id, agent, roleKey, prompt, run? }) // created | nudged | notFound
set.restore({ id, agent, roleKey })
set.bindChildSession(id, childSessionId)
set.markInterrupted(id, reason)
set.cancelAgent(id)
set.awaitAgent(id, timeoutMs?)             // Promise<result<RunCompletion, string>>
set.list()                               // detached agents + ptys snapshots
set.registerPty(record); set.unregisterPty(id)
set.publishPtyCompletion(item)
set.drainAgentWakes(max); set.drainPtyCompletions(max)
set.waitForSignal(interrupt); set.waitForWake(); set.pulseWake()
set.close()
```

`roleKey`、agentName、childSessionId 是调用方给定的中立身份数据；库不认识 Manager/DevOps 工具权限。RunCompletion 使用明确的 completed/failed/abandoned DTO，带 run/child/participant、code/message/returned 等现有数据；不能把主体 DU 当作不透明对象再把整个 status 算法回调出去。ReturnedMaterial 保持原字节，不在本项再编解码。库负责首次完成、完成优先于取消的快照判断和计数。主体桥只将 DU/身份包装/日期与普通 JS 数据互转，且 API 返回快照不得外泄内部可变对象。

取消对象仍由库内运行持有。不要为这次迁移把当前逻辑取消升级为物理 abort。生产 `runWork` 当前是 `unit -> Task`，内部 `_ct` 没有交给宿主 runner；迁移应保留这一点。若库内部继续使用 F# CancellationTokenSource，它是私有实现；外层无需维护第二份可取消 run。若内部改用布尔标记/Promise，其状态转换必须与当前代码一致，不能用 Promise.reject('cancelled') 代替原本不结算的 ParentCancelled。

`Execution/Agent/Program.fs:29` 的 `validateSession` 已核清：只有 `ctx.AgentName = expectedName`，没有能力副作用或宿主 I/O；`runAgentFlow` 是 Task 的成功/异常/取消映射。将这次运行的比较和现有错误映射直接放入运行边界，不引入全量 AgentProgram、主体 session 类型或一个“调用旧程序”的回调。ChildRunProgram 当前用同一 run.AgentName 组装 ctx 和 expectedName；保持该行为，不借此新增名称注册校验。

### 必须原样保留的细节

1. `fork` 对 agent 名称 Trim；mailbox 已取消返回 NotFound；已有 active run 返回 Nudged，不能再次调用 work 或换 prompt。已有结束/取消 run 被新运行替换，但仍返回 Nudged；新 id 才 Created。
2. run-id 仍按现有 `run-` + 8 位 GUID 形式生成；restore 是 `restored-<id>`、提示 `"(restored from journal)"`。先把新 run 放入 map，再启动 detached task，防止同步完成时查询不到自己。
3. completion cell first-write-wins；存值和 IsCompleted 先更新，再唤醒等待者。Fable 的 Task.Result 不能替代 StoredValue。当前完成发布会 pulse，再调用 listener；listener 抛错被吞掉。不要顺带改变成只有 TrySet=true 才 pulse 的优化。
4. 外层 work 抛异常当前先转 `AgentCompletion.ofSimpleError`；运行程序中父取消返回 ParentCancelled 而不写完成格/不伪造中断完成，内部取消但 token 未取消走 HostFailure。必须分清两层 catch 顺序，不把全部 Promise rejection 统一为 ParentCancelled。
5. await 未知 id 仍是 `Unknown agent id: ...`；timeout<=0 立即给 `await agent timed out: ...`，正数走既有 raceExit；超时只结束本次等待，不取消 run。原 await 已持有旧 run 的 completion，不会因同 id 后续替换自动改等新 run。
6. List 完成优先：INTERRUPTED→Interrupted、abandoned→Closed、其它完成→Idle；未完成且 runtime/子运行已取消→Closed，其余 Busy。CurrentRunId 只在完成时清空，不能在逻辑取消时顺手清掉。TerminalStatusLabel 保留原文字来源。
7. restore 只补缺失；MarkInterrupted 只取消而不完成。Cancel/Close 仅第一次 mailbox.Cancel 成功时取消 agent 并逐个 cleanup，cleanup 单项抛错不阻断其它项；PTY 登记保留到物理退出。PublishPtyCompletion 对已不归此 set 的 id 静默忽略。
8. agent 通道只存唤醒 token，持久 Join 仍从 Journal 取结果；PTY 通道保持现有具体结果队列。这不是引入新的 PTY 产品能力。

### 必须保留的行为与失败边界

- linkNamed 无 journal 仍 Ok；有 journal 先预检再 append。完全相同绑定重放幂等，不能把 handle 静默绑定另一个 child。Byname trim/忽略大小写查询、已退休绑定仍可寻址、creation order 按 HandleLinked fold 顺序不变。
- exact work 是 handle+child+authorityRoot，run id 另核对。相同 exact work+run 重放保留旧状态；另一个 active work 阻止新准入；历史 legacy 记录不得升级成当前可执行 work。
- recordWorkCompletion：必须有 journal；核对 handle/child、admitted work 和 logicalRun；已 voided 且无完成拒绝；Active 才写新完成，已经终局保持现状。先写完成 blob 再 append HandleWorkCompleted；append 失败不伪造已落事实，不自动重发外部工作。原 CompletionRecord codec 复用，不复制。
- consume：先 refresh，再取当前 work 和 expected completion cell，再 mint consumptionId、预检、append，最后 refresh 并确认同一 consumptionId。另一消费者先完成给 AlreadyRetired；未确认给原 AppendFailed。不可把进程内锁当持久 CAS，也不可使用调用方旧 record 选择 expected cell。
- 历史无 work 的唯一消费例外仍为 Abandoned(Voided)；其它旧 unscoped 完成只读。cancelChildren 逐个写放弃，首个失败停止，已写过的保持已写；不引入批量事务或回滚。
- Join 候选先拼 abandoned+completed，再按 CreationOrder/TargetAgent 稳定排序，不能按 Promise 完成顺序。maxCount 上限仍为当前 JoinBatch.Max（32），<=0 返回空。
- body ref/digest/读取失败、exact-work mismatch 的错误与原路径一致；无正文的 Cancelled 生成 abandoned 回报并消费；无正文的 Terminal/SendFailure 不假装空成功。无效解码继续等，且不消费；legacy false abort 保持现有撤销/退休拒绝/读错忽略的细分。
- drain 跳过竞争后刷新：候选未变走余项，变化重取；成功已累积后碰硬错误，仍返回已消费的成功结果，第一项就硬错则 Error。Promise rejection 不在此项顺手改 Result 或加 retry。
- Fission 的 accept 作用于 effective record，拒绝的结果留给对应 lane。当前实现先筛 binding 的有效 summary，再形成该 binding 的 delivery work；新 API 必须保持这一先后关系，不能改成逐个 historical work 独立重判 affinity。没有临时第二份 mutable History。

## 4. OpenCode compaction 生命周期

### 为什么是一件事

用户让软件继续处理长对话时，OpenCode 会启动压缩请求、请求自动继续，然后把压缩后的新输入送回插件。适配需要辨认这些特殊请求、暂时让出产品历史变换、向现有产品压缩能力取贡献，并把实际观测交给 Prefix 的重锚协议。现在同一个生命周期分散在 PluginHooks 的 HashSet、PluginRuntimeScope 的一次性观察标记和配置缺口、HostCompactionObserver、HostCompactionGate，以及 HostSignalBootstrap 的快照入口。完整迁动应收走这些宿主协作状态，不能只搬两个 Gate 文件。

真实路径：

- `OpenCode/Plugin/PluginHooks.fs`：`configurePluginHost` 记录 ConfigPolicy.establish 返回；`activeCompactingSessions` 同时被 `RequestLatency.create`、`isCompactingTransform`、session-deleted 消费；真实注册 `experimental.session.compacting` / `experimental.compaction.autocontinue`。
- `OpenCode/Host/PluginRuntimeScope.fs`：`compactionSettingGap`、`startupProbeDone`、`startupProbeGate` 及四个访问方法，是第二处 compaction 状态 owner。
- `OpenCode/Host/HostSignalBootstrap.fs:160`：组装 `CompactionProbe` 并把 `HostCompactionObserver.observe` 注册为 Scheduler 的 `onSnapshot`。它必须独立于业务 Turn：手动压缩可能根本没有 active logical run。
- `OpenCode/Host/HostCompactionObserver.fs` 90 行、`HostCompactionGate.fs` 135 行是生产实现；不是 Surface 夹具。`Host/CompactionPolicy.fs` 与 `Composition/Plugin/ConfigPolicy.fs` 是当前产品策略，不应误算为新核职责。

### 目标边界

在 `wanxiangtong/opencode/compaction/` 放 `OpenCodeCompaction`，拥有 active session 集、配置缺口和一次性首轮观察标记。对外消息建议：`RecordSettingGap`、`OnCompacting(input, output)`、`OnAutoContinue(input, output)`、`TryConsumeHistoryBypass(input, output)`、`IsCompacting(session)`、`ObserveSnapshot(session,messages)`、`ForgetSession(session)`。这是一个对象的生命周期，不分别发布“set / gate / probe / observer”。

输入是现有产品 `ICompactionPort`（OnCompacting/AutoContinue）、临时咨询上下文、诊断和 Prefix 重锚参与者。临时咨询的 overflow/abort 是 OpenCode 协议，留在本适配；临时咨询快照本身仍归上一批 RequestProjection / negotiation 实体，不复制。产品 Scope/Prefix 判定、Journal 事实编解码和压缩材料内容仍由已有产品组合提供。`HostCompactionGate.reanchorObserved` 若继续涉及产品事实 DTO，缩成产品侧 `PrefixReanchor` 连接器供适配调用；不要让核认识 SessionMessage，也不要用“整个 onSnapshot 回调”把刚迁走的流程藏回产品面。

ConfigPolicy 是共享产品能力，先保留其现有位置和行为；不要因名称里有 Host 就整段塞进 opencode 目录。HostSignalBootstrap 只注册本对象的 ObserveSnapshot；PluginRuntimeScope 不再持有第二份三个状态。PluginHooks 保存真实 hook 注册、调用对象；延迟看护的谓词直接读同一个对象。

## 6. Change：Manager 作业准入、发布与恢复的完整生命周期

### 总流程与边界

建议一个 `wanxiangli/change` 入口、一个完整模块，内部为 `ChangeHistory` 与 `ChangeJob` / `ChangeRuntime`。这是新增入口的合理候选：现有 `wanxiangli/git` 是物理 Git/Worktree 能力，`result-mailbox` 是结果队列，`work` 是任期规则，均不拥有这条跨能力发布流程。不要将 WorktreeCreateIntent、CAS判断、CleanupOutcome 分别建包；也不要把 Manager 会话生命周期整体塞入 git。

### 对象与公开 API 草案

`ChangeHistory` 私有拥有 Jobs 与 WorktreeEffects，支持 `apply(event)`→不可变新 History / 原拒绝；`job(id)`、`jobBySession(id)`、`jobByName(name)`、`activeJobs()`、`worktreeEffect(identity)`。输出 detached DTO，事实字段用不透明字符串/数组；不暴露 F# record、全局 ProjectionSet 或宿主 Session 对象。

`ChangeJob.run(job, collaborators)` 拥有单个作业的发布在途状态与顺序。`collaborators` 分为具体职责对象而非每个 if 一个函数：

- `history` 只读取得**当前已提交**的 ChangeHistory；`journal.append(event)` 只做 fact/stream 转换和持久提交。
- `git` 执行现有 isDirty/readHead/targetHead/rebase/conflictedFiles/hasRebaseHead/ffMerge；业务选择都在 ChangeJob，不把整段旧 Program 包成回调。

`ChangeRuntime.start(request)` 拥有准入协作；`recover(jobRecord)` 采用现有 durable worktree、接回同一发布流程；批量等待组合现有 ResultMailbox。请求已带确定 jobId、identity/path/target/agent/byname/request，默认路径与 `manager/` 命名在产品组装一次决定；库当作原样标识。不能让 runtime 拼 OpenCode payload 或获取全局 provider 配置。

### 必须逐一保持的规则

**History：** 重复 create 不覆盖已有作业；unknown job 的普通状态事实是 no-op；terminal 保留在 Map 防重放且不再被更新。Candidate/Conflict/Rebased/Claim 是独立字段，不压成“最新阶段”。Rebased 与 Claim 的后到不同值可覆盖前值；不得改成冲突拒绝。PublishClaimed 先查是否有 rebased，再比 commit，不擅自额外比 expectedHead/target；即使 terminal，fold 的既有前置拒绝顺序也照旧。Worktree request 遇已有记录 no-op；created 遇已有 created no-op，不能以冲突检查替代。byname 空白 fallback 到 agent；查询 trim 且 OrdinalIgnoreCase，重复别名按原 Map jobId 次序选首项。

**准入：** 先 target cleanliness；确定 identity/path 后先记录 WorktreeCreateRequested 再物理 create，确认后写 WorktreeCreated。只有 Requested 不确定态需要枚举物理 worktrees；无相关项才可重建，路径/identity混配拒绝；Created同属主/路径直接 adopt，不重复Created事实。将工作树标durable之后，持久模式 Manager创建失败保留它待恢复；非持久模式失败释放。确认事实写失败时释放刚取得资源，释放返回错误不覆盖原错误。门内完成准入后释放门，之后才 activate/startPublication。

**发布：** Manager 的 Continue 真正 ContinueLoop 后再等下一信号；Candidate准备失败先查冲突，无冲突时当前代码会再 PrepareCandidate，一刀中不要改成单次。变基/冲突与Manager续行均在发布锁外。门内重新读 target、查 job/target/CAS、worktree HEAD pin、dirty/conflicts，先落PublishClaimed再FF，后落Published。精确字符串 `target ref moved` 才进入已有CAS错失处理；普通错误不冒充重试。FF已落地但Published尚未记录，恢复先判 target==candidate，再判 target==expected，已落地只补事实、绝不第二次FF。
