## 1. 用户真正要求的行为

resetScope 之后的新模型并非一无所知。它拥有旧模型主动撰写的 oldScopeVerboseVerbatimExperience、newScopeObjective、按原规则保留的用户原文和历次 reset 调用/结果。**交接材料已经告诉它工作到了哪里、做过什么以及需要接着做什么。**

但交接材料不能穷尽原来的上下文，也不必复述一切。新模型可以据此辨认需要更深入核对的某项具体决定、依据、错误、原始输出或未决问题。它应该**自己选择问题，向旧 Scope 咨询**，而不是让系统替它判断哪些信息可能遗失。

这与 negotiate 如出一辙：子代理收到当前委托任务及可见指令后，首次必须问委托者；新 Scope 收到旧我的交接材料后，首次必须问旧我。两者不是“你不知道自己不知道什么”，而是“你知道目前获得了什么，因而有能力决定还要澄清什么”。

**每次成功 reset 后，新模型必须亲自调用一次 askPreviousScope(questions: string)**；没有“可选首问”或“系统自动代问”两个分支。后续若有需要可以再次调用。首次问答采用与 negotiate 相同的异步发送、接受回执和后到 steer，不等待答案才继续工作。

模型的内容选择完全自主：宿主不为 questions 预填文本，也不做语义审查。允许把若干相关疑问集中问完。举例，若交接写有“已排除方案 B”，新模型可以问：“方案 B 具体被哪个反例排除？该反例的输入、输出和观察边界是什么？”；如果交接已很充分，它仍需提出自己最想核对的一处依据、假设或下一步细节，而非跳过问答。不要把例子转成硬编码模板。

旧 Scope 的“旧我”是利用它真实冻结的 provider 请求视图重新进行的一次只读模型推理，并非复活隐藏思考；回答不构成新的事实权威或完成凭证。

## 2. 唯一工具接口

askPreviousScope(questions: string)

questions 为非空字符串，由**重置后的新模型**在看过交接材料之后组织，可同时问多个问题。第一版仅访问同 session 刚关闭的、紧邻上一 Scope；来源身份由持久 epoch 决定，不暴露任意跨会话查询，也不要求模型自己指定 archiveRef。

第一次 reset 前调用，明确回复 NoPreviousScope。每次 reset 创建新 epoch，必须产生新一次首次问义务；之前其他 epoch 的调用不算。首次调用之后的主动追问为普通咨询，每个真实调用有独立 receipt，同一次工具调用重放不能重复派发。

## 3. reset 后的严格时序

1. 旧 Scope 的模型正常调用 resetScope(oldScopeVerboseVerbatimExperience?, newScopeObjective, newScopeTurnBudget)，其中交接经验由旧模型自己填写。依既有 HNI/Provider 物理证据取到**导致该次 reset toolCallId 的完整旧请求视图**。
2. 先保存并验证不可变旧档案 blob，再在同一个 durable 提交中把 ScopeReanchored(e→e+1)、archiveRef/digest 与新 epoch 的 AwaitFirstPreviousScopeQuestion 义务绑定；只有提交确证后更新内存的 scope/budget。**此时绝不创建问题、绝不发送旧模型请求。**同 resetToolCallId 重放不得新开第二个 epoch/首问义务。
3. resetScope 成功返回的原始文本仍为“Scope reset. Objective: ...”，按原合同不改持久化字节。新的 Provider 请求**副本**进入 pending：不显示预算后缀、不递减预算、初始化时序不前进，weak 提醒保持关闭；解除条件是 Host 登记了本 epoch 首次 askPreviousScope 调用的 receipt。这套时序表现与 negotiate 的 BeginNegotiation（置位、budget=0、initialized=false）到 NegotiationReplyAdmitted 同构，见 §4 现状锚点。
4. 首问提醒：“你已经收到前一 Scope 的交接。现在必须先调用 askPreviousScope(questions)，由你根据交接及当前目标，自行向前一 Scope 确认需要澄清的具体问题。调用受理后不必等待答复，可继续工作；回答随后作为 steer 到达。”英/中文资源配对；不往工具原始结果或用户原文写入提示。提醒按同一身份冻结，只写一次、逐字重放。
5. pending 期间，每个新首次呈现的工具结果、assistant tool part 和操作员消息都挂对应的 MUST 提醒：negotiate 的提醒去问 delegator，askPreviousScope 的提醒去问旧 Scope；两者按同一身份冻结，只写一次，逐字重放。现行 PairHint.fs:476 在 pending 期间把工具结果提示整体抑制，本次要把 negotiate 一并改成逐个新工具结果继续提醒，不保留旧行为（见 §4 现状锚点）。
6. 新 Scope 的**下一次真实模型回合**自行组织 questions，发出真正的 askPreviousScope 工具调用。只有 Host 入口看到该模型回合、session、epoch、真实 toolCallId 和合法 questions，才可把本轮首次问标记为已尝试。仅有工具描述、提示文本、模型的“我问过了”散文或 reset 前预排工具调用都不算。
7. 入口以该调用为源持久登记询问 receipt，立即返回“已接受发送”或明确失败，不同步等待回答。若已受理，才用旧 Scope 冻结上下文发出额外一轮模型请求；答复沿现有 PromptDispatcher/observed 路径送入真实 user-carrier、agent 来源的 steer。
8. receipt 受理即解除 pending：预算与初始化时序恢复，resetScope 的拒绝提示与首问提醒随之撤下。首次有效调用完成其**主动发问义务**以后，新 Scope 可继续工作，即使旧我尚未回答；之后新模型可根据新发现的问题随时再次 askPreviousScope。再一次 reset 又开始新一轮强制首问。

这里“每次 reset 都多一轮模型调用”的**正常路径**含义是：新模型必须亲自发起工具调用，宿主据此再调用一次旧模型。外部 Provider 不可用或效果未知时不能捏造成功或盲目重试，因此不能把“意图”伪装成已经实际完成计费调用。

## 4. “必须调用”如何验证，而不审查问题内容

必须只写在提示文本里，靠提示与时序推进兑现，不做全局工具门禁。negotiate 与 askPreviousScope 共用同一个 pending 状态与呈现规则，区别只在 kind、提醒文本、来源/目标与解除条件；不维护两套提示逻辑。下列行为即目标设计；现行实现与其不同的地方在现状锚点逐条标明，不把旧行为写成目标。

- 提醒挂载：resetScope 结果首次呈现时附 MustAskPreviousScope 提醒；pending 期间每个新首次呈现的工具结果、assistant tool part 和操作员消息都挂对应 MUST 提醒，按同一身份冻结只写一次、逐字重放；提醒不携带预算后缀。
- 时序冻结：未解除 pending 期间不显示预算后缀、不递减预算、初始化时序不前进，weak 提醒关闭；再次 resetScope 由该工具自身拒绝执行并返回说明文字、提示先完成首问，与 negotiate 现行的 resetScope 自拒同构，拒绝时自身不产生 durable 效果。
- resetScope 同批工具调用的既有 barrier 次序不改变：reset 之后已预排的工具仍按原合同归属，但那是**旧模型回合的预排工作**，不能算新 Scope 的首次问。
- 任何普通工具都不因未问而受阻：Host 不在 tool.execute.before 检查首问义务、不拒绝新外部工作效果。现存的两处硬拒绝（临时会话工具、negotiate 会话资格）保留，与本节无关。
- 有效 questions 仅检查非空等形式要求，不根据内容阻拦或要求特定关键词。新 Scope 问什么是它自己的判断。
- 一次真实有效调用即完成“模型亲自问过”的要求；**不以旧我回复、排队成功或 PhysicalAccepted 为解除首问义务的条件**。与 negotiate“首次答复物理到达后才可初始化 resetScope”的既有条件分别管理，不混淆——ask 的解除条件是首问 receipt 受理，negotiate 的解除条件是首次答复物理到达。
- 调用确实执行后若档案不可用、transport 明确失败或 Provider 后果 Unknown，向模型返回真实失败/未知；已验证的有效失败调用尝试也证明模型确实主动问了，不能把未答误称已回答；失败不阻断后续工作，模型可自行再次追问。
- 同一调用身份重放只能读原 receipt/结算，不能重复向模型请求。

## 5. 旧档案与恢复义务

不得把已经清理的 Host 历史重编码成旧我上下文，更不得拿 wanxiangli/pair-hint 中 process-local rememberSystem、rememberMessages、rememberModel 的不同回合最后值拼成同一份物理请求。档案应捕获与本次 reset 严格因果匹配的完整实际 provider 出站 system、messages、model/variant、工具目录和必要 run/attempt 身份；不可捕获时须在真实 canary 中确认阻塞，不能用摘要假冒。

档案写入主工作树 .Herdchestra/ 的不可变内容地址 blob，由 Journal 原子引用；旧前缀在之后问答中逐字复用，不重算预算或 pair-hint 注入，也不回填新 Scope 正常请求。失败、不确定提交及重复 resetToolCallId 都要遵守原子、查询先于重试和单一权威不变量。重启后通过持久 ref 恢复，而不是依赖内存。下一次 reset / session.deleted 时要按真实 in-flight 资源租约收尾，不能让晚到回答串 epoch。

## 6. 与 negotiate 的真实 DRY

不复制第二套 BTW。使用同一个只读咨询执行单元，统一以下机制：短命 Host 会话创建/关闭、实际 Provider 出站视图热替换、原模型/variant 与工具目录、tool.execute.before 无条件拒绝临时会话所有工具外部效果、统一的 pending 状态与 MUST 提醒呈现、普通文本答复抽取、有界失败处理、PromptDispatcher Detached/observed steer 投递和 PhysicalAccepted 确认。

| 合作事实 | negotiate | askPreviousScope |
| --- | --- | --- |
| 谁发问 | 收到任务指令的**新受委托者**，首次必问 | 收到交接材料的**新 Scope**，每次 reset 后首次必问 |
| 问什么 | 模型根据委托任务自行决定 | 模型根据交接材料与当前目标自行决定 |
| 向谁问 | 委托者的完整实见出站视图 | 同一 session 紧邻旧 epoch 已封存的实见出站视图 |
| 唯一身份 | delegator / recipient / generation / receipt | session / source epoch / target epoch / reset callId / receipt |
| 回来以后 | 实体答复到达才能解锁首次 reset | 受理有效首问后就能继续工作；答复稍后 steer |
| 共用物理能力 | 同一个 read-only consultation executor、provider request transform、临时会话 tool 前置禁令、Dispatcher 与确认观察者 | 同一组，不复制 |

具体复用已有的 PluginHooks.fs negotiationSdk / createTemporarySession / runTemporaryQuestion / deleteTemporarySession、PluginTransforms.fs 的 negotiationStartTemporary / negotiationProjectMessages 和临时会话工具前置硬门禁、ToolRuntimeScope.fs 的 sendNegotiationSteer；OMP 复用其 runEphemeralTurn 原生只读能力，不强迫转换成 OpenCode SDK。把源选择、协议 receipt 与目标 epoch 的差异放在各自的领域 owner，物理执行器不认识这些业务流程，也不注入兄弟服务回调。

现有 runTemporaryQuestion 对空回复和工具违规可能没有有界终止，两条路径共用的 executor 必须共同修正为有界重试与真实失败结算。实现是否 DRY 以两个使用方确实调用**同一执行体**、单方移除不破坏另一方基本契约为验收，而不是两个 helper 的名称相似。

## 7. 答案如何以 steer 到达

工具 Accepted 仅证明问题已受理，不等于旧模型已答。Answered、Queued、PhysicalAccepted 和模型已实际消费分别记账。回答通过 Host 原生用户消息载体进入本轮模型上下文，但来源标为 agent/ScopeConsultation，不能伪装成 operator 新输入、作废 turnBudget 或触发不相干初始化提示。

送达验证必须同时匹配真实 receipt、session、源/目标 epoch 与物理消息身份；晚到时若目标已再次 reset、用户已取消或 session 已删除，标记 Stale 并禁止注入下一 epoch。重复投递不得形成第二条已接纳 steer，Provider 结果 Unknown 不得盲目再执行有可能计费的请求。旧我可以坦言不知道；宿主不能替模型裁判回答内容。

## 8. 必须先红后绿的验收

1. 每次成功 reset 都有可验证旧档案 + 新 epoch 首问义务，但在**新模型实际调用** askPreviousScope 之前没有额外旧模型 Provider 请求。伪造“我问过了”不能通过。
2. 新模型确实拿到交接材料，问题可以针对其中一条具体决策补充理由与证据，不是宿主预置“你忘记了什么”；正常路径每次 reset 至少一次真实 ask，继而有一次真实旧模型请求。
3. 未问期间请求副本持续可见 MUST 提醒：reset 结果首次呈现、新到的操作员消息、新的工具结果与 assistant part 都挂对应提醒且逐字重放；预算与初始化时序不前进（无预算后缀、不递减、weak 关闭）；resetScope 自身拒绝并提示先问；首问 receipt 受理后时序恢复。测试必须证明普通工具不被拦：未问期间其他工具调用正常执行产生效果。旧模型失败不得冒称答复已送达。
4. fast-check 随机交错：连续 reset、工具同批次、真实/伪造 ask、后续主动追加问答、negotiate 首问、回答迟到、PhysicallyAccepted、会话删除、重启/Unknown。验证每 epoch 首问身份独立、同 receipt 最多一次有效 steer、不同代际不互相解除 pending。验收还需覆盖：未问期间普通工具调用不被拦、预算后缀不呈现；首问 receipt 受理后恢复。
5. reset blob 写失败、Journal Unknown、丢失真实出站视图时不得创建无档案的成功 reset；跨重启查询与已确认外部效果不得盲目重放。
6. 两条问答通过同一已抽出的物理执行器、provider transform、临时会话工具前置拒绝和 PromptDispatcher；重构前后的 negotiate 反例全部通过，不准复制后改名；共用的 pending 提醒呈现路径反例同时跑 negotiate 与 ask 两种 kind。
7. 单独 Fable 构建、真实 npm tarball 在 Node/Bun 安装、Host prefix-stability/context-compression/delegation-negotiation 回归、OpenCode/OMP hooks 与真实 Provider canary 分别取证。TODO/GAP 不计通过。
8. 对称验收：同一组测试分别覆盖 negotiate 与 askPreviousScope 的 pending 提醒，证明两者共用同一 pending 状态与呈现路径（每个新首次呈现的工具结果/assistant part/操作员消息挂对应 MUST 提醒、同一身份只写一次、逐字重放、不呈现预算后缀），且真实受理后两者都恢复预算时序。

## 9. 实施顺序与关键不变量

A. 修订 WHAT（并核对 context-compression [036] 的过时全文委派描述），把“**每次 reset 后必须由拿到交接的模型亲自首次调用**”写成正式协议与失败测试，且不改变 reset 原始工具结果。

B. 先把 negotiate 的临时模型问答与物理 steer 通道抽为共用执行体，保证原有协商语义等价。

C. 在 wanxiangli 建立持久旧 Scope 来源档案及每 epoch 首问义务的独立所有者，和真实物理 observation/Journal 显式组合；恢复、幂等、隔离测试通过。

D. 在真实 reset hook 中以同笔 durable 事实绑定档案与首次义务；下一模型回合由 askPreviousScope 自行选择 questions 启动旧模型。沿用与 negotiate 共用的同一 pending 状态与提醒呈现路径，临时咨询回合内的工具前置拒绝不扩展到新 Scope 的普通工具；处理并发与过期回答。

E. 依实际宿主和 Provider canary 验收，不凭设计稿关闭 GAP 或冒称运行时已更新。

关键不变量：

- CommittedReset(s,e→e+1,callId) ⇒ Archive(s,e) 已提交可校验，并有 AwaitFirstPreviousScopeQuestion(s,e+1)，**不推出旧模型已被调用**。
- PendingPreviousScopeAsk(s,e+1) 未解除 ⇒ 发往模型的请求副本不呈现预算后缀、不递减预算、初始化时序不前进、不允许再次重锚（resetScope 自身拒绝，拒绝时不产生 durable 效果）；每个新首次呈现的工具结果、assistant part 与操作员消息都携带对应 epoch 的 MUST 提醒，不得只挂用户消息；首问 receipt 受理解除 pending。
- AskPreviousScope(s,source=e,target=e+1,r) ⇒ 只能用 e 的冻结视图回答，只能向 s 的 e+1 发送，且同 r 至多一次 PhysicalAccepted。
- 每次 reset 都要新的首次问；答复不必同步到达；后续追问仍由新模型自行选择。
- negotiate 与 askPreviousScope 只在来源和作用域的业务协议上不同，其共用的 pending 状态与提醒呈现路径、只读问答、临时会话工具前置拒绝及物理投递必须共用一条实现。
