## 3. 第一项：returned-material（已接回）

### 3.1 对总流程有什么用，边界在哪里

一个参与者做完后，主程序需要保留报告和随报告交回的材料，之后取回、交接和展示。当前 [Foundation/ReturnedMaterial.fs](../src/Wanxiangshu/Foundation/ReturnedMaterial.fs) 统一保存 `{body: string[], carry: string[]}`：body 是报告原文，carry 是材料原文。这个划分由调用方明确提供，不从文字内容推断。

迁走整套表示协议：`encode`、`body`、`carry`、`validate`、`entries`、`fullText`。它没有持久状态；用纯函数即可，不造令牌、WeakMap 或管理对象。

三个相邻职责明确组合：

| 责任 | 所在处 |
| --- | --- |
| 会话交付格、围栏、选材和去重 | 已有 `wanxiangli/delivery`；本轮不改 |
| body/carry 的规范 JSON、读取与原文视图 | 新 `wanxiangli/returned-material` |
| 指令注释、材料表格及 TOML 转义 | 已有 `wanxiangli/llm-text`；本轮不改 |
| 调用先后、完成记录、存储和宿主工具协议 | 现有主体调用方，宿主部分将来按万象通边界处理 |

`delivery` 的 `JsDeliveredValues` 已在生产返回原生 body/carry，并没有保存这个 JSON 协议；所以本项是新职责，不是补接旧库。新模块不依赖 delivery 或 llm-text，二者也不反向调用它；主体继续显式组合。

### 3.2 建议公开接口与兼容边界

```ts
export function encode(body: readonly string[], carry: readonly string[]): string;
export function body(encoded: string): string[];
export function carry(encoded: string): string[];
export function validationError(encoded: string): string | null;
export function entries(encoded: string): { text: string }[];
export function fullText(encoded: string): string;
```

`validationError` 的 null 对应主体原 `Ok()`，错误字符串对应原 `Error`；保持现有两种错误文字。其余函数仍可按原约定抛错，不把读取失败转成空材料。数组为原生 JS 数组，不暴露 Fable list/Result。

必须先把下列现状写成小测试，移植时不顺手统一：

1. `encode` 生成 `JSON.stringify({body, carry})` 的字节，body 键在前。保留每个字符串、块顺序、空串和重复；不 trim，不归一化换行，不排序。
2. `body` 与 `carry` **只检查被读取的字段**。显式 null 返回空列表；缺字段 undefined 或非字符串数组抛错。另一个字段无效不阻止当前字段读取。不能用一次严格 `decode` 替换这两个入口。
3. `validate` 比较重新编码后的完整字符串。键序、额外键、JSON 空白和字符串转义不同，即使解析对象相同也不通过。`{"body":null,"carry":[]}` 可读取 body，但不是规范存储字节。
4. 非法 JSON 的直接读取仍抛错；校验入口仍返回原错误。非对象、数组根、混合元素的数组保留原拒绝路径。测试比较项目自己的错误文字，不硬编码不同 Node 版本的原生 JSON.parse 报错全文。
5. `entries` 只把 carry 依序映成 `{text}`，保留重复；`fullText` 将 body 后接 carry，以 `\n\n` 连接原块，不先渲染 TOML。
6. 完成记录 schemaVersion 仍为 4，存储字节不变，不引入历史数据迁移或新版本兼容层。发现字节不一致先修移植，不改快照迁就它。

`ofEntries` 当前唯一使用方是 [JoinSurface 的输入转换](../src/Wanxiangshu/Execution/Delegation/Fork/JoinSurface.fs)。它是测试 Surface 的 `{text}` 夹具输入，不是新增库 API 的理由。将这段形状转换收回该 Surface，保留原输入错误行为，再从 ReturnedMaterial 的 `.fs/.fsi` 删除 `ofEntries`。生产 `entries` 仍迁入新模块，因为 ToolRegistry 的真实返回会使用它。

## 4. 第二项：keyed-serial（已接回）

### 4.1 迁走的是跨调用状态

同一会话可能同时收到多次捕获请求。现有 [Context/Trace/Capture.fs](../src/Wanxiangshu/Context/Trace/Capture.fs) 用 `captureTails` 排队，避免两次操作同时根据旧投影分配持久游标。新的实例拥有 key 到完成尾项的映射，负责排队、放行与清理；Capture 仍拥有捕获协议。

```ts
export class KeyedSerial {
  run<T>(key: string, action: () => Promise<T>): Promise<T>;
}
```

只接受 key 和工作函数，不接收 Session、Journal 或 Trace 对象。一次 run 对应一次执行，不合并、不去重；没有公开队列、reset、drain、计数、取消、超时或重试接口。

它与 `bounded-map` 的差别是跨调用、同 key 串行；后者只管单次映射的并发上限。已有 `admission-queue` 管准入/容量/认领，不替代它。也不顺带统一 ManagedChatExecutionFlight、ReconcileScheduler 等领域协调器：它们的失败传播和业务含义不同。

### 4.2 先固定调度细节

- 同 key 按 run 调用顺序执行；不同 key、不同实例独立。
- **同步登记队尾，异步启动 action。** 当前生成的 JS 即使没有前驱，也经过 Promise 微任务后才调用 action。不能把第一项改为同步执行。
- 队尾是独立、最终成功完成的放行信号，不是 action 的结果 Promise。成功、同步抛错或异步拒绝都放行后继；本次结果/错误对象原样交回，不包装。
- A 完成时若 B 已经排队，A 不能删除 B 的尾项。清理只删除仍指向本次完成信号的 key。
- 后继等待 action 结清与放行，不等前一调用者消费结果。不要新增“调用者 await 返回后才开始下一项”的时序承诺。
- 工作若一直不结清，同 key 后继继续等待，其他 key 不受拖累。非重入用法不变：action 可以排同 key 后继，但不能在自己结束前 await 该后继，否则自等待。写清这个限制，不新增运行时警察、跳队或超时机制。
- Capture 原无 journal 直接返回、冲突拒绝、存储错误转换、原文保存均保留。已有 Trace 的生产桥接不变，本项不是首次接入 Trace，也不是 Trace 协议升级。

### 6.1 一次迁走完整的物理锁职责

候选源码是 [Git/IntegrationGate.fs](../src/Wanxiangshu/Git/IntegrationGate.fs) 与 [Persistence/EventStore/ProcessEventLog.fs](../src/Wanxiangshu/Persistence/EventStore/ProcessEventLog.fs)。发布锁使用后者公开的 `processAwareFs`；只搬 IntegrationGate 会保留 Git 对日志实现的依赖，边界不完整。

拟设公开入口 `wanxiangli/file-lock`，共同迁走：

- 私有进程感知 fs 适配：原子创建锁目录、写入 owner.json、读取 owner PID、按原逻辑调整 mtime、递归删除锁目录。
- proper-lockfile 的获取、心跳与释放协作，以及现有两种获取等待策略；保留底层错误，不加入日志或发布判断。
- 每次成功获取后独有的释放句柄与一次性 released 状态。调用者只能请求释放，不取得原生 fs、计时器、PID 状态或底层 release 函数。

主体继续负责：repo/branch 的 SHA-256 锁路径、日志 `.Herdchestra/wanxiangshu` 路径及目录准备、何时持锁、保护哪段工作、发布诊断、日志 `AppendNotAttempted`／`CommitUnknown`／`NoNewWriteReleaseFailed` 结算。`withStoreLock` 保持调用方的工作与异常处置，不把整个业务回调框架搬进锁库。已有 Trace 桥接、存储与语义不在这刀内。

### 6.2 接口起点与不能混同的两种策略

已采用的公开获取与租约接口如下；完整声明以库的 `src/file-lock/index.d.ts` 为准：

```ts
export interface FileLockLease {
  release(): Promise<void>;
}

export type LockWait =
  | { kind: 'Retry'; retries: number; minTimeoutMs: number; maxTimeoutMs: number; factor: number }
  | { kind: 'Budget'; budgetMs: number };

export function acquire(path: string, wait: LockWait): Promise<FileLockLease>;
```

这不是通用锁框架。共同的 `realpath: false`、stale 5000 ms、update 1500 ms 先作为现有实现的固定行为；不为将来需求扩充配置、跨机器协调、自动续约恢复、取消或同步锁 API。Budget 分支的退避算法保留现有固定规则，不增加任意策略回调。

| 使用方 | 本次必须保留的实际行为 |
| --- | --- |
| 发布锁 | 交给 proper-lockfile 原有 retry 策略：50 次重试，minTimeout 50、maxTimeout 250、factor 1.1。它将获取错误交给 retry.operation，**不只重试 ELOCKED**；耗尽后由原 retry.mainError 选出的错误仍在主体转换为原 `publish lock acquire failed for ...` 诊断 |
| 日志锁 | 每次 proper-lockfile 调用设置 retries=0；外层只捕获 ELOCKED，按 `min(150, round(30 * 1.1^step))` 毫秒等待，step 在 0…9 循环；在每次尝试前检查 Date.now 的 30000 ms 总预算。非竞争 I/O 错误立即抛出原对象 |
| 日志预算耗尽 | 保留 attempts 与 waitedMs，且不再发起一次获取。预算约束的是再次尝试，不承诺精确在第 30000 ms 取消已开始的调用或等待；不改用单调时钟或新增 AbortSignal |

预算耗尽返回库的原生 `FileLockAcquireTimeout`，携带 path、attempts、waitedMs，并由公开 `isAcquireTimeout(cause)` 识别。主体仅将它转换回原 `StoreLockAcquireTimeout`，其他错误对象原样传递，不丢失 cause 身份、code、syscall 与 path。

### 6.3 必须保留、也必须说实话的边界

- owner.json 含 PID 和时间，当前只用 PID 活性辅助识别陈旧锁。`process.kill(pid, 0)` 的 EPERM 视为进程存在；失活 PID 令观察到的 mtime 变为 0。活 PID 不会强制 mtime 永远新鲜，锁仍可能按心跳时间判为陈旧。
- owner 文件写入失败或读取、JSON 解析失败目前被忽略，回落到既有 mtime 判断。这不构成可靠的跨机器身份或 PID 防复用机制；本刀不能添加更强承诺，也不能静默改变缺损 owner 文件的处理。
- 两处 Release 都先置 released，再等待真实删除。第一次失败后重复调用不重试；并发的第二次调用也不会等待第一次释放完成。不要换成共享 release Promise 或失败后恢复标志后仍声称行为不变。
- 第一条 release 的失败必须向调用者报告；重复调用的成功不能被解释为之前失败已恢复。底层 onCompromised 目前沿用 proper-lockfile 默认抛错，不改成吞掉异常或后台自动重试。
- 日志仍区分“没有开始追加”“追加后释放未知”和“没有新写入但释放失败”；锁库不依据文件是否消失宣布业务提交成功。

### 10.1 公共面与执行边界

入口 `wanxiangli/git-worktrees` 的 `GitWorktrees(repo, run)` 接收现有执行能力。run 只接收 `{cwd?, args}`，返回 `{code, stdout, stderr}`；主体固定执行 Git，仍经既有 OrchestratorGit/ProcessRunner，不改超时、输出转 spool、异常传播和默认 cwd。

| 消息 | 结果 |
| --- | --- |
| create(identity, path, sourceRef) | 成功返回拥有资源；失败不产生资源 |
| adopt(identity, path) | 接管已有资源，不查询、不创建，默认保留 |

### 11.3 公共接口

```ts
type JoinResult<T, I> =
  | { kind: 'items'; items: T[] }
  | { kind: 'empty' }
  | { kind: 'interrupted'; reason: I }

type JoinStart<T, I> =
  | { kind: 'ready'; result: JoinResult<T, I> }
  | { kind: 'pending'; completion: Promise<JoinResult<T, I>> }

class ResultMailbox<T, I> {
  start(): void
  publish(value: T): void
  drain(maxCount: number): T[]
  readonly hasActive: boolean
  readonly pendingCount: number
  beginJoin(maxCount: number, interrupt: Promise<I>): JoinStart<T, I>
}
```

主体在 beginJoin 前按现有规则夹到 `0..JoinBatch.Max`，再把库的 items/empty/interrupted 转成原 F# 返回值。empty 映射为包含一个 Empty 的 batch，但不把 Empty 入队；它不宣称所有工作已结束，因为零容量慢路径也可能返回 empty。drain 继续采用调用方给出的数量，不额外套全局上限。

Ready/Pending 表达原快慢路径，不承诺 Pending 的 Promise 此刻一定未完成。主体只在 Pending 路径使用现有 CausalAwait，并保留描述和中断原因；库不认识 observer。不得为了逐微任务复刻诊断调用顺序再增加 finish 端口或等待协议。

### 11.4 本次保留和修正的行为

1. StartJob 增活动计数；Publish 入队并将活动计数减至最低零，唤醒一个等待者。保留当前无 start 的 publish 可入队行为，不加配对检查员。
2. Join 先排空；在容量允许时已有结果优先于已经到达的中断。无结果且无活动工作立即 empty。
3. 慢路径先注册唤醒，再竞争本次中断，醒来再次排空；若已经有结果，交回结果。中断只撤回本次 waiter，工作与后来结果继续存在。
4. 保留零/负上限的现状：drain 不取结果；Join 在无活动工作时返回 empty，在有活动且无结果时等待。若队列已有结果而 cap 为零，旧代码仍走可立即唤醒的慢路径，随后可能返回 empty；先用用例记录，不悄悄改为“至少取一项”。
5. Host 已限制并发 Join；不新增多消费者公平或 wakeAll 承诺。原 Job.fs 私有 awaitSignal 无调用，退出 owner 时一并删除，不迁成新 API。
6. 旧代码在 CausalAwait 返回后才二次排空，库把二次排空包含在 completion 中，存在微任务顺序差异。本次保留原三种竞态，并补跨 1/2/3 微任务到达用例；由 race 先清理注册再排空，保住原断言，未放宽结果优先规则。
7. typed interrupt 拒绝在旧实现中会原样外抛，但不执行 dropWaiter。本次先用“拒绝→下一次等待→发布”复现遗留，再修复为原样外抛且撤回本次 waiter，保留工作和后来结果。这部分是定向修复，不称为纯等价搬迁。

## 14. 第一项 task-scope：回调工作的接纳与排空

### 14.1 迁走什么

用户退出、取消或卸下观察器时，已经接纳的回调需要收完，随后才能释放日志等底层资源；普通观察等待则只等当前忙期结束，不关闭后续接纳。

两处现有实现：

- `Execution/Delegation/Fork/Host/Runtime.fs` 的 acceptingOwnedWork、ownedWorkCount、ownedWorkDrainWaiter、observedWorkWaiter、ownedWorkFailure，以及 start/observe/finish/stop 和 AwaitObservedWork。`Host/Agent.fs` 的实际回调通过 TrackOwnedWork 进入，取消与 detach 路径负责 drain。
- `OpenCode/Host/PluginRuntimeScope.fs` 的 AdmitOwnedWork、FinishOwnedWork、RunBackgroundTracked、RunOwnedWork、StopOwnedWorkAndDrain 及对应状态。插件关闭先停止外部入口，关闭两路内部接纳，再等待调度器和回调，最后释放底层资源。

新对象只拥有接纳开关、在途数量、等待者与后台错误。宿主订阅、取消 agent、PTY、provider 生命周期、日志释放次序、disposeTask/cancelTask 单飞仍由原组合者拥有。这些不能被打包为“通用 shutdown”。`ToolRuntimeScope` 的同名工作入口依赖 ownership lease 而非这份计数，不在本项统一。

### 14.2 接口与行为起点

```ts
type DrainResult = { ok: true } | { ok: false; error: unknown };
class TaskScope {
  run(work: () => Promise<void>): Promise<void>;
  background(work: () => Promise<void>): Promise<void>;
  waitIdle(): Promise<DrainResult>;
  close(): Promise<DrainResult>;
}
```

`run` 对应插件前台：本次异常原样拒绝，finally 放行，不记入后台错误；`background` 对应两处已有后台路径：观察并保留错误，返回的工作 Promise 正常结清。Fork 的 waitIdle/close 适配将失败结果重新抛出；插件 close 取得错误后继续既定资源收尾，最后由外层报告。没有 start/finish 公共配对接口，没有可修改计数，不能让调用方忘记归还。

必须先固定下列细节：

1. 同步检查接纳并登记工作，然后沿原 TaskBuilder 的时点启动回调；不要额外插一个微任务，把 hook 从同步启动改成延迟启动。同步 throw 和异步 reject 都会结束本次登记。
2. 关闭后提交不运行回调，返回已完成 Promise；不加新的“scope closed”异常，不重开、不取消已经接纳的工作。
3. waitIdle 只等到当前数量归零。归零后新进来的工作属于下一忙期，不能把已经完成的等待重新挂回去；多次 waitIdle 的当期等待共用一次释放。它不承诺以后不会再有工作。
4. close 同步关闭接纳后等当前工作归零；重复 close 都能完成，不提前释放底层资源。回调中再提交任务，关闭前接纳、关闭后忽略。工作等待自己所在 scope 排空会自等待，保持既有限制，不加检测器。
5. **保持最后被观察的后台错误。** 两处注释说“first”，实际 `Option.orElse old (Some failure)` 在 generation 723 生成 `orElse(failure, old)`，后错覆盖前错。新实现保持现状并修正相关注释；若要改成首错，应作为另一个明确的行为决定。错误不会因读一次、出现成功任务或进入下一忙期自动清空；读取的是等待结束后实际观察到的错误槽，不是在调用 waitIdle/close 时冻结的快照。
6. 只等待本作用域已接纳的回调；不把 Promise 完成说成远端 provider 已停，不引入超时、重试或取消框架。

### 14.3 逐步施工

1. 在两处旧桥上固定启动时点、前台/后台错误差别、两次可控失败的覆盖顺序、当前忙期与永久关闭的区别。用手动 Promise 门闩，不靠 sleep；所有任务在 finally 释放。
2. 库新增就近说明、TaskScope.fs、工程、声明和行为测试；一个对象独占上述状态。不要把原宿主对象或日志传进来，也不要复用 result-mailbox 存任务结果。
3. 注册公开入口和独立构建，用真实安装包检查 TS 及 Node/Bun：接纳两项、关闭、拒绝后仍排空、晚到回调不执行。复用既有打包夹具。
4. Fork 每个 runtime 建一个 scope。TrackOwnedWork、终局/失败回调仍通过原入口，只把登记与排空委托库；AwaitObservedWork 和 DrainOwnedWork 做结果到 F# 异常的转换。删除旧计数、锁、两个等待者、错误槽与登记/放行算法。captureOwnedWorkFailure 还被 DetachObserversAfter 用来收集独立清理错误，保留必要的无状态 catch，不能把取消/卸载组合一并搬走。

### 15.2 不顺手改变的行为

- prepare：add -A → unmerged 检查 → 冲突标记扫描 → 检查真正 rebase 目录 → continue 或清理旧 REBASE_HEAD 后 commit。“nothing to commit” 的既有成功解释保留。
- rebase：以 rebase-merge/rebase-apply 目录决定继续还是新开始，不把 REBASE_HEAD 当作在途信号。独立 continue 路径先 stage，prepare 内 continue 已 stage，不重复或漏掉。
- fastForward：核对工作树 HEAD 与 candidate pin → 当前分支与冻结 target → target HEAD 与 expectedHead → ancestor → clean → merge 固定 SHA → 读取实际 HEAD。任何一步失败不继续后续命令。
- 原 dirtyPaths 的文本解析、stderr/stdout 优先顺序、宽泛 ref-moved 文本判断先保持。不同时改 porcelain -z、路径语义或错误分类。库不声称提供 Git 原子 CAS，外部进程竞争仍可能存在。
- Git 命令失败或 runner 拒绝不能变成成功；如果物理 merge 已发生、结果核对失败，外层按现有协议观察，不自动重发。库不代写 Published 事实。

## 16. 第三项 file-baseline：原始文件捕获与比较

### 16.1 用途与组合

完成一个案例时保留相关文件原件；以后查询旧答案时，用同一次目标读取形成差异和下一份基线。生产调用是 `Casebook/Lifecycle.fs → Capture.freezeCompletionState` 和 `Casebook/Bookkeeper.fs → Capture.computeMaintenanceDiff`，不是只有 Surface。

迁走 `Repository/Knowledge/Casebook/Capture.fs` 中 StoredFileState/CapturedFile、严格读取、payload 保存/读取、基线编码解码与比较循环。没有长期业务账本，只有一次操作的读取与保存协作；Casebook 是否刷新、何时提交、body/基线事务仍归原业务 owner。

新组合者 `FileBaseline` 绑定 `resolvePath` 与只含 read/write 的 payload 能力，不接整个 IEventStore。`capture(paths)` 返回规范基线字符串；`compare(paths, baseline)` 返回 diffSummary、refresh、targetState，均使用 `{ok,value/error}` 结果。payload read 返回字节或 null，write 返回引用字符串；回调拒绝继续原样传播。库内部通过公开入口使用现有 casebook-maintenance 的 fileDiff/summarize/readFailure，不能复制 diff，也不把 I/O 塞进原纯能力。主体把既有 root 绑定到 resolve 函数，避免仅为路径解析引入整个 FileSession，不另造文件系统抽象框架。

### 16.2 固定兼容与退出条件

## 17. 第四项 segmented-writer：分段日志的物理写入器

`Persistence/EventStore/ProcessEventLog.fs` 同时含追加、读缓存、倒读、保留、旧布局收敛与文件锁，不能把整文件当成一个容易拆的模块。第一条可研究的边界是单 writer 对象：目录、writerId、segmentCap、CurrentFile，以及定位目标、滚段、物理追加、fsync/close 与失败阶段。生产由 `Store.fs` 创建并调用 append；已有 segments 只提供命名、成帧等纯规则，没有这个物理 owner。

施工前先完成以下准备，再确定接口与授权范围：

1. **确定输入边界。** 主体仍 normalize/encode EventEnvelope，writer 接收本次完整编码文本或字节。空输入返回 NoAppend；库不认识主体事件、角色或业务提交。产品 `.Herdchestra/wanxiangshu/events` 路径由外侧给入。
2. **列出 CurrentFile 的读写者。** 对象独占缓存文件名，filePath 查询委托它；主体不得镜像另一份。materialization/导入换布局后，缓存目标消失时重新枚举的现行行为保留。先核对换布局与追加的锁范围，而非臆测其并发安全。
3. **确定结局表示。** NoAppend、AppendDurable、BeforeAppend、AfterAppend(primary, cleanupFailures) 与现有 Store 的解释一一对应。物理追加抛错也可能已写部分字节，不能转为“未发生”或自动重试。fsync 与 close 双失败都要保留；不得只留下最后一次异常。
4. **保留滚段规则。** 缓存目标存在则续写它，缺失才回选最高段；恰好上限、空段接受超大 batch、旧 suffixless 原地追加、缓存消失、段号耗尽分别固定。没有全局 writer 排队或新幂等保证；锁仍由现有外层组合管理。
5. **明确不迁范围。** readStreams、读缓存、倒读保留、compaction/materialization 的业务与物理算法先留原处；如共用 helper，按职责复用现有公开 segments 或保留原调用，不跨工程编译原宿主源码。不能迁完 writer 就写“整个 ProcessEventLog 已退出”。
6. **找最小真实失败注入。** 复用 durable-events/005 中追加/滚段与当前文件变化用例、004 的锁释放次序，以及现有物理写/fsync/close 失败夹具。若缺某阶段夹具，先补能改变迁移决定的一条，不能加运行时检查员。重组/保留未改时不跑它们整套回归。
7. **再决定能否切。** 只有在错误、锁与布局变化的关系写清且可保持时，才安排 writer 的完整迁移、主体替换与包消费；否则先整理当前支撑实现。不要为了把计划填满，预定一个看似百行却藏着持久化责任的大坑。

本节起初只作开工准备。前三项依次完成小范围闭环后，已沿下面的真实调用确认状态、目录和错误边界，本轮按用户“继续按顺序”的指令推进这个完整物理对象；不扩大到整个 ProcessEventLog，也不把“多规划一些”等同于继续增加模块数。实际运行结果写在本节末尾，计划本身不代表完成。

### 17.1 沿现行调用得到的边界

`CurrentFile` 仅由 ProcessEventLog 的构造、filePath、目标解析和滚段操作访问；Store 没有另一份缓存。`Store.appendOwned` 先取得跨进程 store lock，再在本地 gate 内准备和调用物理 append，最后释放锁并结算。迁移不能把锁收进 writer，也不能让 writer 自行重试一次结局未知的追加。

当前 `convergeWriterFiles` 的唯一调用是 `RetentionSurface.reorganizeWithSegmentCap` 测试边界，使用同一 `withStoreLock`。不能由历史注释推定生产仍有 materialization/import 调用。保留“目标文件消失后重新枚举”的能力，但说明其实际触发方式；这次不恢复旧同步入口。

路径策略也有状态相关后果：`eventsDirectory` 每次经 `localPath` 检查 `.git` 路径及现存路径的 realpath，创建 writer 时只做 commonDir 的初步检查。若把解析结果固定为构造时的字符串，后来目录变为指向 `.git` 的符号链接就会改变现行行为。建议 writer 绑定 `directory: () => string`，由主体闭包调用原 `eventsDirectory commonDir`，库在原各个取路径位置调用它。库不认识 `.Herdchestra` 或 `.git`，也不把所有路径访问提前到构造时。

### 17.2 接口与退出步骤

接口起点为 `SegmentedWriter({directory, writerId, segmentCap})`，公开 `writerId`、`filePath()`、同步 `append(text)`。对象独占 CurrentFile；段名和序列选择使用既有 `wanxiangli/segments`，不新增相同命名算法。空文本返回 no-append，非空完成返回 durable；失败区分 before-append 和 after-append，并携带原始 cause、phase 与有序 cleanupFailures。写入文本仍由主体 normalize/encode，不在库内检查业务事件。

1. 主体 `ProcessEventLog` 改为持有库对象的薄包装，不留 CommonDir/WriterId/SegmentCap/CurrentFile 镜像。构造保留 commonDir 产品路径初检，再提供目录闭包；writerId 和 cap 的物理合法性由库负责，错误文字保持。
2. filePath、writerId 委托对象；append 保留编码异常到 BeforePhysicalAppend 的转换，再把库物理结果映射到现有 DU。`Store.commitPrepared` 的 NotAttempted/Unknown 解释保持不动。
3. 从主体删除 writer 专用的目标选择、滚段、追加与追加后 barrier/close 链。`seriesFilesOf`、段命名、byteLengthUtf8、AppendAllText、普通 durabilityBarrier 仍被未迁走的整理算法使用，不能按名称批删。
4. 构造的 CurrentFile 固定为 0000；缓存文件存在时直接续写它，只有缓存缺失才枚举最高段，无段时再选 legacy 或 0000。目录同时存在 0000 和 0007 时仍续写 0000，这项保留现状，不把“最高段续写”的简写当成无条件选最高段。保持 legacy 原地追加、恰好上限不滚、空段容纳超大 batch、非空段滚动及 9999 耗尽。CurrentFile 在滚段后、实际 append 失败前已变化的行为也保持，不回滚成另一份虚构状态。
5. appendFileSync 抛错即使已写完整字节，也属于 after-append；open/fsync/close 失败同属该类。fsync 和 close 都失败时 primary 保留 fsync 原对象，cleanupFailures 保留 close 原对象；外层 lock release 错误继续由 Store 追加，库不吞掉或替换它。
6. 库差分测试、隔离构建与安装包消费者完成后，主体只跑真实追加、滚段、结局和相关目录行为。再固定候选、检查实际包消费并合回原目录；不扩大到读缓存、保留或全量重组织测试。
