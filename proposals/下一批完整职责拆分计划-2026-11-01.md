## 第一项：完成记录的读写与解释

### 用途与迁移边界

子工作完成后，父工作需要取回正确的结果；重启后也必须按同样方式解释已保存的记录。新能力暂名 `CompletionRecord`，从现有 `wanxiangli/handle-lifecycle` 导出，不新增子路径或工程。

源头是 [CompletionCodec.fs](../src/Wanxiangshu/Execution/Delegation/Handle/CompletionCodec.fs) 和 [ChildRecovery.fs](../src/Wanxiangshu/Execution/Delegation/Fork/ChildRecovery.fs) 中完成载荷/解码结果的类型。真实调用包括 RunLifecycle 的写入，JoinDrain、Controller、Restart、ChildRecoveryWorkflow 的读回和归属判断。

迁走一整套能力：完成/失败记录编码、历史分类、工作归属判断、ref/digest 配对、读取及摘要核对、缺省值解释。无长期可变状态，不为纯协议制造全局注册表。

主体保留：选择何时读取、Handle 生命周期迁移、Blob 写入与 HandleCompleted 追加、Join 消费、恢复动作，以及 Role/SessionId/RunCompletion 的 F# 形状转换。不要把整个 AgentJournalPort 或恢复工作流传进库。

公开面按用途收敛为 `encode(outcome)`（含 runId）、`decode(body)`、`belongsToWork(work, decoded)`、`materialize(agentId, decoded)`、`read(reference, readBlob, sha256)`。materialize 处理原 runId 回退及空白可选字段，返回中立结果；主体补上调用方已有的角色、名字、completedAt 和 F# 类型。`read` 只取得并核对原始正文；组合者按现有路径选择 decode-first 或直接物化。库返回普通 JS 字段/带标签结果，原错误原因原样交回，读取回调的 Promise 拒绝也不改成另一种失败。原始正文和 ref/digest 随成功读取返回，避免 Join 再读一次。

`events` 的 CanonicalEventCodec 和 `returned-material` 的校验走现有公开入口；不复制 canonical JSON 或材料规则。施工时修准 handle-lifecycle 局部规则中“禁止依赖其它 wanxiangli 模块”的过宽文字，声明这两个实际基础依赖，并把隔离构建夹具按依赖闭包配置好。

### 必须保持的行为

1. 写入仍是 schemaVersion 4。数字 `4` 与字符串 `"4"` 继续按现有字符串化被接受；源码旧 v3 注释只修正说明，不能倒改格式。
2. `status="aborted"` 先于 schema 检查；保留 LegacyFalseAbort 和原始正文，不把它变成可 Join 的完成。completed 的 view 继续要求规范 ReturnedMaterial 字节。
3. 字段读取仍是 own-property 检查和既有字符串转换；不收紧为新严格 schema，不 trim 或重写正文。错误分类、检查顺序、错误文字保持。
4. completed 归属只比 childSession、authorityRoot，并要求 providerRun 非空；failed 只比 childSession。不能额外要求 providerRun 等于某个预期值。没有 Work 的旧记录仍按原调用逻辑放行。
5. Abandoned 误传 encoder 时仍产生 failed/ABANDONED；本轮不改为拒绝。空白 runId 仍回退 `run-<agentId>`；completedAt 由调用方给定，不读新时钟。
6. 仅 CompletedAwaitingJoin 发起读取；ref/digest 都无时不读，单缺报错；摘要先核对再解码。失败不重试、不补记录，不改变 Join 与恢复后续决定。

### 施工步骤

1. 在原实现上固定编码字节、字段强制转换、legacy abort 优先级、归属差异与 ref/digest 读路径。补少量缺失用例，预期值手写，不由新实现反算。

## 第二项：Bookkeeper 单次案例编辑

### 用途、状态和接口

Bookkeeper 用一次程序修改一对问答，失败时不把半次修改写进暂存案例。真实入口为 PluginHooks → CasebookTools.buildSpecs → JsBookkeeperTool；保持现有启用条件，不扩大产品使用范围。

当前实现位于 [BookkeeperPolicy.fs](../src/Wanxiangshu/Repository/Knowledge/Casebook/BookkeeperPolicy.fs) 的 StagedMutation、createApi、runtimeBaseClass，以及 [BookkeeperTool.fs](../src/Wanxiangshu/Repository/Programming/Js/OpenCode/BookkeeperTool.fs) 的运行/结束接线。

在现有 casebook 工程内增加调用级编辑对象，暂名 `CasebookEdit`，私有持有本次原始 Q/A、可选修改与两次 setter 是否成功使用。question/answer 锚点视图、两项 setter、完成后应用一对修改一起迁移；不新增 text-anchor、setter-buffer 等入口。

已有 BookkeeperStaging 仍持有跨调用事务槽和 touched/take/abort；BookkeeperLedger 仍持有会话附着与授权；ProgramSession 继续拥有程序执行和结算。这三者不互相复制状态。

建议由现有 staging 在原 snapshot 时点创建 edit，提供编辑 API 和提交消息；同工程内部完成补丁应用，不把可变字段交给主体。编辑持有的是本次原始快照和补丁，不持有另一份事务槽权威；提交仍按 txId 查找当前槽，保留现有同名覆盖语义，不新加一次提交后拒绝的规则。运行用基类文本由此能力提供，主程序继续传给既有 ProgramSession。接口定稿要保留 stageRequest 的“会话绑定 → program 参数 → snapshot”错误顺序，不增加新的事务代际校验。

留在主体：工具名、权限、会话查找、语言、描述和例子、返回值 JSON 解析、呈现、10000ms 执行预算与现有输出上限。整个 BookkeeperRuntime 的会话启动/订阅/Abort 不迁入本对象。四种 setter 错误通过窄小的本地化回调呈现，仍在错误发生时读资源，不提前求值四段文案。

### 必须保持的行为

1. question/answer 始终读取本次开始的快照，setter 后读取不变。每字段只能成功设置一次；首次非法类型不消耗成功设置次数，重复调用的错误优先级不变。
2. 原程序成功且返回值解析成功后才应用修改；任一失败都不应用这次缓冲。只改一个字段时另一个保持现值；空字符串是合法修改。
3. 成功且零 setter 的程序仍调用原 apply，使 touched 成立。不能以“没有变化”为由跳过，不能把本次状态改成未交付。
4. 锚点按声明顺序向后搜索，RegExp 去 g/y 再加 g，保留 UTF-16 索引、`^/$`、偏移递归与裁剪、零宽匹配、错误顺序和文字。不合并 runtime 文件锚点，两者语义不同。
5. 保持现有同 txId 覆盖、缺失事务失败、并发调用和提交时机；不顺便加互斥锁、乐观版本号、重试或新取消策略。

## 第三项：案例集合的重放与查询

### 完整边界，不迁持久 codec

用户取用已有案例时，要看到已保存的问答及维护后的文件基线；访问顺序决定当前可见的案例集合。当前 [Model.fs](../src/Wanxiangshu/Repository/Knowledge/Casebook/Model.fs) 仍拥有 CasebookProjection.State、四类事件的 apply、观察规范化，以及 evict/projectCases/resolve 的集合处理。

真实调用是 WorkspaceEventStore 注册 [IntegrationRules](../src/Wanxiangshu/Repository/Knowledge/Casebook/IntegrationRules.fs)，由 CanonicalIntegrator 逐事件形成 Current，再经 [Workflow](../src/Wanxiangshu/Repository/Knowledge/Casebook/Workflow.fs)、IndexSurface、FetchTool 和 Bookkeeper 消费。这里的“重放”指已解码案例事实，不是暂缓的 Replay.fs 对文件重新读取。

把案例状态值及全部变化、可见集合和定位行为归入现有 casebook。暂名 `CasebookState`：`empty()` 创建空状态，`apply(event)` 返回新状态，`visible(capacity)` 返回按现行顺序的案例和 victims，`resolve(capacity, shelfmark)` 返回案例或缺失。观察 normalize 作为这项模型的同入口函数供 Capture/Workflow/Bookkeeper 现有调用，不另开工程。

**唯一 Current 仍由 CanonicalIntegrator 持有。** 它装入库的不可变状态值；apply 不能修改输入值，准备后未提交的候选不能污染旧 Current。库不再建立全局 Cases 字典，不扫描历史、不读 EventStore，也不复制已有 CasebookIndex 的 frozen/dirty 状态。索引和淘汰使用同工程已有 CasebookIndexLaw/CasebookIndex 方法，不重写算法。

存储适配原样留主体：Store.fs 的 Thoth 解码、事件载荷编码、Engineer/Inspector 历史名、默认字段、baseline payload refs、UUID/parents、Append、cut 与失败身份。它把已解码的四类事件转换为库输入。这是字节适配与领域状态的正常分工，不为“迁得干净”强搬依赖。底层 codec 将来若确需迁移，另评估完整持久协议，本批不预建新包。

### 必须保持的行为

1. capture 覆盖同 identity 的案例，赋当前访问序后计数加一；refresh/access 不存在的 identity 不变且不推进计数；evict 删除但不推进计数。
2. refresh 的空 maintenanceFileState 与空 relatedPaths 保留旧值；空 observations 却确实清空。Q/A 可为空；completionFileState 和 sourceTrace 仍保留旧值。
3. 观察身份的 `read:`/`glob:`/`grep:` 拼法、分隔符、排序和去重保持；不顺便修潜在碰撞，不把空观察解释成“未知”。既有 classifyReplay 可复用规范化结果，仍不启用 Replay 产品路径。
4. capacity≤0 仍不淘汰；同访问序按原输入顺序决定，案例枚举保持原 F# Map 的键顺序，访问序使用 bigint，不改成有精度损失的 number。
5. 可见集合的裁剪仍是查询，不自动追加 eviction 事件。现有 production capacity pressure 的 TODO 不在本批修复。
6. shelfmark、冲突取首项、索引失效/刷新时机保持。case 缺失继续缺失，不新增补建、回退或恢复。
7. 不改事件字节、旧日志读取、追加未知结果、FaultScope、PlanCut/ApplyCut；不将“apply 得到候选”当作已提交。
