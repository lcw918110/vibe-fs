2026-11-01。第 1–5 项均已在隔离树实施并接回主体，运行结果见文末。下文保留边界选择及没有合并的理由；不把 WarmStart 去留或额外新模块算作已完成。

调查基线：主体 `59d97425085df176c402850a4d17a0ace847f3be`，库 `8650c47e0a677e12495a8dcd63fc4ad9c05ceec5`（0.80.0）。重点逐项查看最近拆出的 13 个模块，追到实际主体调用，并扩查相邻公开能力及早期较小模块。对其余早期入口只作公开契约和依赖筛查，不声称已逐个审阅全部实现。

## 判断方法

代码短不等于边界错，状态独立也不等于必须单占 npm 子路径和构建工程。这里区分三件事：

- 对象或纯函数的职责边界：谁拥有状态，输入输出是什么，为什么会改变。
- 源码组织：同一完整能力可以有多个文件和多个独立对象。
- 公开与构建边界：是否真的值得独立入口、工程、类型声明、隔离构建及安装消费者。

合并可以只发生在后两层。不能为了撤一个入口，合并互不相干的状态、制造模式开关，或让纯计算调用方先构造物理资源。也不能只加一个转发入口，旧工程和装置全部留下。可省的是多余间接层和重复安装装置，有意义的行为测试继续保留。

## 一、先调整两个明确问题

### 1. 撤销 response-text 的独立公开边界

原 response-text 实现只有空白检查、固定工具标签正则和三种返回值，原件在 Git 历史。现已内收 [TerminalValidity](../src/Wanxiangshu/Participant/Provider/Attempt/TerminalValidity.fs)，删除跨库分类转换；[CompletedTurn](../src/Wanxiangshu/Interaction/Repair/CompletedTurn.fs)继续结合真实工具活动、正文和结束原因决定后续。

这次抽取只迁走一个局部词法策略，增加了一层字符串分类转换，没有形成完整的回复解释能力。建议将实现收回现有 TerminalValidity 内部，撤销 `wanxiangli/response-text`，不另造 response 聚合模块。

不并入 llm-text（组织输出表示）、terminal（分发已经确定的结束事实）、projection（选择和排列请求消息）。固定标签表也尚未被证实为某一个宿主专有，不能仅凭名字宣称它应迁进万象通。暂时回到当前响应处理边界，是撤销过细抽取；不把主体文件宣告为永久归宿。以后整理完整回复解释职责时，再按事实决定中立能力与具体宿主适配的归属。

实施时：

1. 把原词法实现收回 TerminalValidity，保留现有 `check/isValid/describe` 签名；移除仅为跨库转换而存在的 TextShape 和 import。
2. 保持当前包含匹配、破损标签、Unicode 空白、大小写及词边界行为，保持原 `XmlOnly` 类型和诊断。本步不解决正文混有工具标签是否应该拒绝的产品策略。
3. 把仍有意义的词法用例收进现有主体相关测试，保留 CompletedTurn 的组合检查；删库旧源码、工程、入口、声明、专用包消费者及仅为它存在的隔离构建分支。
4. 从主体实际包探针移除已撤入口的消费；新库候选与主体适配一起切换，不把旧入口留作永久别名。

### 2. 将根目录缓存内收 workspace-state

[RuntimePathStore](../../wanxiangli/src/workspace-state/RuntimePathStore.fs)拥有 roots 字典、键归一化、按对象身份驱逐和失败 Promise 清理，原先挂在 `git-porcelain` 公开入口。实际生产使用方只有 [WorkspaceState](../../wanxiangli/src/workspace-state/WorkspaceState.fs)，现已内收其中；Git 文本解析不再拥有工作区定位缓存。

建议把这个对象的实现收进 workspace-state，作为定位能力内部状态，撤销 git-porcelain 的 `RuntimePathStore/runtimePathStore` 公开出口。不新增缓存模块，也不再要求 workspace-state 的调用方跨入口清缓存。

保持异步调用共用缓存、同步查询不借用异步缓存、Promise 失败只驱逐原条目等现有行为。测试改为使用独立临时路径、观察公开查询的重复调用与失败重试；不要为了沿用测试另公开 clear/has。已有键和失败清理的有效用例须就近保留，不能仅删除测试了事。

## 二、适合合并公开边界的三组候选

以下按推荐实施顺序排列，各自独立完成后可以停。它们不是为了减少模块数而必须全部做完的清单。

### 3. 优先：segments 与 segmented-writer

共同职责是分段日志文件的格式与物理使用。[WriterSegments](../../wanxiangli/src/segments/WriterSegments.fs)处理命名、布局、成帧与共存计算；[SegmentedWriter](../../wanxiangli/src/segments/SegmentedWriter.fs)持有 CurrentFile 并追加、滚段、落盘。两者现已处于同一工程；主体读取和整理也使用前者，因此纯规则不藏在 writer 实例后。

建议沿用 `wanxiangli/segments` 入口和一个工程，内部分文件保留 **WriterSegments 与 SegmentedWriter 两个对象**：纯规则对象不做 I/O，物理对象只拥有自己的写入状态。删除独立 segmented-writer 工程、入口和跨公开入口 import，内部直接组合唯一的规则实现，不复制源码。

读者无需创建 writer，写者也不管理读缓存。events 编码、保留策略、业务提交、Store 锁不并进来。模块说明须如实改为同时包含纯计算和物理能力，不能继续声称整个入口无 I/O。纯计算单独导入时可能加载该模块的 Node 文件依赖，这是合工程的代价；当前目标是 Node/Bun，若后来明确需要无文件运行时的独立消费，再重审这个选择。

可删一套独立入口/工程及仅验证两者跨工程接线的装置，合并实际安装测试的准备过程；保留命名/格式、缓存重选、滚段、未知追加、fsync/close 原错误和主体接线用例。**本步不改变任何持久化语义。**

### 4. 第二候选：文件基线与纯差异计算；结算状态归回案例能力

原 [file-baseline](../../wanxiangli/src/file-baseline/FileBaseline.fs)只从 casebook-maintenance 使用 `readFailure/fileDiff/summarize`，主体 Capture 另用 `truncate`。这些现已归入同入口的 [FileDiff](../../wanxiangli/src/file-baseline/FileDiff.fs)，构成“文件原件 → 差异 → 差异视图”的同一能力。

原 casebook-maintenance 工程还编译 CasebookSettlementOwner，后者持有按事件保存的冲突状态并报告案例不可用，与文件读取和 diff 无关。现已移入 [casebook](../../wanxiangli/src/casebook/CasebookSettlementOwner.fs)；没有把整个旧目录塞进 FileBaseline。

建议分别归位：

- `file-baseline` 保留 FileBaseline 对象，吸收纯 diff/summary/truncate 实现；纯函数或独立纯对象与 FileBaseline 并列公开，不要求只截断文本的调用者提供 payload 或路径能力。readFailure 可内收。
- `CasebookSettlementOwner` 移入现有 `casebook` 工程和入口，继续是独立对象，不并入索引或基线状态，不改变冲突报告、身份与去重规则。
- 两类消费者完成切换后撤销 `casebook-maintenance` 入口/工程，不保留转发壳，也不新增 settlement 独立包。

收益在于消除一个混合职责的工程及一条公开依赖，而不只是合并小文件。代价是同时调整两类消费者，所以排在分段日志之后。现有 casebook 工程本身已有多个对象；这里仅归入案例可用性状态，不能以此为理由继续把所有知识处理收进去。

分别保留纯 diff/截断、基线字节与单次读取、结算失败三类测试；只合并重复安装准备，不将库侧成功当作案例真实刷新已接回。

### 5. 第三候选：Git 解析、工作树资源与发布操作

[GitWorktrees](../../wanxiangli/src/git/GitWorktrees.fs)和 [GitPublication](../../wanxiangli/src/git/GitPublication.fs)共用 repo＋runner 命令形状，并由主体 [GitOperations](../src/Wanxiangshu/Git/Operations.fs)显式组合。现已归到 `wanxiangli/git` 一个入口和工程，保留各自对象、错误契约及资源状态；没有新建拥有一切的 GitManager。

这项先有两个清理前提：

1. 完成上述 RuntimePathStore 归位，Git 模块不再替工作区定位持有缓存。
2. 从 git-porcelain 分离 `managerBranchOf/isManagerBranch/staleWorktrees/staleBranches` 的产品规则。它们由主体 [Change/Runtime](../src/Wanxiangshu/Change/Runtime.fs)及 [WorktreeCleanup](../src/Wanxiangshu/Change/Host/WorktreeCleanup.fs)实际使用；`manager/` 分支约定和活动任务归属不是 Git 原生协议。规则应贴近现有 Change 策略，不是放进万象通，也不新增 branch-policy 小包。解析与物理清理由 Git 对象负责，什么该清理由产品决定。

归位之后，纯解析可作为 Git 工程内部基础文件。workspace-state 仍须从新公开入口消费所需的 `primaryWorktree` 解析能力：可保留精简后的 GitPorcelain 对象，或明确的纯解析函数；不能跨编译私有源码。主体仅用于转发未使用解析函数的旧桥可删除，不能把“主体没调用”误当作“库内和定位模块也没调用”。

workspace-state 保持独立：它定位主工作区并管理状态目录，与工作树租约、发布操作生命周期不同。不得顺手把它的直接 execFile、同步查询和严格非 Git 回退改成发布模块的 ProcessRunner。

预期可将三个 Git 工程/入口收成一个，合并工作树和发布包测试的重复安装准备；保留分别覆盖资源释放、发布顺序、解析及定位的用例。因为包含产品规则归位，风险和改动面大于前两组，排在后面。只有一个新 barrel 而旧工程仍全部存在时，不实施这种名义合并。

## 三、最近 13 项的去留结论

| 模块 | 建议 | 主要原因 |
| --- | --- | --- |
| response-text | 撤独立入口，贴回当前 TerminalValidity 内部 | 局部词法策略多出公开分类桥；不等于完整回复解释能力 |
| llm-text | 保留 | 文档、指令、数据块和值的表示边界完整；原 synthetic-toml 已在同一工程内部，无须再次拆小 |
| returned-material | 保留，不并 delivery 或 llm-text | 是持久完成记录也直接使用的规范值格式；交付格状态和输出呈现可分别变化 |
| bounded-map | 先处理使用方去留，不找大模块收纳 | 静态链只确认 WarmStart/Semble → Surface，尚未确认产品入口；不是已证实无任何动态消费者 |
| keyed-serial | 本轮保留；完整 Trace Capture 收拢时再考虑内收 | 53 行有真实跨调用按键尾表，但仅一个生产使用边界，公开收益有限；不为它另造 async 杂物模块 |
| task-scope | 保留 | Fork 与插件两处使用；接纳、前后台错误、排空与关闭是一套完整生命周期 |
| result-mailbox | 保留 | 拥有结果、活动计数与 join 等待；不负责运行或关闭任务 |
| file-lock | 保留 | 两处真实跨进程租约消费者；进程内串行队列不能替代释放失败与物理锁语义 |
| workspace-state | 保留，并内收根目录缓存 | 定位、严格错误回退和状态目录操作有独立用途 |
| git-worktrees | 与 Git 组收同入口，保留资源对象 | 合工程不取消工作树资源自身的生命周期 |
| git-publication | 与 Git 组收同入口，保留发布对象 | 候选准备/发布协议不接管工作树资源、授权或重试决策 |
| file-baseline | 吸收纯 diff/summary/truncate，保留组合对象 | 文件读取、payload 保存与同次差异组成完整能力；案例冲突状态不进入其中 |
| segmented-writer | 与 segments 收同入口，保留物理 writer | 格式与物理使用同属分段文件能力，读者和写者不被迫共享实例 |

bounded-map 的下一步应是检查 WarmStart 产品需求与可能的动态入口：若整条能力已经退出，才一起删除仅服务它的接线、测试专用表面及公开入口；若仍要产品能力，应整理真实调用路径后再决定调度器是否作为内部实现。**不为保住一个库而新增产品调用，也不为了本轮合并擅自启用或删除用户功能。**

不建议把 ResultMailbox 与 program/wait 的 CompletionMailbox 合成可配置邮箱。前者 wakeOne、活动计数、单次 join 中断；后者双通道、wakeAll、永久 cancel，并依赖 CausalWait 类型。现在没有共同协议能抵消新翻译成本，也不应让 Change 只为收结果就依赖整个 program。

同理，TaskScope、KeyedSerial、bounded-map、admission-queue 和 runtime 的 LargeGate 不能因为“都在等”合成 concurrency 工具包。它们分别负责关闭排空、按键串行、每调用限流、请求代际仲裁和单许可等待，取消与失败行为不同。

## 四、早期模块的扩查结果

- **provider-calibration（36 非空实现行）保留。** 同一个会话的最新用量和声明上限由不同宿主观察入口更新，由展示读取，随会话退出一起清理。它虽短，却是真实共用状态；不并入 failure-budget、capacity 或提示渲染。[实现](../../wanxiangli/src/provider-calibration/ProviderCalibration.fs)
- **external-namespaces（20 行）优先重审所属层，不按大小合并。** 它持有两处 OpenCode 消费者共享的历史声明集合，同时硬编码 `server_` 前缀及 `server_*` 模式。命名翻译应随外部工具配置/准入适配归万象通；保持进程内历史并集与本次配置投影的区别，不能分成两份局部集合，也不能与 provider-calibration 拼成状态仓。当前万象通只有说明，实施须先明确可编译的适配落点；本轮不声称它已迁出。[实现](../../wanxiangli/src/external-namespaces/ExternalNamespaces.fs)、[配置调用](../src/Wanxiangshu/OpenCode/Host/ManagedAgentConfig.fs)、[准入调用](../src/Wanxiangshu/OpenCode/Host/ExternalToolAdmission.fs)
- **quarantine、retention 不并进分段写入器。** 前者持有规则/作用域的隔离值与截尾解释，后者决定整条 writer 的活动与保留；写入字节不应获得案例/规则隔离或删除历史的决策权。这里保留职责边界，不对其全部历史实现作背书。
- **Work/Journal/DurableWork、program/runtime 的分工不因模块数调整而合并。** 领域状态、持久提交与组合，以及程序结算与物理执行，仍有明确的不同变化原因。也不能仅为收纳短函数，把 runtime 或任何已有大模块当作杂物柜。

## 五、施工顺序与停止条件

推荐顺序是：response-text 撤入口 → 根目录缓存归位 → segments 收拢 → 文件基线/案例结算归位 → Git 组收拢。WarmStart 去留、external-namespaces 适配归属单独处理，不夹带进以上行为保持的整理。

每步先在隔离工作树确认实际消费者，给出最终公开接口与明确删除清单，再手工调整。合库时仍保留内部对象的独立状态，不建立共享全局账本；需要新模式开关、复制实现、仅用于转发的新层才能接上的，重新缩小范围。

库入口变化使用同一新候选完成主体 import、锁定输入、实际安装和 pack 消费切换；不以“只是改目录”为由跳过发行闭包。复用现有交付步骤，不新增流程。只重跑本步受影响的行为、真实主体调用和依赖/分发检查；原始字节、正则解释、取消时点、未知结果和资源释放都保持。

若没有实际减少公开边界、工程或重复适配，或合并迫使独立使用方承担不需要的生命周期，就停下保留现状。没有模块数量或行数目标，也不把完成全部候选作为本轮调整成立的条件。
