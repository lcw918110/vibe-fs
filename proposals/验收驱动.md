# Work / DurableWork / Projection：2026-10-26 设计记录

**状态：历史设计记录，已实施，不冒充现状。** 本文只解释当时为什么这样分包、时序为什么这样排；现行合同在 `requirements/work/WHAT.md`、`requirements/context-compression/WHAT.md`、`wanxiangli/src/lifecycle/AGENTS.md` 与 `wanxiangli/src/assembly/AGENTS.md`。实现见 `wanxiangli/src/lifecycle/Program.fs`（`WorkBuilder`）与 `wanxiangli/src/assembly/DurableWork.fs`。

## 1. 为什么是三个包

当时把工作生命周期重新评了一遍，结论是不拆成 `work-review`、`work-relay`、`work-stage`、`work-ask`、`work-ce` 五个小包：它们不是五个独立职责，而是同一工作协议内部的五种行为。拆开会迫使外部组合者同时照看同一任期的多个状态。

| 包 | 职责 |
| --- | --- |
| `wanxiangli/work`（源码 `src/lifecycle/`） | 里程碑、任期、义务账与 Review 时序协议 |
| `wanxiangli/durable-work`（源码 `src/assembly/`） | 持久提交、效果调度、失败恢复与操作闭环 |
| `wanxiangli/projection` | 按已提交的 Context Barrier 生成新任可见的历史 |

`authority`、`capability`、`eventstore` 继续独立，只调整必要的协议接口。`wanxiangli/delivery` 不在删除范围：它管材料交还、调用围栏与去重，不是生命周期 `deliver` 工具，名字相同不代表职责相同。

## 2. 用户看得见的时序

Plan 里程碑：事实与取舍 → 理解与路径 → 流程与伪代码 → 待执行。Manager 里程碑：执行 → 收尾 → 已完成。任期只有 Originator 与 Successor。

- **初任**：空账就问「我需要干什么？」并真实等待；用户答复后仍是同一任。第一次非空账才进入工作期；此后账被清空则交棒。
- **接任**：第一次评审空账直接晋级下一里程碑，不新建任期、不建屏障；非空则进入普通工作期。
- **待执行**：每次新的空账 review 启动一个独立 Manager Session；同一调用重放不会二次启动。
- **收尾**：空账且真实资源阻塞解除即结案，不另立验收任期。
- **已完成**：只有新的真实操作员消息重开一次；Advisor、系统 steer 或代理答复不触发。

生命周期工具只有 `review` 一个入口。执行到哪个等待点，本身就决定了下一次 review 该怎样解释——不靠一串 `IsFirstReview` / `ShouldRelay` 布尔条件。

## 3. 仍然成立的协调约束

这几条与当时的具体实现无关，今天读来仍是对的：

- **Ask 跨两个持久账本**（Work 的预留与 PromptAuthority 的提问），不能声称一次 SQLite 原子事务。顺序是「Work 持久预留 → 确认提问 → 物理 park → 用户答复 → 恢复 Work」，各步用同一稳定操作身份关联。外部结果未知时只观察或恢复原请求，不盲目重发。
- **先提交事实，再发提示**。Relay 在同一笔事务里写下旧任退休、后任打开、精确屏障与待发提示身份；崩溃发生在提交与发送之间时，重启按同一持久派发身份补齐，不制造第二条提示。
- **启动不消耗待执行状态**。每次启动绑定 `planWorkId + providerRunId + toolCallId + 当前成果 digest`；同一次调用重放沿用同一 operation。任何一步结果未知，都不自动创建第二个 Manager。
- **收尾先提交终态，再停止当前 attempt**。停止请求与停止已被观察到是两回事。
- **CE 不持久化函数闭包**。持久化的是领域事实与确定性等待位置，恢复时重新解释已提交事实找到当前合法等待点；这样同一套程序可在 Node、Bun 与不同宿主上跑，也不受进程重启影响。

## 4. 当时的 Context Barrier 意图

屏障是工作任期的可见性边界：新任看不到触发接力的 Review 及其之前的 operator / assistant / tool 历史，但持久原始历史完整保留，改变的只是后任的 Provider 请求视图。屏障身份与精确物理切点由 Work 提交，不靠消息下标、固定加一或游标猜测；归属不明的消息保持待核实，而不是泄漏给新任。

现行投影规则以 `wanxiangli/src/projection/AGENTS.md` 第 2 条为准：role 为 user 且不是合成行的消息全部进入后任，原序保留；其余消息在切点之后只保留 `tenureId` 等于后任的。这与 2026-10-26 的设计不同，按现行规则读。

## 5. 当时的宿主退出方向

宿主不再持有 Plan / Manager 生命周期的第二份判断，只提供真实事件与执行能力。`Mission/Work/*.fs` 等宿主文件仍在树中，其去留见 `requirements/GAP.md` 第 7 条。旧文的「旧代码退出清单」「实施顺序」「必须覆盖的反例」三节已删除，施工流水在 git。
