# 验收驱动接力：Wanxiangli Clean-break 重构方案

**状态：架构方案，尚未实施**

**范围：** 从废除生命周期 `deliver` 工具开始，到 Review 驱动的接力、晋级、Ask、待执行、收尾、重开，以及 F# CE 时序 DSL。

**明确排除：** Advisor 四段咨询、ScopeProgress、resetScope、negotiate、askPreviousScope 和系统 compaction 的既有改造。新工作生命周期只与这些系统通过已有事件及投影接口协作，不接管其状态。

## 一、重新评定包的数量

### 最终采用三个包

| 包 | 处理方式 | 唯一职责 |
|---|---|---|
| `wanxiangli/work` | **彻底重写** | 拥有里程碑、任期、义务账和 Review 时序协议 |
| `wanxiangli/durable-work` | **彻底重写** | 拥有持久提交、效果调度、失败恢复和完整操作闭环 |
| `wanxiangli/projection` | **重构现有任期投影** | 根据已提交的 Context Barrier 生成新任可见的历史 |

不创建 `work-review`、`work-relay`、`work-stage`、`work-ask`、`work-ce` 等小包。

原因是它们并非五个独立职责，而是**同一工作协议内部的五种行为**。拆成五个包会迫使外部组合者同时照看同一任期的多个状态。

### 已有支撑包

`wanxiangli/authority`、`wanxiangli/capability` 和 `wanxiangli/eventstore` 继续作为独立职责使用，只调整必要的协议接口。

特别注意：

**`wanxiangli/delivery` 不在删除范围。**

这个包管理的是材料交还、调用围栏和去重，不是 Plan／Manager 的生命周期 `deliver` 工具。名字相同不代表职责相同，不能误删。

因此，本次需要重写的生命周期核心是**两个包**，另外重构一个已有投影包。

## 二、当前实现的实际问题

### 2.1 `wanxiangli/work`

目前在：

`wanxiangli/src/lifecycle/`

其中：

- `State.fs` 定义旧 S1～S4 阶段及 Delivered／Relayed 事实。
- `Work.fs` 把 Review 和 Deliver 设计为两个独立命令。
- `Wire.fs` 编解码旧生命周期记录。
- `index.d.ts` 继续公开 `Deliver`、`PlanAuthorized`、`Promoted` 等旧操作。

主要问题不是代码位置，而是模型已经过时：

1. Review 只记录资格，Deliver 才执行推进。
2. 第一次 Review 决定的晋级资格长期锁定。
3. 空账后需要另一次模型调用。
4. 初任 Ask、接任首评快速晋级和收尾结案没有形成统一时序协议。
5. 原地晋级、任期接力和完成后的重新开立由不同调用路径拼接。

**裁决：整个 Work 领域对象及公开协议重写，不在旧 `Deliver` 命令上继续增添分支。**

### 2.2 `wanxiangli/durable-work`

目前在：

`wanxiangli/src/assembly/`

它已经正确承担一项独立职责：把 Work 决定和 Journal 的原子追加组合起来。

但它现在主要处理同步 `execute`、提交冲突和 Unknown。

新协议还需要协调：

- Review 产生的持久 Ask 意图。
- 真正的 `UserQuestionAsked` 与物理 park。
- 接力屏障与下一任提示词。
- 晋级后下一里程碑提示词。
- 待执行状态下可重复的 Manager 启动。
- S7 完成后的物理停止及重开。
- 崩溃后未完成的外部操作。

这些协作不能继续全部散落在宿主。

**裁决：保留 `durable-work` 这一包的职责定位，重写它的执行协议，让它成为真正完整的持久工作协调者。**

### 2.3 `wanxiangli/projection`

目前的 `tenure` 投影主要按 `openingCursor` 过滤旧 assistant/tool 消息，**同时无条件保留非合成 user 消息**。

这与新 Context Barrier 的要求不同：

> 新任不能看到触发接力的 Review 及其之前的任何历史。

因此不能直接沿用旧过滤语义。

**裁决：在现有 `projection` 包内重构任期可见性，不新建 Work 专用的第二套历史投影包。**

原始历史仍由持久层完整保存；只改变后任的 Provider 请求视图。

## 三、全新 Work 时序模型

### 3.1 不再使用 S1～S7 编号

采用两个里程碑序列：

**Plan**

事实与取舍 → 理解与路径 → 流程与伪代码 → 待执行

**Manager**

执行 → 收尾 → 已完成

里程碑与任期相互独立。

任期具有两个来源：

`Originator`：当前里程碑的初任。

`Successor`：经同里程碑接力打开的后任。

晋级后，同一个工作者成为新里程碑的 Originator。

### 3.2 初任协议

初任首先等待一次真正的实质评审。

如果提交 Review 后义务账为空：

- 不产生 Reviewed。
- 按现有 Ask 机制向用户询问“我需要干什么”。
- 真实 park。
- 等待用户回复，随后仍由本任继续。
- 再次直接空账，继续 Ask。

直到第一次产生**非空义务账**，才提交真正的 Reviewed，进入正常工作期。

正常工作期持续接受增量评审。义务账清空时执行接力。

### 3.3 接任协议

接任首先进行独立验收。

第一次 Review 直接产生空账：

- 不再接力。
- 不建立 Context Barrier。
- 当前任期直接晋级下一里程碑。
- 在 Review 执行期间排队下一里程碑提示词。

第一次 Review 产生非空账，则进入普通工作期。之后清空义务账时再次接力。

### 3.4 特殊终点

**Plan 待执行**

每次新的 `review([])` 可以启动一个独立 Manager Session。

Plan 始终保持待执行。不同调用可以反复启动；相同调用重放不能再次启动。

**Manager 收尾**

任意一次 Review 清空义务账，且实际资源阻塞解除，直接结案。不要求新的独立验收任期。

**Manager 已完成**

新的真实操作员消息重新打开执行任期。

Advisor、系统 steer 或其他代理答复不触发重开。

## 四、Work 包的 F# CE 设计

不建议开发一个通用 Workflow 引擎。

只实现一个领域专用的 `work { ... }` Computation Expression。

它表达的不是一次性执行的 Task，而是**能够停在持久等待点、再由真实事件恢复的时序程序**。

### 4.1 领域程序

下面是目标 DSL 形态。原语名称是新设计，并非当前仓库已存在的 API。

```fsharp
let rec originator milestone = work {
    let! review = awaitReview milestone

    match review.Obligations with
    | Empty ->
        do! askAndPark "我需要干什么？"
        return! originator milestone

    | NonEmpty _ ->
        do! commitReview review
        return! workUntilClear milestone
}

and workUntilClear milestone = work {
    let! review = awaitReview milestone

    match review.Obligations with
    | NonEmpty _ ->
        do! commitReview review
        return! workUntilClear milestone

    | Empty ->
        do! relayWithBarrier review
        return! successor milestone
}

and successor milestone = work {
    let! review = awaitReview milestone

    match review.Obligations with
    | Empty ->
        do! advance milestone review
        return! enterNextMilestone milestone

    | NonEmpty _ ->
        do! commitReview review
        return! workUntilClear milestone
}
```

这里没有一串 `IsFirstReview`、`IsSuccessor`、`ShouldRelay` 布尔条件。

执行到了哪个等待点，本身就说明了下一次 Review 应当如何解释。

### 4.2 特殊里程碑

```fsharp
let rec readyToExecute = work {
    let! request = awaitEmptyReview

    do! launchManagerExactlyOnce request

    return! readyToExecute
}

let rec cleanup = work {
    let! review = awaitReview Cleanup

    match review.Obligations with
    | NonEmpty _ ->
        do! commitReview review
        return! cleanup

    | Empty ->
        do! completeWhenUnblocked review
        return! completed
}

and completed = work {
    let! message = awaitAuthenticOperatorMessage

    do! reopenExecution message

    return! originator Execution
}
```

这些分支复用 Work 自己的里程碑、任期与义务账，不创建另外三套状态机。

### 4.3 CE 不持久化函数闭包

这是实现中的重要边界。

Work CE 应被解释成有限的领域指令及等待点，例如：

`AwaitReview`、`AwaitOperatorAnswer`、`CommitReview`、`Relay`、`Advance`、`LaunchExecution`、`Complete`。

持久化的是**领域事实和确定性的等待位置**，不是 F# continuation、Promise 或 Task 对象。

恢复时重新解释已提交事实，找到当前合法等待点。

这允许同一套程序在 Node、Bun 和不同宿主中运行，也不受进程重启影响。

## 五、DurableWork 包的职责

`Work` 负责决定什么动作合法。

`DurableWork` 负责把合法动作真正执行完。

两者不能各自保存一份权威生命周期账。

### 5.1 一笔 Review 的执行

新的协调过程是：

```text
接收真实 Review 调用及物理身份
        ↓
读取已提交 Work 事实
        ↓
Work CE 解释当前等待点
        ↓
获得领域转移及其待执行效果
        ↓
在同一 Work Journal 事务内提交
        ↓
根据提交回执执行对应外部效果
        ↓
按持久身份确认效果
        ↓
生成工具回执
```

Work 返回的是可验证的领域决定，不在命令结果中夹带要求宿主猜测的脚本。

DurableWork 负责效果的真实顺序、回执归属和恢复。

### 5.2 Ask

初任空账时，Work 产生 `QuestionRequested` 一类的持久工作意图。

DurableWork 将它提交后，调用现有 PromptAuthority 的真实用户提问机制。

这里涉及两个不同的持久账本，因此不能虚称两次写入是一个 SQLite 原子事务。

正确协议应当是：

**Work 持久预留提问 → PromptAuthority 确认提问 → 物理 park → 用户答复 → 恢复 Work。**

各步以同一个稳定操作身份关联。

如果外部提问结果未知，只能观察或恢复原请求，不能盲目再次发送。

整个 Ask 不提交 Reviewed，也不推进里程碑。

### 5.3 Relay 与 Advance

Relay 的生命周期事实必须在一笔 Work 事务中同时建立：

- 旧任期退休。
- 下一任期打开。
- 精确 Context Barrier。
- 待发送的继任提示身份。

Advance 则在一笔事务中推进里程碑，并记录下一阶段提示的派发义务。

提示词不能先发、后补生命周期事实。

只有确认提交成功后才允许发送。

如果崩溃发生在提交和发送之间，重启后根据同一持久派发身份补齐，不能制造第二条新提示。

### 5.4 LaunchManager

现有系统已经有值得保留的事实：

`DeliveryRequested`、`DeliverySessionBound`、`DeliveryRejected` 及其实际接受确认。

但要改变一个重要假设：

**每一次执行启动都不能退休或消耗 Plan 的待执行状态。**

新的启动 operation 应绑定：

`planWorkId + providerRunId + toolCallId + 当前待执行成果的 digest`

同一次调用重放沿用同一 operation；另一条新的有效 Review 调用拥有新的 operation。

因此，同一份 Plan 可以独立创建任意多个 Manager Session。

外部流程继续遵守：

持久预留 → 创建 Session → 持久绑定 Session ID → 发送底稿全文 → 确认真实准入。

任何一步结果未知，都不自动重新创建第二个 Manager。

### 5.5 Complete 与 Reopen

Manager 收尾结案先提交持久终态，再进行当前 Provider attempt 的实际停止。

停止请求与停止已观察到成功，是两回事。

完成状态收到新的真实操作员消息后，由同一工作账原子创建新的执行任期；已退休记录不复活。

这一切都由 DurableWork 协调，宿主只提供真实事件和执行能力。

## 六、Context Barrier 的新合同

Context Barrier 不等于 `resetScope`，也不要求修改此前的 Scope 系统。

它是**工作任期的可见性边界**。

触发 Relay 的 Review 及其之前的历史，新任全部不可见。

具体包括：

- 以前的操作员消息。
- 以前的 assistant 消息及可见 reasoning。
- 以前的工具调用和工具结果。
- 触发接力的 Review 本身及其结果。

这些记录仍存在于持久原始历史中。

新任看到的第一批工作内容，应来自**新任提示和屏障之后确实属于它的消息**。

### 技术变化

现有 `wanxiangli/projection.tenure` 有两个必须修改的旧行为：

1. 不再无条件保留全部历史 user 消息。
2. 不再仅凭消息带 Host ID、但尚无 XTrace 游标，就推定它一定属于新任。

新接口应直接接收 Work 产生的持久屏障身份及精确物理切点。

切点必须覆盖触发 Relay 的工具调用及其对应结果，不靠消息数组下标、固定加一或猜测游标实现。

消息尚未能够可靠归属时应保持待核实，而不是把旧内容泄漏给新任。

现有 `projection` 的线格式规范、布局冲突裁决和其他非 Work 功能仍归它自己，不迁入 Work。

## 十、必须覆盖的反例

核心验收围绕实际时序，而不是仅检查最终状态：

- 初任连续三次空账，只产生三次真实 Ask，零 Reviewed、零接力；真实回复后仍是同一任。
- 第一次非空评审建立实质工作期；后续增量删除使义务账清空，才真正 Relay。
- 接任第一次空账直接 Advance，不生成新任期或 Context Barrier。
- 接任首次非空后再清空义务账，必须 Relay，不能错误晋级。
- Plan 三个里程碑逐项推进，最后进入稳定的待执行。
- Plan 待执行的相同 Review 调用重放只启动一次；三个不同有效调用允许三个互不混淆的 Manager Session。
- Manager 执行接力、接任首评晋级收尾、收尾任意空账结案。
- Manager 已完成后，真实操作员消息只重开一次；Advisor steer 与代理消息零重开。
- Relay 后新任看不到触发 Review 及此前的任何消息；原始持久历史逐字节不变。
- 每个效果在 Committed、Replayed、Conflict、Unknown、崩溃后恢复和迟到回执下均不重复。
- `deliver` 不再出现在生命周期工具目录、权限映射和模型可见帮助中；正常接力与结案仍可完成。

最终还需要真实 OpenCode Provider 请求、OMP 相关边界、Node／Bun 独立 npm 包消费及本机 SQLite 强杀恢复测试。

## 方案定论

**两个完整自治对象承担工作时序和持久协作，一个既有投影对象承担任期可见性。**

`wanxiangli/work` 决定合法的下一步。

`wanxiangli/durable-work` 确保它确实发生且可恢复。

`wanxiangli/projection` 确保接任者只看到属于自己的历史。

宿主不再持有 Plan／Manager 生命周期的第二份判断。

**整个协议只有一个验收入口 `review`：初任空账则询问，实质评审后清账则交棒；接任首评空账则晋级，收尾清账则结案，待执行空账则启动独立 Manager。**
